# 页面自动化优先链路

这份文档回答的是：

- 你们已经把 `Playwright + MCP` 接进来了，接下来最值得拿它自动化什么
- 哪些链路最能体现 `AI-Agent-OS` 的平台价值
- 哪些链路适合用 `Playwright smoke`
- 哪些链路更适合用 `MCP` 交互式操作

结论先说：

- 第一优先不是“把所有页面都测一遍”
- 第一优先是把 **最容易回归、最影响 AI 开发闭环、最能体现平台价值** 的链路先打通
- 你们项目最适合优先自动化的，是 **工作空间主链路 + 服务树操作 + 工作台 + 动态页面 + Hub**

## 分层建议

- `Playwright Test`
  - 用来做稳定 smoke / 回归
  - 目标是“每次改代码都能快速知道主链路有没有坏”
- `playwright-mcp`
  - 用来做交互式排查、复现、截图、验收
  - 目标是“让 AI 真正进系统里点、看、操作”

不要把两者混成一套：

- 稳定回归用 `Playwright Test`
- 临场排障和开发联调用 `MCP`

## 优先级清单

### 1. 登录 -> 进入工作空间 -> 选择工作空间

这是所有页面自动化的入口链路。

为什么优先：

- 后续所有操作都依赖它
- 它同时验证登录态、路由守卫、工作空间选择器
- 一旦这里坏了，后面所有 smoke 都没有意义

建议：

- `Playwright Test` 固化成最小 smoke
- `MCP` 用来排查“为什么今天进不去工作区”

当前状态：

- 已有基础 smoke

### 2. 工作空间切换器 -> 切换到指定 workspace

这是你们系统最核心的导航动作之一。

为什么优先：

- 你们不是单应用，而是“一个用户管理多个工作空间”
- 很多 bug 会出在 workspace 切换后的状态同步、路由刷新、服务树重载

建议：

- 自动化验证“打开切换器 -> 选择 workspace -> URL 和主面板联动”
- 这条适合做稳定 smoke

当前状态：

- 已有基础 smoke

### 3. 服务树根目录操作：创建目录 / 创建文档 / 创建讨论区

这是“从空工作空间长出结构”的核心能力。

为什么优先：

- 它代表 AI 生成或人工搭建系统的第一步
- 目录、文档、讨论区都是后续系统构建的基础单元
- 很多生成类需求，本质上都会落到这三个动作

建议：

- 至少先覆盖创建目录
- 然后再补文档、讨论区

当前状态：

- 创建目录已有 smoke
- 文档、讨论区值得下一步补

### 4. 打开目录详情 / 文档详情

这条链路代表“服务树点击后，右侧主区域是否真的渲染正确”。

为什么优先：

- 它是目录树和主工作区联动的核心
- 你们很多内容沉淀在 Docs 里，文档页是高频场景
- AI 做需求分析、读平台说明、读 SDK 文档都会频繁进这里

建议：

- 验证点击文档节点后 URL、标题、正文渲染
- 验证目录详情页 tab 切换正常

当前状态：

- 已可通过 MCP 实际打开
- 还值得补成稳定 smoke

### 5. 打开 Mini Workstation -> 输入消息 -> 发送

这是你们“AI 原生开发入口”的核心链路。

为什么优先：

- 这是最能体现项目特色的页面之一
- 它不是普通后台功能，而是“让 AI 真正参与开发”的入口
- 一旦这里不稳定，你们整个平台最核心的体验就会打折

建议：

- 验证从目录树打开工作台
- 验证输入框激活、发送按钮状态变化
- 后续再补“发送后会话生成”

当前状态：

- 打开工作台、输入激活已经有 smoke
- 发送后会话流转值得下一步补

### 6. 会话面板：新增会话 / 切换会话 / 查看历史

你们不是一次性聊天，而是工作区内带上下文的长期会话。

为什么优先：

- AI 开发过程天然依赖会话历史
- 这里很容易出现“新建了但不显示”“切换后主面板不同步”“筛选状态错乱”

建议：

- 验证新增会话按钮
- 验证会话列表筛选 tab
- 验证切换会话后右侧状态同步

当前状态：

- 只有锚点，尚未形成完整 smoke

### 7. Form 页面：打开 -> 输入 -> 提交

这条是“业务应用真正可用”的核心。

为什么优先：

- 对平台来说，`Form` 是标准能力之一
- AI 生成出来的很多“工具型功能”最终会落成 Form
- 没有表单提交验证，生成页面再多也只能算半成品

建议：

- 先找一个稳定 form 示例
- 验证字段渲染、输入、提交按钮、成功提示
- 后续再补权限不足场景

当前状态：

- 只有页面锚点，未形成真实提交流程 smoke

### 8. Table 页面：打开 -> 搜索 -> 新增 / 编辑 / 删除

这条是“管理系统型需求”的核心链路。

为什么优先：

- `Table` 是后台业务系统的主战场
- 你们平台要做企业应用，表格 CRUD 回归一定会很高频
- 这也是最容易在改 schema、权限、行详情时出回归的页面

建议：

- 先做打开 + 搜索
- 再做新增 / 编辑 / 删除中的一条最稳定分支
- 不要一开始就把所有表格复杂操作都塞进一个大用例

当前状态：

- 只有锚点，未形成真实 CRUD smoke

### 9. 权限链路：申请权限 -> 审批 / 管理 -> 页面状态变化

这是你们平台区别于普通低代码系统的关键横切能力。

为什么优先：

- 你们反复强调权限是平台级能力，不应在业务代码里重复实现
- 如果权限链路跑不稳，平台的治理价值就很难站住

建议：

- 先做最小链路：无权限页面 -> 进入权限申请入口
- 后面再扩到审批列表、授权列表

当前状态：

- 页面和列表能力已经存在
- 还没有浏览器级回归覆盖

### 10. Hub 链路：发布到 Hub / 推送到 Hub / 从 Hub 安装

这是你们最有平台飞轮潜力的一条能力链。

为什么优先：

- Hub 是“资产沉淀和复用”的核心
- 如果这条链路稳定，你们才真正从“能生成系统”走向“能复用系统”

建议：

- 先验证发布/推送弹窗能稳定打开
- 再验证最小发布路径
- “从 Hub 安装”建议拆两层：
  - 组件/单测锁住弹窗初始化
  - E2E 再逐步逼近真实剪贴板或粘贴行为

当前状态：

- 发布/推送弹窗入口已做基础覆盖，但取决于当前目录业务条件
- 从 Hub 安装的弹窗初始化 bug 已修复，并有单测覆盖
- 剪贴板驱动 E2E 在 headless Chromium 下仍不稳定，不建议暂时把它当主 smoke

## 最推荐的推进顺序

如果只按投入产出比来排，我建议这样推进：

1. 登录 -> 工作空间 -> 服务树 -> 主面板
2. 创建目录 / 打开文档 / 打开目录详情
3. 打开工作台 -> 输入 -> 发送 -> 新增会话
4. Form 打开与提交
5. Table 搜索与一条最小 CRUD
6. 权限申请入口
7. Hub 发布 / 推送

这个顺序的好处是：

- 先保平台骨架
- 再保 AI 开发主链路
- 再保动态业务页面
- 最后覆盖平台飞轮能力

## 不建议一开始就重押的方向

- 不要先做大量像素级 UI 回归
- 不要先做最复杂的剪贴板 / 浏览器权限 / 上传场景
- 不要试图在一周内把所有 `Form/Table/Chart` 都做完

更合适的节奏是：

- 先把高频主链路稳定
- 再补高价值业务链路
- 最后再做复杂边缘场景

## 当前仓库里的现实基线

目前这套仓库里已经具备的基础包括：

- 登录页 smoke
- 工作区壳层 smoke
- 工作空间选择器 smoke
- 服务树创建目录 smoke
- Mini Workstation 打开 / 输入 smoke
- `PullFromHubDialog` 初始 Hub 链接注入单测

也就是说，当前最适合你们继续发力的，不是再补更多基础设施，而是开始把：

- 文档详情
- 会话链路
- Form 提交
- Table 搜索 / CRUD
- 权限入口
- Hub 发布

这些真实业务链路一个个补起来。

## 一句话建议

把页面自动化优先用在：

- `AI 生成后的验收`
- `工作区主链路回归`
- `服务树和工作台联动`
- `动态 Form/Table 页面`
- `Hub 和权限这种平台级能力`

这样最能体现这套能力的价值，也最能直接减少你们日常开发排障成本。
