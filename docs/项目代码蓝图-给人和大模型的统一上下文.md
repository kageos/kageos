# AI-Agent-OS 项目代码蓝图（给人和大模型的统一上下文）

> 文档目标：用一份文档解释这个仓库“现在实际上是什么、为什么这么设计、核心代码怎么串起来、未来应该怎么扩”。
> 适用对象：新加入项目的人、需要快速建立上下文的大模型、要做二次开发或架构讨论的开发者。
> 判定原则：**如果本文与旧文档冲突，以当前仓库代码为准**。

## 1. 一句话定义

AI-Agent-OS 不是一个单点 AI 功能，也不是一个普通的低代码平台。  
它更接近一个 **“AI 可理解、可生成、可运行、可治理的企业应用操作系统”**：

- **人** 用自然语言描述需求。
- **Agent** 在工作台里读代码、读文档、写代码、编译、执行工具。
- **平台** 负责统一的目录组织、函数元数据、动态渲染、权限、运行时、存储、日志和部署。
- **业务代码** 只需要遵循 SDK 契约，平台就能把它变成可执行、可展示、可被 AI 调用的系统能力。

---

## 2. 这个项目的价值观与世界观

这套系统背后的价值观，不是“让 AI 帮人多写一点代码”，而是“让软件系统从一堆黑盒重新变成平台内的标准件”。

### 2.1 核心价值观

1. **学习成本必须低于开发成本**
   - 平台希望用户学会一个系统之后，看到另一个系统也能立即上手。
   - 因此必须统一 UI、交互、权限、调用方式、组织方式。

2. **用减法做平台，而不是用加法做功能拼盘**
   - 平台没有无限扩张“页面类型”，而是收敛成 `Form / Table / Chart` 三类函数形态。
   - 再用 `Docs / Board / ServiceTree` 补足内容节点和组织节点。

3. **所有能力都要可被 AI 理解**
   - 业务函数不是黑盒页面，而是带有 request/response schema、template_type、callback、full_code_path 的“可解释对象”。
   - Agent 可以把现有系统当工具调用，而不是每次都从零生成。

4. **平台能力优先于业务能力**
   - 权限、审批、日志、评论、定时任务、存储、运行时隔离，应由平台提供。
   - 业务代码应尽量只写业务字段和业务逻辑，不重复造平台轮子。

### 2.2 世界观

从代码能看出的世界观是：

- **一个工作空间就是一个应用容器边界**。
- **一个目录就是一个能力边界**。
- **一个函数就是一个最小可编排单元**。
- **一个 `full_code_path` 就是平台里的统一身份标识**。
- **一个 Widget schema 就是前后端共享的协议层**。
- **一个 Agent 会话就是围绕当前目录进行开发和执行的工作上下文**。

这也是为什么项目反复强调“服务树”“目录”“函数”“工作台”，而不是单纯强调“页面”“表单”“Prompt”。

## 3. 仓库的真实构成

这个仓库是一个 **多服务单仓（monorepo）**，不是单后端仓，也不是单前端仓。

### 3.1 主要目录

| 目录 | 作用 |
|------|------|
| `core/` | 平台核心后端服务：网关、应用元数据、运行时、Agent、HR、存储、控制服务 |
| `sdk/agent-app/` | 用户应用/生成应用的 Go SDK，是业务代码的标准契约层 |
| `web/` | Vue 3 前端，负责工作空间、服务树、动态渲染、工作台 UI |
| `pkg/` | 平台通用基础库：配置、NATS、LLM、权限、中间件、HTTP/内部 API 调用等 |
| `dto/` | 跨服务 DTO |
| `enterprise/` + `enterprise_impl/` | 企业特性抽象与实现，受 License 控制 |
| `deploy/` | 开发、嵌入式部署、Podman、生产部署脚本与配置 |
| `blueprint/` | 项目蓝图和对外/对模型文档入口 |
| `docs/`、`note/` | 设计分析、临时方案、技术讨论沉淀 |

### 3.2 需要特别注意的现实情况

1. **仓库存在多代架构并存**
   - 前端已经有新的分层架构：`web/src/architecture/{domain,application,infrastructure,presentation}`。
   - 同时仍保留较多 `web/src/core`、`web/src/components`、`web/src/views` 的历史代码。

2. **文档不少，但并不都代表当前真相**
   - 有些 blueprint 是方案稿，有些是阶段性总结。
   - 真正的现状必须回到 `core/`、`sdk/agent-app/`、`web/src/architecture/` 看代码。

3. **Hub 相关代码与说明存在“生态层”和“当前成熟度”差异**
   - 仓库里保留了 `enterprise_impl/hub/` 以及前端 Hub 集成配置。
   - 但 `enterprise_impl/hub/README.md` 仍明确把 Hub 定义为独立项目/闭源生态层。
   - 结论：**Hub 是平台蓝图的重要组成部分，但不应把它与核心 OS 主链路视为同一成熟度。**

## 4. 平台最重要的抽象

理解这几个抽象，等于理解了整个项目。

| 抽象 | 代码载体 | 作用 |
|------|----------|------|
| App / Workspace | `core/app-server/model/app.go`、`core/app-runtime/model/app.go` | 一个用户工作空间，也是一个生成应用、容器运行和版本管理的单位 |
| Service Tree | `core/app-server/model/service_tree.go` | 平台统一目录树，组织 package/function/docs/board |
| Function | `core/app-server/model/function.go` + SDK 注册信息 | 平台里的可执行单元 |
| Template Type | `sdk/agent-app/app/render_template.go` | 函数的执行与渲染形态：`form` / `table` / `chart` |
| Full Code Path | `service_tree.full_code_path` | 平台统一身份标识，串联权限、路由、Agent 上下文、文件存储 |
| Field Schema | `sdk/agent-app/widget/field.go` | 后端通过反射和 tag 生成的字段协议 |
| Field Value | `web/src/core/types/field.ts` | 前端统一字段值：`raw + display + meta` |

### 4.1 Service Tree 节点类型

当前代码中，服务树节点类型在 [`core/app-server/model/service_tree.go`](../core/app-server/model/service_tree.go) 里明确是：

- `package`
- `function`
- `docs`
- `board`

这意味着平台不是只有“函数”，还有可被平台管理和展示的文档节点、讨论区节点。

### 4.2 三种函数模板

模板类型定义在 [`sdk/agent-app/app/render_template.go`](../sdk/agent-app/app/render_template.go)：

- `form`
- `table`
- `chart`

这不是纯前端概念，而是贯穿：

- SDK 注册
- 元数据生成
- app-server 标准 API
- 权限中间件
- 前端渲染视图
- Agent 工具调用

### 4.3 `full_code_path` 是平台主键

从代码实际使用看，`full_code_path` 是平台里最重要的统一主键之一：

- 服务树定位靠它
- 权限靠它
- 标准 API 路由靠它
- 文档定位靠它
- Agent 工作台上下文靠它
- 文件存储 router 也围绕它组织

如果要改这个概念，几乎等于动整个平台的骨架。

## 5. 平台运行拓扑

### 5.1 核心服务

统一启动入口在 [`core/cmd/main/main.go`](../core/cmd/main/main.go)。  
当前一个“完整 OS 后端”由这些服务组成：

1. `control-service`
2. `app-runtime`
3. `app-storage`
4. `agent-server`
5. `hr-server`
6. `app-server`
7. `api-gateway`

### 5.2 它们各自干什么

| 服务 | 主要职责 |
|------|----------|
| `api-gateway` | 统一入口、按 path 代理、透传 token/trace/header |
| `app-server` | 工作空间、服务树、函数元数据、文档、讨论区、标准执行 API、权限/日志/任务等平台元数据能力 |
| `app-runtime` | 编译、版本管理、Podman 容器、NATS 调度、用户应用进程生命周期 |
| `agent-server` | 工作台会话、SSE 流、LLM 配置、工具注册、工具循环 |
| `hr-server` | 登录、注册、用户、部门 |
| `app-storage` | MinIO 对象存储、预签名上传下载 |
| `control-service` | License / 控制层 |

### 5.3 一句话理解服务分工

- `app-server` 不跑业务代码，它管“平台元数据与调用入口”。
- `app-runtime` 不管 UI，它管“用户应用如何编译、启动、升级、隔离”。
- `agent-server` 不直接拥有业务元数据，它围绕工作台调用工具、读写上下文。
- 真正的业务逻辑最终运行在 **SDK app 进程** 里。

## 6. 三条最关键的闭环

### 6.1 闭环一：SDK 注册 -> 元数据同步 -> 服务树可见

这是“生成一段 Go 代码，平台就能认识它”的关键链路。

1. 用户应用用 `sdk/agent-app/app.PackageContext` 注册路由。
2. SDK 在更新/启动阶段执行 [`sdk/agent-app/app/on_app_update.go`](../sdk/agent-app/app/on_app_update.go)。
3. SDK 通过反射把 `Request / Response / TemplateType / Callback / CreateTables` 组装成 `ApiInfo`。
4. `app-server` 的 [`AppService.processAPIDiff`](../core/app-server/service/app_service.go) 把 diff 写入：
   - `function`
   - `service_tree`
5. 前端拉取服务树后，这个函数就成为平台里的一级能力。

这说明平台不是扫描源码目录直接展示，而是通过 **SDK 注册结果 + 同步过程** 建立元数据索引。

### 6.2 闭环二：前端标准 API -> app-server -> NATS -> SDK app

这是实际业务执行链。

1. 前端调用 `table/form/chart` 标准 API。
2. `app-server` 在 [`core/app-server/api/v1/standard_api.go`](../core/app-server/api/v1/standard_api.go) 里把 `full-code-path` 解析成 `user/app/router`。
3. `AppService.RequestApp()` 根据应用当前版本，把请求发给 `app-runtime` 管控下的 SDK app。
4. `pkg/appcall.Client` 通过 NATS subject `function_server.app_runtime.{user}.{app}.{version}` 发消息。
5. SDK app 在 [`sdk/agent-app/app/handle.go`](../sdk/agent-app/app/handle.go) 中执行对应 handler。
6. 结果再通过 `app.function_server.*.*.*` 回到 `app-server`，最终响应前端。

结论：平台标准 API 只是统一门面，真正执行业务的是 **应用容器内的 SDK app**。

### 6.3 闭环三：工作台对话 -> 工具循环 -> 改代码/调平台

这是 AI 原生平台和普通平台最大的差异之一。

1. 前端调用 `/agent/api/v1/workspace/chat/stream`。
2. `WorkspaceChatService` 负责：
   - 会话创建
   - 消息持久化
   - 加载目录上下文
   - 选 LLM
   - 启动工具循环
3. `ToolRegistry` 暴露一批内置工具，例如：
   - `read_go_file`
   - `read_doc`
   - `read_dir`
   - `write_go_file`
   - `write_doc`
   - `build_workspace`
   - `run_table_search`
   - `run_form_submit`
   - `run_chart_query`
   - `search_hub_directory`
4. Agent 在一个目录上下文里，既能开发，也能执行。

这就是平台“开发态”和“运行态”统一在工作台里的真实代码基础。

## 7. 后端代码结构的真实蓝图

### 7.1 API Gateway：只做代理，不承载业务

关键文件：

- [`core/api-gateway/server/router.go`](../core/api-gateway/server/router.go)

特征：

- 根据配置注册具体路由和兜底路由
- 负责透传 `trace-id`、token、`X-Forwarded-Host`
- 自己不做业务判断，只做入口层统一

这个设计是对的，因为它把“平台边界”和“业务能力”分开了。

### 7.2 App Server：平台元数据内核

关键文件：

- [`core/app-server/server/router.go`](../core/app-server/server/router.go)
- [`core/app-server/service/service_tree_service.go`](../core/app-server/service/service_tree_service.go)
- [`core/app-server/service/app_service.go`](../core/app-server/service/app_service.go)

它是整个 OS 的“元数据中枢”，负责：

- App 管理
- Service Tree 管理
- Function 元数据管理
- Docs / Board
- 标准函数执行 API
- 权限、日志、定时任务等平台能力入口

要点：

- 路由前缀是 `/workspace/api/v1/...`
- `service_tree` 是目录与节点管理主线
- `table/form/chart` 是标准执行接口
- `run/*` 是更通用的调用入口

### 7.3 App Runtime：真正的用户应用运行时

关键文件：

- [`core/app-runtime/server/server.go`](../core/app-runtime/server/server.go)
- [`core/app-runtime/server/nats_router.go`](../core/app-runtime/server/nats_router.go)
- [`core/app-runtime/service/app_manage_service.go`](../core/app-runtime/service/app_manage_service.go)
- [`core/app-runtime/service/container_service.go`](../core/app-runtime/service/container_service.go)

它负责：

- 初始化本地 SQLite 元数据
- 连接 NATS
- 连接 Podman
- 管理应用编译、版本、启动、关闭、清理
- 订阅 app-server 发来的 runtime 请求

关键事实：

- 用户应用不是直接在 `app-server` 里执行，而是由 `app-runtime` 管理容器和版本。
- 容器名采用 `{user}-{app}-{version}`。
- 运行时带有 QPS 跟踪、旧版本清理、启动等待器、NATS 状态通知。
- 代码中已经开始考虑 LSM（AppArmor/SELinux）和运行时安全约束。

### 7.4 Agent Server：工作台与工具编排中心

关键文件：

- [`core/agent-server/server/router.go`](../core/agent-server/server/router.go)
- [`core/agent-server/service/workspace_chat_service.go`](../core/agent-server/service/workspace_chat_service.go)
- [`core/agent-server/service/tool_registry.go`](../core/agent-server/service/tool_registry.go)
- [`pkg/llms/`](../pkg/llms)

它不是“聊天接口集合”，而是一个带状态的工作台编排层。

核心能力：

- `agent_chat_sessions` / `agent_chat_messages`
- 工具列表与执行
- SSE 流式输出
- 多 LLM 提供商适配
- 会话状态：`active / generating / done / cancelled`

### 7.5 HR / Storage / Control 是平台底座，不是外挂

- `hr-server`：用户、登录、部门，是用户组件与权限系统的基础。
- `app-storage`：文件上传/下载统一入口，按路径维度多租户隔离。
- `control-service` + `pkg/license`：社区版/企业版的功能切换基础设施。

也就是说，这个平台不是“生成页面 + 调大模型”这么简单，它其实已经具备标准企业平台所需的底层服务分层。

## 8. SDK 是整个平台最关键的契约层

如果说 `app-server` 是元数据内核，那么 `sdk/agent-app` 就是“业务代码如何接入平台”的法律文本。

### 8.1 注册方式

关键文件：

- [`sdk/agent-app/app/register.go`](../sdk/agent-app/app/register.go)
- [`sdk/agent-app/app/render_template.go`](../sdk/agent-app/app/render_template.go)

业务代码通过：

- `PackageContext.GET(...)`
- `PackageContext.POST(...)`
- `PackageContext.PUT(...)`
- `PackageContext.DELETE(...)`

注册函数。

注册时写入的是：

- 路由
- method
- handler
- template
- package path

### 8.2 模板为什么很薄

`FormTemplate`、`TableTemplate`、`ChartTemplate` 的代码都很薄。  
真正重要的不是模板 struct 本身，而是它们共同依赖的 `BaseConfig`：

- `Code`
- `Name`
- `Desc`
- `Tags`
- `CreateTables`
- `Request`
- `Response`
- `OnSelectFuzzyMap`

这说明平台设计理念是：

> 模板是一个轻量类型标记，真正的协议在 `BaseConfig + schema + callback`。

### 8.3 为什么 struct tag 是关键

后端字段 schema 不是手写 JSON，而是从 Go struct tag 反射出来的。

关键文件：

- [`sdk/agent-app/widget/decode.go`](../sdk/agent-app/widget/decode.go)
- [`sdk/agent-app/widget/field.go`](../sdk/agent-app/widget/field.go)
- [`sdk/agent-app/widget/widget.go`](../sdk/agent-app/widget/widget.go)

参与协议生成的 tag 主要有：

- `json`
- `widget`
- `validate`
- `search`
- `data`
- `permission`
- `callback`

`DecodeForm()` / `DecodeTable()` 会把这些 tag 转成前端字段协议。

### 8.4 这条链路意味着什么

这意味着这个平台的业务代码其实不是“写页面”，而是：

1. 写 Go struct
2. 标字段 tag
3. 注册模板
4. 平台自动生成：
   - schema
   - 前端控件
   - 标准 API 能力
   - Agent 可读的函数元数据

这正是“描述生成应用”能规模化成立的前提。

## 9. Widget 系统是前后端统一协议的核心

用户提到的 widget，确实是这个项目最值得深挖的地方之一。

### 9.1 后端如何定义 widget

后端定义位置：

- [`sdk/agent-app/widget/widget.go`](../sdk/agent-app/widget/widget.go)
- [`sdk/agent-app/widget/*.go`](../sdk/agent-app/widget)

当前核心 widget 类型包括：

- `input`
- `text`
- `text_area`
- `select`
- `multiselect`
- `switch`
- `timestamp`
- `user` / `users`
- `department` / `departments`
- `number`
- `float`
- `files`
- `checkbox`
- `radio`
- `slider`
- `rate`
- `color`
- `richtext`
- `table`
- `form`
- `link`
- `progress`

### 9.2 后端 widget 是怎么从字段里解析出来的

关键流程：

1. `ParseModelWithType()` 读取结构体字段和 tags。
2. `parseTagValue()` 把 `widget:"name:标题;type:input"` 解析成 key-value。
3. `ConvertTagsToField()` 生成统一的 `Field`。
4. `inferDataType()` 根据 Go 类型推断 `string/int/float/[]struct/...`。
5. 如果字段是 `widget.type=table/form`，就递归解析 `children`。

结论：

- **widget type 决定“怎么渲染”**
- **Go 类型决定“数据是什么”**
- **两者不是一回事**

这是一个很正确的拆分。

### 9.3 前端如何接住这套协议

前端核心类型：

- [`web/src/core/types/field.ts`](../web/src/core/types/field.ts)
- [`web/src/core/types/widget.ts`](../web/src/core/types/widget.ts)

前端把后端的 `Field` 接成：

- `FieldConfig`
- `FieldValue`

其中 `FieldValue` 是统一值模型：

- `raw`：提交值
- `display`：显示值
- `meta`：附加元数据

这是前端动态渲染能成立的关键，否则每个组件都得各玩各的值结构。

### 9.4 前端 widget 渲染链

核心文件：

- [`web/src/architecture/infrastructure/widgetRegistry/index.ts`](../web/src/architecture/infrastructure/widgetRegistry/index.ts)
- [`web/src/architecture/infrastructure/widgetRegistry/WidgetComponentFactory.ts`](../web/src/architecture/infrastructure/widgetRegistry/WidgetComponentFactory.ts)
- [`web/src/architecture/presentation/widgets/WidgetComponent.vue`](../web/src/architecture/presentation/widgets/WidgetComponent.vue)

流程是：

1. 启动时注册基础组件和容器组件。
2. 根据 `field.widget.type` 从工厂里取 Vue 组件。
3. `WidgetComponent.vue` 作为统一包装器，向下传递：
   - `field`
   - `value`
   - `mode`
   - `fieldPath`
   - `formRenderer`
4. 具体组件按模式渲染。

### 9.5 Widget 的多模式设计是这个系统的亮点

前端模式定义在 [`web/src/core/types/field.ts`](../web/src/core/types/field.ts)：

- `edit`
- `response`
- `table-cell`
- `detail`
- `search`

这意味着一个 widget 不是只服务于“表单编辑”，而是服务于：

- 输入
- 结果展示
- 表格单元格展示
- 详情页展示
- 搜索过滤展示

这正是统一 UI 学习成本的关键。

### 9.6 容器 widget：`form` 和 `table`

容器组件位置：

- [`web/src/architecture/presentation/widgets/FormWidget.vue`](../web/src/architecture/presentation/widgets/FormWidget.vue)
- [`web/src/architecture/presentation/widgets/TableWidget.vue`](../web/src/architecture/presentation/widgets/TableWidget.vue)

它们不是普通组件，而是“嵌套 schema 的递归渲染器”。

尤其 `TableWidget` 明确处理了：

- 编辑态与展示态
- 嵌套 `form/table` 的抽屉化展示
- 行内编辑
- 导入导出
- 明细抽屉

这意味着平台的复杂表单/主从表能力，并不是临时拼出来的，而是组件系统内建的一部分。

### 9.7 Widget 相关的三个关键扩展点

#### 1. 初始化器

- [`web/src/architecture/presentation/widgets/initializers/WidgetInitializerRegistry.ts`](../web/src/architecture/presentation/widgets/initializers/WidgetInitializerRegistry.ts)

用于处理 select/multiselect/form/table 等需要特殊初始值装配的组件。

#### 2. 提取器

- [`web/src/core/stores-v2/extractors/FieldExtractorRegistry.ts`](../web/src/core/stores-v2/extractors/FieldExtractorRegistry.ts)

用于在提交前把不同 widget 的 `FieldValue` 转回后端想要的 raw 结构。

#### 3. 插件注册

- [`web/src/architecture/infrastructure/plugins/pluginManager.ts`](../web/src/architecture/infrastructure/plugins/pluginManager.ts)
- [`web/src/architecture/infrastructure/plugins/WidgetPlugin.ts`](../web/src/architecture/infrastructure/plugins/WidgetPlugin.ts)

这给未来做自定义 widget 留出了正式扩展点。

### 9.8 如何扩展一个新 widget

如果未来要新增组件，建议按这个顺序做：

1. 后端 SDK 增加 widget 类型常量和配置解析。
2. 确保 `DecodeForm/DecodeTable` 能输出正确 schema。
3. 前端在 `WidgetType` 常量中对齐类型名。
4. 实现对应 Vue 组件。
5. 注册到 `widgetComponentFactory`。
6. 如有特殊初始化/提取逻辑，补 initializer / extractor。
7. 检查至少 5 个模式：
   - `edit`
   - `response`
   - `table-cell`
   - `detail`
   - `search`

这是最稳妥的端到端扩展方式。

## 10. 前端的新架构蓝图

前端现在很明显在朝分层架构演进。

目录位于：

- [`web/src/architecture/`](../web/src/architecture)

分层是：

- `domain`
- `application`
- `infrastructure`
- `presentation`

### 10.1 当前分层的真实意义

不是纯粹为了“好看”，而是在把以下职责拆开：

- **domain**：业务概念和接口
- **application**：工作流编排
- **infrastructure**：API client、state manager、widget registry、route manager
- **presentation**：Vue 组件和视图

例如工作空间这条链：

- `WorkspaceApplicationService`
- `WorkspaceDomainService`
- `WorkspaceStateManager`
- `WorkspaceView.vue`

说明前端已经开始把“页面逻辑”和“业务编排”拆开。

### 10.2 但也要看到当前技术现实

前端并不是已经完全重构完：

- 新旧代码并存
- 状态与组件职责还在迁移中
- 文档里存在 `widgets-v2` 等历史称呼，但当前主路径已经是 `architecture/presentation/widgets`

因此后续大模型或开发者改前端时，要优先判断：

1. 这是新架构路径里的代码吗？
2. 这个需求应该补在 `architecture/` 还是旧目录？
3. 是“继续迁移”还是“就地修复”？

## 11. Agent / 工作台是平台第二条主心骨

如果说 SDK + Service Tree 是“平台如何承载业务”，  
那么 Agent / 工作台就是“平台如何承载 AI”。

### 11.1 工作台不是问答框，而是目录级开发环境

当前工作台绑定的是：

- `tree_id`
- `full_code_path`
- 当前目录上下文
- 当前会话历史

这意味着 Agent 不是在“空上下文聊天”，而是在“当前目录里做事”。

### 11.2 工具系统体现了项目蓝图

`ToolRegistry` 已经暴露出来的工具非常能说明方向：

- 读代码
- 读文档
- 看目录
- 写文档
- 写代码
- search-replace
- build
- 查表 / 提表单 / 查图表
- 搜 Hub / 发布 Hub
- 定时任务
- 官方 Python 执行

换句话说，这个平台的目标不是“AI 帮你写一小段代码”，而是：

> 让 AI 在平台里完成理解、开发、验证、执行、发布这一整条链路。

### 11.3 LLM 适配层是平台化的，不绑死单模型

`pkg/llms` 提供统一接口，当前支持多家 provider：

- DeepSeek
- 千问 / 千问3-Coder
- 豆包
- Kimi
- Claude
- Gemini
- GLM
- MiniMax
- 小米

这说明平台在技术选择上是开放的，Agent 层并不依赖单一模型厂商。

## 13. 从当前代码能看出的未来蓝图

以下蓝图不是空想，而是从当前代码结构推断出来的。

### 13.1 平台会继续强化“目录级 Agent”

工作台已经不是纯写代码模式，而是逐步在变成：

- 目录级开发环境
- 目录级执行环境
- 目录级知识入口
- 目录级自动化入口

未来它很自然会走向：

- 更强的 PRD 生成
- 更强的工具编排
- 更完整的开发-测试-部署闭环

### 13.2 平台会继续强化“统一协议而非页面拼装”

从 SDK、Field schema、Widget、标准 API 的实现看，平台未来最应该继续强化的是：

- schema 的稳定性
- callback 的约束
- widget 的扩展规范
- full_code_path 的一致性

而不是盲目增加新的“页面类型”。

### 13.3 平台会继续强化“社区核心 + 企业增强”

`pkg/license`、`enterprise/`、`enterprise_impl/` 很明确地表明了路线：

- 核心 OS 平台保持可运行
- 企业能力通过 feature gate 增强
- Hub 作为生态层延伸平台价值

### 13.4 不建议轻易扩展“第四种函数模板”

从当前代码成熟度看，`form/table/chart` 已经深度贯穿全链路。  
如果要新增第四种模板类型，会牵一发动全身：

- SDK
- 元数据 diff
- app-server 标准 API
- 权限点
- 前端视图
- Widget 和展示层
- Agent 工具与 Prompt

所以最优策略通常不是增加函数模板，而是在现有三类模板内继续增强能力。

## 14. 当前架构的优势与技术债

### 14.1 优势

1. **平台主线非常清晰**
   - Service Tree
   - SDK
   - Widget schema
   - app-runtime
   - workspace agent

2. **运行态与开发态打通了**
   - 这不是单纯的代码生成器，而是带运行时、元数据、权限和工作台的完整平台。

3. **Widget 协议设计是项目核心护城河之一**
   - 后端 tag -> schema -> 前端渲染 -> 值提取 -> 校验 的链路很完整。

4. **服务边界总体合理**
   - 网关、元数据、运行时、Agent、HR、Storage、License 的职责分层基本清楚。

### 14.2 技术债

1. **文档碎片化**
   - 方案稿、旧说明、现行实现混在一起，容易误导大模型和新人。

2. **前端新旧架构并存**
   - 演进方向清晰，但迁移尚未完全结束。

3. **工作台工具注册表较大**
   - `ToolRegistry` 已经承担很多能力，未来需要更清晰的分组与治理。

4. **Hub 生态说明与主仓真实边界需要更明确**
   - 否则容易让读代码的人误判它的当前成熟度与交付边界。

5. **很多“平台级规范”仍靠文档而不是代码约束**
   - 例如生成规范、某些目录约定、部分工作台行为约束。
