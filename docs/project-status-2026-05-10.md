# AI-Agent-OS 项目现状简报

> 整理时间：2026-05-10  
> 依据：根 README、前端/部署/核心服务 README、当前仓库目录与工作区状态。  
> 结论先行：项目已经过了概念验证阶段，核心主链路和平台骨架已经形成；当前默认进入产品聚焦模式，优先打深 AI 工作台创建、修改、构建、运行企业轻应用的主链路，并先隐藏还在演进的横切能力入口。

## 1. 总体判断

AI-Agent-OS 当前处在 **MVP 主链路已打通，平台能力正在产品化补齐** 的阶段。

它不是一个只有蓝图的早期项目：仓库里已经有多服务后端、前端动态渲染、SDK 协议、运行时、Agent 工作台、部署入口、备份恢复、企业权限/日志、Hub 等实际代码。

但它也还不是一个完全成熟的商用平台：README 里明确把很多能力标为“已形成骨架/正在演进/规划中”。尤其是流程审批、消息通知、工作流编排、协作层、Hub 资产市场化、前端架构统一，还需要继续推进。

2026-05-13 的产品决策是：短期不删除权限、组织、Hub、消息、操作日志、定时任务等代码，但默认通过产品聚焦模式隐藏这些入口，把用户心智收敛到“AI 生成企业轻应用的工作台”。恢复高级能力前，需要先证明 Form/Table/Chart 创建、修改、构建、运行、出错修复这条链路足够稳定。

## 2. 已经成型的主链路

### 2.1 平台核心抽象已经清楚

当前项目的核心抽象已经比较稳定：

- `ServiceTree`：统一组织目录、函数、文档、讨论区等资源。
- `Function`：平台内可发现、可调用、可治理的能力单元。
- `Form / Table / Chart / Docs / Board`：主要资源形态已经被收敛到标准模板。
- `full_code_path`：资源定位、权限、调用、工作台上下文的统一身份。
- SDK schema：通过 Go 结构体标签生成前端可渲染、Agent 可理解的字段协议。

这说明项目已经不是在讨论“要不要这样做”，而是在围绕这些抽象继续补实现和体验。

### 2.2 后端多服务骨架已经存在

根 README 里列出的主服务已经在 `core/` 下形成实际目录：

- `api-gateway`：统一入口和路由分发。
- `app-server`：平台元数据、服务树、标准 API 门面。
- `app-runtime`：应用构建、版本、容器运行、NATS 调用。
- `agent-server`：工作台会话、SSE、工具循环、代码读写与构建。
- `app-storage`：对象存储、上传下载、文件引用。
- `hr-server`：用户、部门、认证等身份能力。
- `message-server`：消息模型、消费、收件箱接口已有代码。
- `control-service`：License 管理。
- `backup-service`：备份与恢复控制面。
- `timer-scheduler`：定时任务服务已经独立。

这部分的状态更接近“骨架可运行”，不是纯文档规划。

### 2.3 业务能力注册和执行闭环已经打通

README 描述的三条关键闭环已经是当前项目主线：

- SDK 注册业务函数，生成模板、字段和回调元数据。
- app-server 把函数同步进 `function` 和 `service_tree`。
- 前端通过标准 API 调用 Form/Table/Chart。
- app-server 解析 `full_code_path` 后，经 NATS 转给 app-runtime。
- app-runtime 再转发给 SDK App 容器执行。
- 工作台可以读代码、写代码、构建、执行函数、搜索资源和发布 Hub。

这代表“从代码到平台可见能力，再到运行时执行”的闭环已经成立。

### 2.4 前端主业务已经迁入新架构，但还在混合态

`web/README.md` 明确写了真实状态：

- 主页面入口已经迁到 `web/src/architecture/`。
- 当前采用 `presentation / application / domain / infrastructure` 分层。
- `web/src/core`、`web/src/shared`、`web/src/utils` 仍然承担线上主链路底座。
- `web/src/views` 基本只保留错误页等遗留页面。

所以前端不是没有架构，但还处于“新架构承接主页面，公共底座混合复用”的过渡阶段。

### 2.5 部署和恢复入口已经收敛

`deploy/README.md` 给出的部署主线比较清楚：

- 本地开发：`deploy/dev`
- 单机生产：`deploy/prod`
- 共享资源：`deploy/base`
- 可选安全模块：`deploy/security`

当前成熟主线只有开发环境和单机生产环境。多机分布式还不是官方成熟入口。

`backup-service` 已经支持 namespace、MySQL、MinIO 的快照、恢复、删除和恢复前保护快照，说明运维恢复能力也已经开始补齐。

## 3. 正在推进或需要收口的部分

### 3.1 前端架构收敛

前端已经有新分层，但旧底座还在主链路里。下一阶段需要继续减少 `architecture` 与 `core/shared/utils` 之间的边界含混，避免后续功能分散。

### 3.2 权限、日志、License 等企业能力产品化

`enterprise_impl/permission` 和 `enterprise_impl/operatelog` 已经有 repository/service/test，`control-service` 也已承担 License 管理。

但 README 的成熟度判断仍然把基础权限归为“正在演进”。说明底层能力已经有了，下一步重点应是产品边界、管理界面、审计查询和策略表达。

### 3.3 流程审批仍主要是规划

`core/flow-server` 当前只有 README，定位很清楚：做平台级“先审批，后执行”的横切控制面。

但从目录看，它还没有形成与其他服务类似的代码结构。因此流程审批应判断为“方向明确，但实现尚未进入主链路”。

### 3.4 消息通知和协作层刚起步

`message-server` 已经有模型、API、消费服务和测试，但根 README 仍把“消息通知中心”“评论/点赞/收藏/订阅”列为规划中。

这说明项目正在补消息底座，但还没形成完整的产品化通知中心和资源协作层。

### 3.5 Hub 已经不是纯概念，但还需要从目录市场升级

根 README 提到 Hub 已有发布、更新、列表、详情、版本、star、copy 等能力。

`enterprise_impl/hub/backend/README.md` 也列出了实际路由，包括目录发布、导出、版本、收藏、公钥发布等。

当前 Hub 可以判断为“目录市场主链路已具备基础”，但距离“工作流市场/行业模板市场/资产市场”还有明显距离。

### 3.6 当前工作区还有未提交开发改动

当前分支是 `main`，工作区存在一批未提交改动，集中在：

- service tree / runtime workspace bridge
- capability bundle 导出相关 DTO、服务和前端弹窗
- service config、storage、netprobe
- SDK app 和若干测试

这说明当前本地代码正在推进服务树能力包或发布导出相关能力。整理项目现状时应把这部分视为“正在开发中”，不要误认为已经稳定发布。

## 4. 主要风险

### 4.1 文档和代码有漂移

根 README 已经提醒“文档成熟度不完全等于代码成熟度”。一些子 README 仍有“待实现”的旧描述，而代码可能已经推进；也有一些蓝图写得很完整，但代码还没开始落地。

当前最需要的是少数权威文档，而不是继续新增大量互相重叠的说明。

### 4.2 产品边界容易发散

README 对风险判断很准确：项目最危险的地方不是做不出来，而是边界失焦。

当前主轴应继续收敛在：

- `Form / Table / Chart`
- `ServiceTree`
- SDK 协议
- Agent 工作台
- 工作流与模板复用
- 企业治理能力

暂时不适合扩成完全自由前端、复杂实时协同、大而全 OA 或万能 SaaS 平台。

### 4.3 “骨架可用”和“生产成熟”还要区分

很多能力已经有主链路，但仍需要补：

- 稳定回归测试
- 管理端体验
- 权限边界和审计报表
- 异常恢复路径
- 文档版本统一
- 对外演示路径和部署脚本校验

## 5. 建议的下一阶段重点

1. **先稳定一条完整演示链路**  
   从创建目录、生成 Form/Table/Chart、构建发布、前端执行、文件上传、Hub 发布，形成可稳定演示的闭环。

2. **完成当前 service tree / capability bundle 方向的收口**  
   当前工作区改动集中在这条线上，建议先完成测试和文档，再进入下一块大功能。

3. **把前端迁移状态收敛成明确规则**  
   明确新页面、新 API、新共享组件分别应该放在哪里，减少 `architecture`、`core`、`shared`、`utils` 的交叉。

4. **流程审批先做最小可用版本**  
   不要一开始做完整 BPM。优先覆盖 `table.update`、`table.delete`、`form.submit` 这类高风险动作。

5. **消息通知先服务审批和构建结果**  
   通知中心第一阶段只需要支撑审批待办、构建失败、任务完成等关键事件，不要过早扩展成完整协作产品。

6. **维护一份权威状态表**  
   建议后续只维护根 README 和这类状态简报，减少分散 README 造成的信息冲突。

## 6. 一句话结论

AI-Agent-OS 当前已经完成“AI 原生企业应用操作系统”的核心技术骨架，最难的服务树、SDK、运行时、动态 UI、工作台工具链已经打通；接下来的项目进度重点不应再是证明方向，而是把现有骨架打磨成稳定、可演示、可部署、可治理的产品主线。
