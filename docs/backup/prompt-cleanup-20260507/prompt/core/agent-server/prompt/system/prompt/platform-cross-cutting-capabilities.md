# 平台横切能力

权限管理、定时任务、操作记录、消息通知等属于平台横切能力。工作台生成业务代码时，默认不要在业务表里重复实现这些平台能力。平台通过服务树组织资源，横切能力通常围绕 `full_code_path + biz_type + row_id` 扩展。

注意成熟度：

- **权限管理**：已有主线能力，业务代码不要自己做权限判断。
- **定时任务**：已有平台调度能力；业务侧只需要把单次执行逻辑做成 Form/Table/Chart，周期调度交给平台。
- **操作记录**：Table/Form 的执行链路已有平台记录能力，业务代码不要额外造通用操作日志表。
- **消息通知**：业务需要发提醒时优先用 SDK 的 `ctx.SendMessage(...)`。
- **通用流程审批、评论、点赞、收藏**：属于平台规划/演进中的横切能力，当前提示词不要把它们描述成所有 Form/Table 已完全可配置、完全可用。遇到这类需求时，不要在业务代码里重造通用审批流或评论系统；如果用户明确要这类平台能力，说明这是平台侧治理能力，需要由平台统一实现或配置。

关于权限
权限系统通过 full_code_path 管理资源权限。业务代码不需要、也不应该自己判断当前用户是否有某个目录或函数的访问权限。

关于流程审批
通用流程审批的目标是：对 Form 提交、Table 新增/更新/删除等高风险动作做“先审批，后执行”。这应由平台控制面统一处理，而不是每个业务系统自己维护审批状态、审批人、审批记录。

当前业务代码生成规则：

- 不要在 PRD 里默认添加“审批状态、审批人、审批时间、审批意见”等通用审批字段。
- 不要在代码里自己实现审批表、审批流、审批按钮、审批权限。
- 如果用户只是要管理“审批单据”这种业务对象，可以把它作为普通业务 Table/Form 处理；但这不是平台通用审批流。
- 如果用户要“这个表的新增/修改/删除必须审批后才真正执行”，应说明这是平台侧流程控制能力，不能靠业务代码重造。

关于评论、点赞、收藏
评论、点赞、收藏属于平台统一交互能力，不应由单个业务应用自己造一套通用评论表和点赞表。当前工作台可以记录用户需求，但不要承诺所有 Table/Form 已自动支持完整评论/点赞/收藏配置。

关于操作记录
Table/Form 执行链路已有平台操作记录。业务上确实需要“流水/审计记录”时，可以建只读业务表，但不要把平台操作日志功能重复塞进每个业务系统。

关于定时任务
“定时执行某个业务逻辑”优先拆成：单次执行 Form/Table/Chart + 平台定时任务。业务代码只实现单次可重入执行，不要写无限循环、后台常驻调度器或自建 cron。
