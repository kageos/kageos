# Form/Table/Chart 组合架构

本文档用于让模型先理解 AgentOS 的业务组织方式，再选择具体 SDK 写法。AgentOS 不是让模型自由生成独立页面，而是让模型在服务树目录下创建一组可执行函数，前端再根据函数 schema 统一渲染。

## 总原则

复杂业务系统由目录和三类函数组合而成：

```text
业务系统 = 目录树 + Table 函数 + Form 函数 + Chart 函数
```

- 目录负责组织业务模块，不是一个手写前端页面。
- 函数负责承载具体能力，路由最后一段必须带 `.table`、`.form` 或 `.chart`。
- 前端根据 SDK 产出的 schema 渲染统一界面，业务代码只定义字段、数据、动作和规则。
- 不要创建独立 HTML/CSS/JS 页面，不要为单个业务系统重造通用 UI、权限、审批、日志、消息、上传等平台能力。

## 三类函数的前端形态

| 类型 | 前端渲染形态 | 适合承载 | 不适合承载 |
|---|---|---|---|
| Table | Element Plus `el-table` 风格的数据表格，通常带搜索区、分页、列展示、工具栏、新增/编辑/删除按钮、行操作和详情抽屉 | 长期保存的一批业务记录、后台管理、台账、流水、主数据 | 一次性文件转换、单次提交动作、纯图表统计 |
| Form | Element Plus `el-form` 风格的表单提交界面，按 Request 字段渲染输入控件，提交后展示 Response、文件、链接或提示 | 一次性动作、提交入口、文件处理、结算、导入、发送通知、流程触发 | 管理一批长期记录、分页列表、趋势图表 |
| Chart | 图表查询界面，按 Request 渲染筛选条件，结果用 ECharts 图表展示 | 趋势、占比、汇总、经营分析、看板指标 | CRUD 管理、一次性文件处理、把多张图塞进一个路由 |

模型在 PRD 中不能只写“用 Table/Form/Chart”，还要写清楚前端会怎么呈现：

- Table：用户会看到一个数据表格，可以搜索、分页、查看列，是否能新增/编辑/删除取决于 TableTemplate 是否配置对应回调。
- Form：用户会看到一个表单，填写字段并点击提交，后端处理一次动作并返回结果。
- Chart：用户会看到筛选条件和一张图表，图表来自后端聚合后的 chart 响应。

## 选择规则

1. 用户说“管理系统、后台、列表、台账、CRUD、记录、档案、客户、订单、库存、工单、招聘”等，默认以 Table 为核心。
2. 用户说“上传、转换、生成、提交、结算、发送、导入、处理一次、执行一次任务”等，优先 Form；简单状态修改或直接编辑记录优先放在 Table update 回调里。
3. 用户说“统计、趋势、占比、报表、看板、分析、汇总、图表”等，优先 Chart。
4. 用户说“做一个系统”且没有详细说明，先按主业务对象建一个核心 Table；只有明确存在一次性动作时加 Form，明确存在统计分析时加 Chart。
5. 多个业务对象通常拆成多个 Table，不要把所有字段塞进一个超大结构。
6. 一个 Chart 路由只返回一张图；多个指标或图表拆成多个 `.chart` 函数。
7. Form 的 Request/Response 是普通表单/结果结构，不要混入 `chart.LineChart`、`chart.PieChart` 等图表结构。

## 场景参考

创建或修改功能时，先按 4 个粗场景判断职责。创建主链路通常已经自动注入完整 SDK 主文档、widget 白名单和 build 校验文档，不必为了“任务包”再额外读取碎片文档；只有遇到专项问题时再按需查阅对应 SDK 参考。

| 场景 | 什么时候命中 | 可选参考 |
|---|---|---|
| 单 Form | 文件处理、转换生成、一次性提交、临时工具 | `/system/prompt/sdk/form-submit-basic` |
| 单 Table | 简单 CRUD、后台管理、台账、记录库 | `/system/prompt/sdk/table-crud-basic` |
| Table + Form | 长期记录管理 + 独立用户动作，例如提交评价、提交投票、快速跟进、导入历史 | `/system/prompt/sdk/combo-table-form` |
| Table + Form + Chart | 长期数据 + 动作 + 统计看板，例如收银系统、投票结果图、工单统计 | `/system/prompt/sdk/combo-table-form-chart` |

模型选择场景时只围绕上面 4 类判断；字段、widget、筛选字段、validate 以完整 SDK 主文档和 widget 白名单为准。

## 目录组织规则

目录按业务模块组织，函数按具体能力命名：

```text
/用户/应用/业务目录
  xxx_list.table       管理某类长期记录
  xxx_submit.form      执行一次业务动作
  xxx_statistics.chart 展示一个统计图表
```

常见命名：

- 管理列表：`customer_list.table`、`ticket_list.table`、`product_list.table`
- 提交动作：`evaluation_submit.form`、`cashier_checkout.form`、`vote_submit.form`
- 统计图表：`sales_trend.chart`、`category_sales.chart`、`ticket_status_chart.chart`

## 组合范式

### 投票系统

投票系统不是一个大页面，而是一组围绕投票主题、选项、投票动作和结果统计的函数。

- `vote_topic_list.table`：投票主题管理。前端渲染为 Element Plus 表格列表，管理员可以看到主题标题、说明、开始时间、结束时间、状态、是否匿名、是否多选等列；搜索区可按状态、时间、关键词过滤；配置新增/编辑/删除回调后，前端会显示对应按钮和表单。它承载“长期存在的投票主题记录”。
- `vote_option_list.table`：投票选项管理。前端也是表格列表，通常按主题筛选，展示选项名称、排序、票数、占比、是否启用等列；管理员在这里维护某个主题下的选项。它承载“长期存在的选项记录”，不负责用户投票动作。
- `vote_submit.form`：用户提交投票。前端渲染为表单，用户选择投票主题和选项后提交；后端校验投票时间、是否重复投票、多选规则，然后写入投票记录和明细。它是“一次提交动作”，所以是 Form，不是 Table。
- `vote_record_list.table`：可选，投票记录审计。前端渲染为只读或半只读表格，展示谁在什么时间给哪个主题投了哪些选项，通常不开放手工新增/编辑。
- `vote_result.chart`：投票结果图表。前端渲染为筛选条件 + ECharts 图表，按主题展示选项票数、占比、趋势等。若只需要展示普通结果字段或跳转链接，也可以用 `vote_result.form` 返回文本/表格化结果；若需要可视化，优先 Chart。

职责分配：

- Table 管主题、选项、记录这些长期数据。
- Form 执行“投一票”这个动作。
- Chart 展示投票结果的统计可视化。
- Table 列表里的 link 字段可以跳到投票表单或结果图表，例如在主题列表中放“参与投票”“查看结果”链接。

### 收银系统

收银系统由基础资料、收银动作、流水记录和经营统计组成。

- `product_list.table`：商品管理。前端是商品表格，展示商品名称、分类、售价、库存、条码、状态等列；支持搜索、分页、新增、编辑，是否允许删除按业务规则决定。它承载商品主数据。
- `member_list.table`：会员管理。前端是会员表格，展示会员姓名、手机号、等级、余额、积分、状态等列；支持查询和维护会员资料。它承载会员主数据。
- `cashier_checkout.form`：收银结算。前端是表单，可以包含商品明细子表、会员选择、优惠、支付方式、实收金额等输入；提交后后端用事务扣库存、更新会员余额/积分、生成支付流水。它是一次业务动作，所以必须是 Form。
- `payment_record_list.table`：支付流水。前端是表格，展示订单号、会员、金额、支付方式、支付时间、收银员等列；这类流水通常只读，不默认开放新增/编辑/删除。
- `sales_trend.chart`：销售趋势图。前端按时间范围筛选后展示折线图或柱状图。
- `category_sales.chart`：品类销售占比。前端展示饼图或柱状图。
- `member_consumption.chart`：会员消费分析。前端展示会员消费排行、复购趋势等。

职责分配：

- Table 管商品、会员、流水这些长期记录。
- Form 承担收银结算动作，并负责事务化写多张表。
- Chart 基于流水和明细做经营分析。
- 不要把收银结算写成 Table 的新增记录；Table 新增只适合直接维护单条记录，不适合复杂结算事务。

### 评价系统

- `evaluation_object_list.table`：评价对象管理。前端是 Element 表格，管理员维护课程、商品、服务、活动或人员等被评价对象，展示名称、分类、负责人、状态、开放评价时间、评价次数等列；搜索区支持状态、分类、关键词；新增/编辑/删除由回调控制。它承载“哪些对象可以被评价”。
- `evaluation_submit.form`：用户提交评价。前端是 Element 表单，用户选择评价对象，填写评分、标签、内容、附件、匿名标记后提交；后端校验对象是否开放评价、是否重复评价，然后写入评价记录。它承载一次用户侧提交动作。
- `evaluation_record_list.table`：评价记录管理。前端是 Element 表格，管理员查看评价对象、评分、内容、标签、提交人、提交时间、状态和管理员回复。简单审核、隐藏、回复可以走 Table update 回调。
- `evaluation_score_chart.chart`：可选，评分分布或趋势统计。只有用户要求趋势、占比、报表、看板时再创建。

评价对象和评价记录是长期数据，用 Table；提交评价是一次动作，用 Form；简单状态修改不要额外拆 Form，Table update 回调就够；评分趋势和标签分布才用 Chart。

### 客户管理系统

- `customer_list.table`：客户主数据表格，展示客户名称、行业、等级、联系人、负责人、状态等列，承载客户档案。
- `contact_record_list.table`：跟进记录表格，展示客户、跟进方式、跟进内容、下次跟进时间等，承载长期跟进记录。
- `followup_create.form`：快速新增跟进动作，适合从客户详情或列表 link 进入，提交一次跟进内容。
- `customer_level_chart.chart`：客户等级分布图，展示各等级客户占比。
- `sales_funnel.chart`：销售漏斗，展示阶段分布或转化情况。

客户和跟进是长期记录，用 Table；快速跟进是一次动作，用 Form；等级分布和漏斗是统计，用 Chart。

### 文件处理工具

- `pdf_to_text.form`：上传 PDF，提交后返回文本或文件。前端是上传表单，不需要 Table。
- `excel_import.form`：上传 Excel 并导入某个业务表。前端是上传表单，后端解析并写入数据；如果需要查看导入历史，再单独加 `import_record_list.table`。
- `image_compress.form`：上传图片并返回压缩文件。前端是文件上传表单。

临时文件处理通常是 Form。只有当用户要求保存处理记录、审批记录或长期管理历史时，才加 Table；只有需要统计处理量、成功率、耗时趋势时，才加 Chart。

## PRD 建模要求

创建类需求输出 PRD 前，必须先写“函数类型判断”：

```text
函数类型判断：
- 主业务对象：评价记录，需要长期保存和后台管理，选择 Table，前端以 Element 表格展示列表、搜索、分页和新增/编辑入口。
- 用户提交评价：如果需要独立提交入口，选择 Form，前端以表单提交一次评价。
- 统计评分趋势：如果用户要求看趋势/占比，选择 Chart，前端以图表展示统计结果。
```

PRD 中“函数类型和目录”部分至少说明：

1. 业务对象是什么。
2. 哪些对象需要 Table，以及前端表格展示哪些核心列。
3. 哪些动作需要 Form，以及用户提交后后端做什么。
4. 哪些指标需要 Chart，以及图表展示什么。
5. 是否需要多个目录；没有必要时，一个业务目录下放多个函数即可。

## 常见错误

- 只说“投票系统包含 vote_submit.form”，但不说明它在前端是表单提交界面，也不说明 Table 负责主题/选项管理。
- 把“长期记录管理”写成 Form，导致前端没有列表、搜索、分页和维护入口。
- 把“一次性处理文件”写成 Table，导致用户需要先新增一条记录才能处理文件。
- 把统计图表结构塞进 Form Response，导致前端不能按 Chart 渲染。
- 为复杂系统写一个巨大函数，而不是拆成多个 Table/Form/Chart。
- 在业务代码里重造前端页面、权限、审批、日志、消息、文件上传等平台能力。
