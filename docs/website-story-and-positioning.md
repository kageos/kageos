# Kageos 官网叙事与能力优势

> 状态：官网与视频叙事草案
> 日期：2026-06-16

本文用于统一 Kageos 官网、演示视频、产品介绍和对外话术。核心目标是用最简单、最狠的话讲清楚：Kageos 不是“更便宜的 AI 生成应用”，而是一个开箱即用的业务目录网络。用户可以从 Hub 安装成熟目录，在自己的空间私有运行和改造，也可以自己创造目录并发布回生态。

## 开放与授权口径

Kageos 由恰研智能（qiayanai.com）打造，源码开放、可自托管，项目地址是 `github.com/kageos/kageos`。

当前 Kageos 核心采用 BSL 1.1，不是 OSI open source；它允许源码可见和自托管，限制第三方商业 Hosted Service，各版本到期后转 Apache-2.0。对外不要把当前核心说成“已开源”，推荐说“源码开放、可自托管；当前采用 BSL 1.1，未来转 Apache-2.0”。

## 核心故事

### 两个版本的故事

**版本 A：Hub 目录网络故事（给企业 IT 决策者和团队负责人）**

企业不缺应用，也不缺 AI 生成工具，缺的是可复用、可安装、可治理、可互通的业务能力供给网络。

今天很多企业已经有表格、低代码应用、自动化脚本、业务系统和 AI 助手，但它们通常分散在不同地方：

- 数据在一个个表格和系统里。
- 流程在群聊和人工习惯里。
- 自动化在单独的脚本或工具里。
- AI 在聊天框里，只能总结和建议。
- AI 生成的新应用越来越多，但没有统一的安装、复用、发布和治理路径。
- 应用之间互相看不见，也不知道应该怎么调用彼此。

这造成两个根本问题：

| 问题 | 表现 |
| --- | --- |
| 数据孤岛 | 系统之间靠复制粘贴、导入导出、人工搬运。数据有了，但不能自然流动。 |
| 智能孤岛 | AI 能聊天、能总结，但不知道企业有哪些应用、函数、数据和权限，也不能稳定执行真实业务动作。 |

Kageos 的解法是：把应用变成目录，把目录变成协议，把协议交给 AI 和企业运行时。

目录不是收纳应用的文件夹。目录是应用之间的连接协议，也是 Hub 上可以被安装、被派生、被发布的业务资产。

**版本 B：开箱即用故事（给业务用户和小团队）**

你不应该每次都从空白 prompt 开始造工具。

你应该先从 Hub 找到一个已经能跑的目录：

- 客户跟进目录
- 文件处理目录
- 工单和反馈目录
- 内容日历目录
- 行业情报推送目录

安装到自己的空间后，用自己的数据运行。需要个性化时，再让 AI 基于这个目录修改字段、逻辑、提示词和自动化，而不是重新生成一个孤立应用。

如果你的版本变得更通用、更稳定，还可以发布回 Hub，成为别人开箱即用的目录。

> 先安装能跑的目录，再用 AI 改成你的目录，最后把稳定能力发布回生态。

### 两个故事的统一

这两个故事不是矛盾的，是同一个产品的两面：

- 给懂治理的人讲：Hub 目录网络 + 挂树即治理
- 给想省事的人讲：别从零造，先安装一个能跑的目录
- 给创造者讲：你做出的稳定目录，可以发布回 Hub，成为可分发资产

统一版本：

> Kageos 把业务能力变成开箱即用的目录——Hub 可安装，工作区可私有运行，AI 可改造和执行，稳定版本可发布回生态。

## 不是应用管理器，是应用网络

“AI 生成应用”只是创造目录的一条路，不能当主叙事。

更关键的是更高一层：

> 让业务能力像软件包一样被安装，像应用一样被使用，像 API 一样被调用，像资产一样被发布。

在 Kageos 里，每个目录节点都可以拥有：

- 人可用的页面：Form、Table、Chart、Docs。
- AI 可理解的上下文：目录、文档、函数 schema、历史会话、操作日志。
- 系统可调用的函数：标准表单提交、表格查询/新增/更新/删除、图表查询。
- 平台可治理的记录：权限、操作日志、trace、版本、消息、定时任务。

所以应用不再是孤立页面，也不再是 AI 生成后散落各处的半成品，而是 Hub 和工作区之间可流动的目录资产。

## 演示故事

### 故事 A：智能会议室到智能工单（治理故事）

这是最适合官网视频的示例。

#### 传统企业里发生什么

智能会议室系统知道某层楼的会议室长期约不上。

智能工单系统负责处理设施问题。

管理员靠群消息、会议反馈或人工报表发现问题。

AI 助手最多能说：

> 最近三楼会议室预约紧张，建议提交工单。

但 AI 不知道该去哪个系统提交，也没有标准入口可以调用。

#### Kageos 里发生什么

会议室系统是一个目录。

工单系统是另一个目录。

站内信、Agent 任务和操作日志是平台能力。

Agent 任务每天巡检会议室预约数据。它发现：

> 3 楼会议室连续 2 周工作日上午预约失败率超过 80%。

然后它调用智能工单目录里的"创建工单"函数，提交：

> 标题：3 楼会议室容量不足  
> 内容：过去 14 天，3 楼会议室工作日上午预约失败率持续超过 80%。建议新增会议室、调整楼层空间或开放跨楼层预约策略。  
> 来源：智能会议室系统定时巡检  
> 优先级：中高

最后给管理员发站内信，并在会议室目录和工单目录里留下操作记录。

这不是简单自动化脚本。

这是企业应用开始互相协作。

### 故事 B：热点情报自动推送（真实生产验证）

这是已经跑通的真实场景，不是设想。

#### 业务场景

团队需要持续关注 AI、创业、行业动态，但没人有时间每天刷新闻。需要一个"AI 情报助手"，定时搜索热点、整理总结、推到企微群里。

#### Kageos 里怎么做的

1. 创建一个 `hot_news` 目录
2. 配置一个 Agent 任务，每 15 分钟执行一次
3. Agent 任务的 prompt 告诉 AI：搜索 4 个关键词 → 调用微信文章搜索目录 → 深度阅读有价值文章 → 整理结构化报告 → 调用企微群机器人目录推送
4. AI 跨 3 个目录执行：`/system/test22/hot_news` → `/system/demos/weixin` → `/system/connector/wecom`

#### 结果

- 执行 486 次，0 失败
- 每 15 分钟一次，稳定运行超过 15 天
- 团队成员在手机企微群里稳稳收到推送，不需要打开任何网页
- 完全无人值守，AI 自动完成搜索→分析→推送的全链路

这个故事验证了一个关键点：**目录之间的确定性组合可以形成稳定的生产级自动化，而这是靠 AI 理解力临时拼凑的 Skills 无法做到的。**

五个步骤构成完整闭环：

```
定时触发 → 跨目录调用 → AI 分析 → 外部渠道推送 → 手机收到
```

| 步骤 | 对应能力 | Skills 能不能做 |
| --- | --- | --- |
| 定时触发 | timer-scheduler + Agent 任务 | 大部分不能，或者只能调 webhook |
| 跨目录调用 | namespace + Service Tree | 没人做这个 |
| AI 分析 | agent-server | 通用能力，但上下文是目录内的 |
| 外部渠道推送 | wecom connector | 需要自己接 API |
| 手机收到 | 企微群机器人 | 最终交付 |

## 要打出去的优势

### 1. 目录化

普通平台把应用当项目管理。

Kageos 把应用当目录管理。

目录有路径，有层级，有权限，有上下文。应用一旦进入 Service Tree，就不再是孤立页面，而是可以被搜索、复制、安装、调用、审计和 AI 理解的业务资产。

### 2. 标准化

AI 要稳定操作企业应用，前提是应用必须标准化。

Kageos 把常见业务能力收敛成标准资源：

- Form：提交动作。
- Table：数据管理。
- Chart：查询和统计。
- Docs：业务说明和上下文。
- Function：可调用业务能力。
- Message：站内信通知。
- Schedule：函数任务和 Agent 任务。

标准化之后，AI 才不是“猜页面在哪里”，而是通过目录路径和函数 schema 确定地调用能力。

### 3. 可互通

一个目录可以调用另一个目录。

会议室可以给工单提单。库存可以提醒采购。客服可以触发财务核查。日报可以拉取多个业务目录的统计。AI 可以在目录之间移动，而不是困在单个聊天窗口里。

这直接解决数据孤岛：数据不再只停在自己的系统里，而是通过标准函数和目录路径流动。

### 4. AI 可操作

Kageos 里的 AI 不是外挂聊天框。

AI 工作台能看到目录、文档、函数、日志、历史会话和当前资源。它能查、能写、能调用、能修改应用，也能定时巡检并主动触发动作。

这直接解决智能孤岛：AI 不再只是回答问题，而是进入企业应用网络执行任务。

### 5. 可治理

跨目录调用不是野脚本。

每次调用都有来源、身份、权限、trace 和操作日志。定时任务、站内信、操作记录和版本历史都在平台里留下痕迹。

这使 AI 自动化可以被企业接受：不是黑盒执行，而是可追踪、可回放、可治理。

### 6. 可分发

一个业务目录可以安装、复制、派生和导出能力包。

这让应用不再是一次性项目，而是可流通的业务资产。一个智能会议室目录可以先在演示空间试用，再安装到自己的团队空间，之后根据真实业务修改。

## 最终主张

Kageos 的优势不是单点功能，而是组合：

> 应用目录化、能力标准化、目录可互通、AI 可操作、过程可治理、资产可分发。

这套组合要解决的是企业软件进入 AI 时代后的核心矛盾：

> 应用越来越容易生成，但越来越难管理、连接和治理。AI 越来越聪明，但越不懂企业真实应用在哪里、能做什么、该怎么安全执行。

Kageos 的答案是：

> 把企业应用变成一棵 AI 能读、能调、能改、能治理的目录网络。

## 确定性定位：目录不是更好的 Skill，是 AI 时代的应用基础设施

### 核心论点

市场上大多数"AI first"产品的思路是让 AI 更强，让 AI 能做更多事。Kageos 的思路不同：

> 让能力更确定，让 AI 和人都能可靠地使用它。

前者赌的是 AI 会持续进步，后者赌的是确定性永远是刚需。哪个赌注更安全，一目了然。

### 确定性做底座，不确定性做加速

这是 Kageos 和所有 Skills/Agent 平台的根本架构差异：

- Skills 生态把不确定性（AI 模型）做底座——AI 挂了全停，模型变了全崩，token 费用线性增长
- Kageos 把确定性（代码+运行时）做底座，不确定性（AI）做增强——AI 在更快，AI 不在照样用

用比喻说：Skills 是打车，目录是买车。打车立刻能用但每次都要重新叫、没有积累；买车前期投入大但是你的、可以改装、可以积累里程。一个每天都要出行的人最终会买车。企业就是那个每天都要出行的人。

### AI 只是目录的一个用户

```
Skills 的世界观：人 → AI → 工具（AI 是中间层，人必须通过 AI）
目录的世界观：人 ←→ 目录 ←→ AI（人和 AI 是平等的用户，目录是共享的基础设施）
```

这意味着：
- 企业可以先不接 AI，只用目录的 UI——人点页面一样完成工作
- AI 在的时候是增强，不在的时候业务不停
- 换 AI 模型不影响任何目录里的代码、数据、权限、日志
- 企业不会因为模型厂商的任何变动而失去业务能力

### 编排靠标准接口，不靠 AI 理解力

Skills 的编排为什么不可靠？因为 Skill 之间没有契约——A 输出自然语言，B 期望结构化数据，靠 AI 翻译，每一步都可能出错。

Kageos 目录的每个函数都有标准入参出参，编排是确定性的接口映射，不需要 token，不需要模型理解力，不会因为模型升级而失效。热点情报推送 486 次执行 0 失败，根本原因就是每一步的输入输出都是确定的。

### 目录吞噬 Skills

Kageos 不需要跟 Skills 对着干。每个目录天然可以对外表现为一个 Skill——AI 看到的是函数签名 + 描述，背后跑的是完整的目录运行时。这样 AI 用 Skill 的方式调用目录（低门槛），调用进来的东西有状态、有治理、有数据、可组合（高天花板）。

> 目录是更强的 Skill——Skill 能做的目录都能做，目录能做的 Skill 大部分做不了。

### 完整对比

| 维度 | Skills 生态 | Kageos 目录 |
| --- | --- | --- |
| 核心依赖 | AI 模型 | 代码 + 运行时 |
| 确定性 | 不确定（依赖模型理解力） | 确定（标准入参出参） |
| 成本模型 | token 随调用线性增长 | 代码执行，固定成本 |
| 模型切换 | 需要重写 prompt | 换个 agent 就行，目录不动 |
| 没有 AI | 完全不能工作 | 人在页面上照样用 |
| 编排 | 靠 AI 理解力拼接，脆弱 | 靠标准接口确定性连接，可靠 |
| 数据积累 | 无状态 | 有状态，可审计，可查询 |
| 状态 | 执行完就没了 | 持久存在，可定时触发，可积累 |
| 企业信任度 | 低（不确定性太高） | 高（确定性做底座） |
