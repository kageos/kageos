# 智能工作台 — 设计文档

> 版本：v0.1 | 状态：待评审 | 配套：`note/临时分析/智能工作台-PRD.md`

## 〇、重要约定

- **保留现有 function_gen**：**不删除** 现有 `FunctionGenChat`、`AIChatPanel`、`/agent/api/v1/chat/function_gen` 及相关逻辑；智能工作台作为**新增能力**与 function_gen **并存**。
- **开发分支**：在 `main` 上新开分支（如 `feature/workspace`）开发智能工作台；与 function_gen 的修改隔离。
- **以目录为边界**：`tree_id` 必填；指定目录 = 该目录 + 子节点；点根 = 上帝视角；鼓励在具体目录开。
- **开发与编排为主**：工具优先 `add_functions`、插件、`web_search`、`docs_*` 等；`table_*`、`form_submit` 等执行业务后置。

## 二、agent-server 模块设计

### 2.1 WorkspaceChatService（新）

- **职责**：工作台对话的编排；会话、消息、知识库加载、LLM 调用、Tool 循环。
- **入口**：`WorkspaceChat(c tree_id, message, session_id?, agent_id?)`。
- **流程**：  
  1. 解析/创建会话（session 与 `tree_id` 绑定）；  
  2. 加载历史消息；  
  3. 按 `tree_id`（及 Agent.DocsPaths 或该 tree 的 docs）加载知识库；  
  4. 构建 System：知识库 + 常用 tools 的简要说明（写死 prompt）；  
  5. 构建 `tools`：从 ToolRegistry.list_tools() 取定义，供 LLM；  
  6. 调用 LLM（Chat with tools）；  
  7. 若存在 `tool_calls`：  
     - 对每个 call：`ToolRegistry.call_tool(name, arguments, tree_id)`；  
     - 将 `assistant`（含 tool_calls）与 `tool` 结果 append 到消息；  
     - 回到 6，直到无 tool_calls 或达到轮数上限；  
  8. 持久化消息，返回最终 `content` 及 `session_id`、可选 `tool_calls` 摘要给前端。

### 2.2 MCP / ToolRegistry（新）

- **list_tools()**：  
  - 内置：add_functions、web_search、docs_search、docs_get、… 的 schema；  
  - 插件：从 **Plugin** 表读 enabled 列表，每条 → `{name, description, [keywords], inputSchema}`，FormPath 仅内部使用。  
- **search_tools(keyword)**：  
  - 在 name、description、keywords 中 LIKE 或简单分词匹配；  
  - 返回 `list_tools` 的子集。  
- **call_tool(name, arguments, tree_id)**：  
  - 若为内置：路由到对应 impl，传入 `tree_id`、`arguments`；  
  - 若为插件：查 Plugin 表取 FormPath，`CallFormAPI(FormPath, {Content: arguments.content, InputFiles: arguments.files})`；  
  - 返回 `{content, is_error?}` 字符串，供填到 `role=tool` 的 `content`。

### 2.3 内置工具与 tree_id

- **add_functions**：  
  - 入参：`tree_id`、`parent_tree_id` 或 `package`、`code`；  
  - 从 `tree_id` 解析 app、user，组 `AddFunctionsReq`，调 `apicall.ServiceTreeAddFunctions`；  
  - 做 tree 归属校验：`parent_tree_id` 须在 `tree_id` 所表示子树内。  
- **web_search**：入参 `keyword`；实现可为外包或预留；与 tree 无强绑定。  
- **docs_search**：入参 `keyword`；调 app-server 的 SearchDocs，增加 `full_code_path_prefix`（由 `tree_id` 换算该 tree 的 full_code_path 前缀）。  
- **docs_get**：入参 `path` 或 `id`；校验 path 在 tree 下，再 BatchGetDocs 或 GetByID。  
- **插件**：无 tree 绑定；Form 的权限由 app-server/Form 侧控制。

### 2.4 会话与消息模型（扩展现有或独立）

- **方案 A（推荐）**：复用 `chat_sessions`、`chat_messages`，扩展或使用字段：  
  - `chat_sessions`：`source` 或 `chat_type` = `workspace`；`tree_id` 必填。  
  - `chat_messages`：`role` 支持 `tool`；`tool_calls`（JSON）、`tool_call_id` 等按 LLM 通用 schema 存。  
- **方案 B**：新建 `workspace_sessions`、`workspace_messages`，减少与 function_gen 的耦合；写入与清理策略单独定。  
- 设计阶段建议采用 **方案 A**，若后续需要再拆表。

## 三、API 设计

### 3.1 工作台对话

- **POST** `/agent/api/v1/workspace/chat/stream`
- **Request**:
  ```json
  {
    "tree_id": 123,           // 必填
    "message": {
      "content": "我有一份 Excel，帮我生成 CRM",
      "files": [ { "name", "url", "..." } ]  // 可选，与现有 types.Files 兼容
    },
    "session_id": "uuid",     // 可选，空则新建
    "agent_id": 1             // 可选，缺省可用 workspace 默认 Agent
  }
  ```
- **Response**（非流式）:
  ```json
  {
    "session_id": "uuid",
    "content": "已经根据您的 Excel 生成 CRM，包含 leads 表与列表...",
    "tool_calls": [           // 可选，本轮的 tool 调用摘要，供前端展示
      { "name": "excel_parse", "status": "ok" },
      { "name": "add_functions", "status": "ok" }
    ]
  }
  ```
- **流式**：可选；可用 SSE，事件类型：`message`、`tool_call`、`done`。

### 3.2 MCP 形态（内部）

- 不暴露独立 HTTP；由 WorkspaceChatService 内调：  
  - `list_tools()`  
  - `search_tools(keyword)`（若 LLM 先查再选，可做一步；也可省略，仅靠 prompt）  
  - `call_tool(name, arguments, tree_id)`

## 四、前端设计

### 4.1 入口

- 在 **ServiceTreePanel**（或等价）的节点**右键菜单**或**节点操作区**增加「**打开工作台**」。
- 点击后：若已有「工作台」路由/视图，则打开并传入 `tree_id`；否则路由到 `/workspace?workstation=1&tree_id=xxx` 或独立 `/workstation?tree_id=xxx`。

### 4.2 工作台视图（新）

- **布局**：左侧可保留精简树或面包屑（当前 `tree_id` 对应目录）；中间对话区；右侧可选「本会话 Tool 调用」折叠面板。  
- **对话区**：  
  - user：文本 + 附件列表；  
  - assistant：文本；若有 `tool_calls`，渲染为可折叠卡片（工具名、参数概要、成功/失败）。  
- **输入**：文本框 + 附件上传；发送 `{ tree_id, message: { content, files }, session_id }` 到 `POST /agent/api/v1/workspace/chat/stream`。  
- **会话**：顶部或侧边展示「当前目录：xxx」、「新建会话」；`session_id` 与 `tree_id` 绑定；切换目录时提示新建会话或切到该目录的已有会话。

### 4.3 与 AIChatPanel 的隔离

- AIChatPanel 继续在包级、选智能体后展示，走 `function_gen` API；**不删不改** 其既有逻辑，仅在有冲突时做最小适配（如共享 `chat_sessions` 表时的 `source` 区分）。

---

## 五、app-server 扩展（最小）

- **SearchDocs**：增加可选 `full_code_path_prefix` 或 `tree_id`；若提供，则 `WHERE full_code_path LIKE 'prefix%'`（prefix 由 tree 的 full_code_path 及其子节点前缀得到）。  
- **BatchGetDocs / GetByID**：若通过 docs_get 调用，由 agent-server 做 path 归属校验即可；app-server 可不变。  
- **add_functions**：已有；agent-server 组装 `AddFunctionsReq` 时带 `tree_id`、目标 package，按现有契约调用。

---

## 六、Plugin 与 插件型 tool

- **数据**：沿用 **Plugin** 表，`FormPath`、name、code、description；可增加 `keywords`（JSON 或逗号串）便于 search_tools。  
- **加载**：ToolRegistry 启动或按需从 DB 读 `enabled=1` 的 Plugin，映射为 tool；`call_tool(plugin_xxx)` → `CallFormAPI(FormPath, {Content, InputFiles})`，请求体与现有 `AgentPluginFormReq` 一致。  
- **FormPath**：必须为本平台已注册的 Form 的 full-code-path，权限与可用性由 app-server/Form 保证。

---

## 七、知识库加载

- **范围**：以 `tree_id` 为根，该节点及其子节点下所有 **docs** 类型节点对应的文档；或按 Agent.DocsPaths 与 tree 的交集。  
- **实现**：  
  - 由 agent-server 调 app-server 的「按 tree 查 docs 子节点」或「SearchDocs(full_code_path_prefix=tree_prefix)」；  
  - 再 BatchGetDocs 拿 content，拼成知识库文本注入 System。  
- 若 app-server 暂无「按 tree 查 docs」：可先用 **DocsPaths** 中落在该 tree 下的路径做 BatchGetDocs，Phase 2 再补 tree 维度接口。

---

## 八、安全与权限

- **tree_id**：校验当前用户对该 tree 所在 app 有权限；可复用现有 app/树 权限。  
- **call_tool**：  
  - add_functions、docs_*、read_file 等：校验目标 path/package 在 `tree_id` 子树内；  
  - 插件：Form 的权限在 app-server 校验，agent-server 负责正确传 token/上下文。  
- **频率与配额**：可与现有 LLM 配额统一；Tool 调用可记日志便于审计。

### 9.3 分 Phase 实现（与 PRD 一致）

- **Phase 1**：目录入口 + 工作台 UI 骨架 + `WorkspaceChat` API + **ToolRegistry（list_tools、call_tool）** + **add_functions、1 个插件（如 Excel）、web_search** + 知识库（DocsPaths 或 tree 下 docs 现有能力）；实现「Excel+需求→解析→生成→落盘」闭环。

- **Phase 3**：docs_list_outline、run_build；table_* / form_submit（可选）；Tool 流式与折叠展示；与 AIChat 的会话/表共用策略定型。

## 十、设计决策与风险

| 决策 | 说明 |
|------|------|
| **不删 function_gen** | 保留 AIChatPanel 与 包级单插件+生成流程；工作台与其并存，降低风险。 |
| **tree_id 必填** | 显式边界，避免隐式上下文；与「一个目录=领域=系统」一致。 |
| **MCP 先内聚** | list/search/call 在 agent-server 内实现，不先对外暴露 MCP 协议；后续可再包一层 MCP 兼容。 |
| **Plugin 映射为 tool** | 复用 FormPath、CallFormAPI，不改 Plugin 表结构；仅可选加 keywords。 |
| **会话表复用** | 优先复用 `chat_sessions`/`chat_messages`，用 `source=workspace` 区分；若后续冲突再拆。 |
| **风险** | SearchDocs 的 tree 维度和 tree→prefix 的获取需 app-server 配合，Phase 1 可用 DocsPaths 降级。 |
