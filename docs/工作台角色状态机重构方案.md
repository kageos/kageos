# 工作台角色状态机重构方案

> 状态：草案
> 更新时间：2026-05-17
> 负责人窗口：事项 8 / codex/document-archive-cleanup

## 1. 背景

当前工作台已经具备一条可行链路：

```text
用户提出新建应用需求
-> product_manager 生成结构化 PRD
-> 用户确认 PRD
-> handoff 到 app_developer
-> 根据 PRD 生成应用并 build
```

这条链路产品上是成立的，技术上也已经有较好的雏形：`write_prd` 是无副作用结构化产物工具，`WorkspaceHandoff` 可以把 PRD 确认后的执行放进新会话，`ContextPolicy` 和 `ArchivedForModel` 可以减少旧上下文污染。

但当前实现仍然偏 prompt 约束：

1. 单 `dev` 模式暴露了大量工具，具体阶段能不能调用主要靠系统提示词约束。
2. 当前需要把内部状态名统一为稳定角色 ID，并对用户展示“工作台团队协作”的角色心智。
3. 角色切换和上下文裁剪还没有形成后端主导的显式状态机。
4. 阶段交接主要是把 artifact 拼进用户消息，缺少独立、可校验、可追踪的交接包。

本方案目标是把工作台从“单 dev 模式 + 模型自觉切换角色”升级为：

```text
后端角色状态机 + 中文展示角色 + 角色工具门禁 + 结构化 handoff + artifact-only 上下文
```

## 2. 核心结论

1. 用户侧展示“产品经理、应用开发工程师、测试工程师”等角色；模型侧和代码侧统一使用 `product_manager`、`app_developer` 等角色 ID。
2. 代码侧使用稳定英文 `role_id`，例如 `product_manager`、`app_developer`、`qa_engineer`。
3. 角色是状态机节点，不只是 prompt 人设。每个角色必须定义目标、输入、工具、禁止事项、输出产物和可流转目标。
4. 主工作台只负责调度、创建角色会话、过滤上下文和执行状态流转，不直接承担所有业务 SOP。
5. 历史消息保留给 UI 展示；模型上下文按角色和 `context_policy` 裁剪，只带 artifact、摘要和必要运行结果。
6. 工具权限必须由后端硬门禁执行，不能只依赖 prompt。

## 3. 命名原则

内部角色 ID 使用英文稳定标识，前端展示中文名称：

| 内部 `role_id` | 展示名称 | 职责边界 |
| --- | --- | --- |
| `router` | 工作台调度员 | 目标识别和角色调度 |
| `product_manager` | 产品经理 | 新应用需求分析和结构化 PRD |
| `app_developer` | 应用开发工程师 | 按已确认 PRD 创建应用并 build |
| `build_engineer` | 构建修复工程师 | 修复构建、schema、SDK 使用错误 |
| `qa_engineer` | 测试工程师 | 运行 Table/Form/Chart 等功能验证 |
| `maintenance_engineer` | 应用维护工程师 | 修改已有应用和业务逻辑 |
| `platform_engineer` | 平台集成工程师 | 平台 OpenAPI、SDK 调用、文件访问和 Table 更新日志 |
| `data_operator` | 数据/文件处理工程师 | 一次性文件、媒体和数据处理 |
| `reviewer` | 代码审查分析师 | 只读分析、解释和风险审查 |

当前处于开发阶段，无需保留历史包袱；模型主链路、前端参数、session 状态和角色文档都直接使用新 `role_id`。

## 4. 角色定义模板

每个角色都按同一份角色卡定义：

```json
{
  "role_id": "app_developer",
  "display_name": "应用开发工程师",
  "goal": "按确认后的 PRD 创建应用并完成 build",
  "input_artifacts": ["agent_app_prd"],
  "context_policy": "artifact_only",
  "prompt_docs": [
    "/system/prompt/roles/app-developer",
    "/system/prompt/sdk/agent-app-sdk-readme"
  ],
  "allowed_tools": [
    "change_role",
    "read_doc",
    "read_dir",
    "create_directory",
    "write_go_file",
    "read_go_file",
    "build_workspace"
  ],
  "forbidden_tools": [
    "write_prd",
    "run_form_submit",
    "run_table_update"
  ],
  "done_artifact": "implementation_result",
  "transitions": [
    {
      "event": "build_success",
      "to": "qa_engineer"
    },
    {
      "event": "build_failed",
      "to": "build_engineer"
    }
  ]
}
```

判断是否应该拆角色的标准：

1. 这个角色是否有独立工具边界。
2. 这个角色是否有独立上下文边界。
3. 这个角色是否有独立产物边界。
4. 这个角色完成后是否天然需要交接给别的角色。

如果只是提示词措辞不同，不拆新角色，放到角色内部的 `task_type` 或专项文档里。

## 5. 推荐角色职责

### 5.1 工作台调度员 `router`

职责：

- 识别用户最新需求。
- 判断目标角色。
- 决定上下文策略。
- 不执行有副作用动作。

允许工具：

- 第一阶段可以不暴露工具，只由后端规则和轻量模型调用输出 `RoleRouteDecision`。
- 如果继续使用工具形式，则只允许 `route_role` 或兼容 `change_role`。

输出：

```json
{
  "target_role": "product_manager",
  "reason": "用户要创建长期业务系统，且还没有确认 PRD",
  "confidence": 0.92,
  "context_policy": "fresh"
}
```

### 5.2 产品经理 `product_manager`

职责：

- 分析新应用需求。
- 必要时做最少量澄清。
- 输出结构化 PRD。
- 等待用户确认。

输入上下文：

- 用户需求。
- 当前目录环境。
- 轻量案例目录。
- 不读取大量源码。

允许工具：

- `change_role`
- `read_doc`
- `read_dir`
- `write_prd`

禁止工具：

- `create_directory`
- `write_go_file`
- `search_replace_file`
- `delete_file`
- `build_workspace`
- `run_form_submit`
- `run_table_*`
- `run_chart_query`

输出产物：

- `agent_app_prd`

结束状态：

- `waiting_user_confirm`

流转：

```text
用户确认 PRD -> app_developer
用户补充需求 -> product_manager
用户取消 -> done
```

### 5.3 应用开发工程师 `app_developer`

职责：

- 只按已确认 PRD 开发应用。
- 读取完整 SDK 主文档和匹配案例。
- 创建目录、写 Go 文件、统一 build。

输入上下文：

- `agent_app_prd`
- 用户确认备注。
- 当前目录环境。
- 必要案例和 SDK 文档。

允许工具：

- `change_role`
- `read_doc`
- `read_dir`
- `read_go_file`
- `read_go_file_lines`
- `create_directory`
- `write_go_file`
- `build_workspace`
- `read_app_log`

禁止工具：

- `write_prd`
- 运行类业务副作用工具，除非开发阶段明确需要读取 schema 做自检。

输出产物：

- `implementation_result`
- 文件清单
- 路由清单
- build 结果

流转：

```text
build 成功 -> qa_engineer
build 失败 -> build_engineer
PRD 缺关键字段 -> product_manager
```

### 5.4 构建修复工程师 `build_engineer`

职责：

- 修复 Go 编译错误、schema compile failed、widget 校验、SDK API 使用错误。
- 读取完整错误，按错误类型批量修复。
- 不重新设计 PRD。

输入上下文：

- build 错误日志。
- 相关文件路径。
- 最新代码片段。
- 已确认 PRD 摘要。

允许工具：

- `read_doc`
- `read_go_file`
- `read_go_file_lines`
- `search_replace_file`
- `write_go_file`
- `build_workspace`
- `read_app_log`

禁止工具：

- `write_prd`
- `create_directory`，除非错误明确指向缺目录。
- 业务运行类工具。

输出产物：

- `build_fix_result`

流转：

```text
修复并 build 成功 -> qa_engineer
错误指向业务设计缺陷 -> maintenance_engineer 或 product_manager
```

### 5.5 测试工程师 `qa_engineer`

职责：

- 按验收用例测试 Table/Form/Chart。
- 区分数据问题、业务规则问题、代码问题和 build/schema 问题。
- 产出测试报告。

输入上下文：

- 路由清单。
- schema 摘要。
- 验收用例。
- build 成功结果。

允许工具：

- `read_dir`
- `search_tools`
- `run_table_search`
- `run_table_create`
- `run_table_update`
- `run_table_delete`
- `run_form_submit`
- `run_chart_query`
- `run_on_select_fuzzy`

禁止工具：

- `write_prd`
- `write_go_file`
- `search_replace_file`
- `delete_file`
- `build_workspace`

输出产物：

- `qa_report`

流转：

```text
测试通过 -> done
业务 bug -> maintenance_engineer
构建/schema 问题 -> build_engineer
需求不清 -> product_manager
```

### 5.6 应用维护工程师 `maintenance_engineer`

职责：

- 修改已有应用。
- 新增/删除/改名字段。
- 修改 widget、选项、回调、跳转、图表指标。
- 修复业务 bug。

输入上下文：

- 用户修改目标。
- 当前目录和相关源码。
- 测试失败报告或用户反馈。

允许工具：

- `read_doc`
- `read_dir`
- `read_go_file`
- `read_go_file_lines`
- `search_replace_file`
- `write_go_file`
- `build_workspace`

可选工具：

- 修改后如果需要快速确认，可 handoff 给 `qa_engineer`，不在本角色中长期执行运行测试。

输出产物：

- `maintenance_result`
- build 结果

流转：

```text
build 成功 -> qa_engineer
build 失败 -> build_engineer
修改范围需要重新确认 -> product_manager
```

### 5.7 平台集成工程师 `platform_engineer`

职责：

- 平台 OpenAPI。
- SDK 调用、文件访问、Table 更新日志等 MVP 平台能力。
- 不硬编码 token，不直连内部服务。

允许工具：

- `search_tools`
- `run_form_submit`
- `read_doc`
- 平台专项工具。

输出产物：

- `platform_operation_result`

### 5.9 数据/文件处理工程师 `data_operator`

职责：

- 一次性文件、图片、视频、PDF、CSV、Excel、Python 数据处理。
- 不沉淀长期业务应用，除非用户明确要求。

允许工具：

- `run_python`
- `read_doc`
- 必要平台文件工具。

流转：

```text
一次性处理完成 -> done
用户要求长期管理/统计 -> product_manager
```

### 5.10 代码审查分析师 `reviewer`

职责：

- 只读分析、代码 review、解释项目、解释函数。
- 不落盘、不 build、不运行有业务副作用的工具。

允许工具：

- `read_dir`
- `read_go_file`
- `read_go_file_lines`
- `read_doc`

禁止工具：

- 所有写入、构建、业务运行副作用工具。

流转：

```text
用户要求修改 -> maintenance_engineer
用户要求新建系统 -> product_manager
```

```text
  -> done
```

## 7. Handoff 交接包

角色之间不要自由传递完整聊天记录，统一传结构化 handoff packet。

```json
{
  "handoff_id": "uuid",
  "from_role": "app_developer",
  "to_role": "qa_engineer",
  "event": "build_success",
  "reason": "应用已生成并 build 成功，需要按 PRD 验收用例测试",
  "context_policy": "artifact_only",
  "artifacts": [
    {
      "kind": "agent_app_prd",
      "id": "prd-uuid",
      "version": 1
    },
    {
      "kind": "implementation_result",
      "id": "impl-uuid",
      "version": 1
    }
  ],
  "summary": "已创建 NPS 系统，包含问卷表、评价提交 Form、评价记录表和统计 Chart。",
  "directory": "/liubeiluo/demo/nps",
  "routes": [
    "nps_questionnaire_list.table",
    "nps_submit.form",
    "nps_record_list.table",
    "nps_statistics.chart"
  ],
  "files": [
    "nps_questionnaire_list.go",
    "nps_submit.go",
    "nps_record_list.go",
    "nps_statistics.go"
  ],
  "known_issues": [],
  "next_steps": [
    "创建一条问卷",
    "提交一次 NPS 评价",
    "查询评价记录",
    "查询统计图表"
  ]
}
```

第一阶段可以继续把 handoff packet 渲染成新会话第一条用户消息，但后端必须保留结构化字段，后续再让模型上下文直接从 artifact 和 packet 生成。

## 8. 上下文策略

UI 历史和模型上下文分离。

| 策略 | 含义 | 使用场景 |
| --- | --- | --- |
| `full` | 当前会话完整上下文 | 同角色连续对话 |
| `artifact_only` | 只带结构化产物、handoff 摘要、用户确认备注 | PRD 确认后进入开发、开发后进入测试 |
| `summary_only` | 只带阶段摘要和关键文件/路由 | 构建修复、测试失败转修改 |
| `display_only` | 只保留 UI 展示，不进入模型上下文 | 已交接的旧会话 |

关键规则：

1. 产品经理到开发工程师只带 PRD artifact 和确认备注。
2. 开发工程师到测试工程师只带 PRD、实现结果、路由和验收路径。
3. 测试工程师到维护工程师只带失败报告、目标路由和必要请求/响应样例。
4. 构建修复工程师只带 build 错误、相关文件和最近修改摘要。
5. 旧阶段聊天正文默认不进入新角色上下文。

## 9. 工具门禁

当前工具暴露策略需要从“按模式列工具”改成“按角色硬授权”。

执行工具前增加统一检查：

```go
func checkRoleToolPermission(roleID string, toolName string) error
```

规则：

1. 如果当前 session 有 `role_id`，按角色 allowlist 判断。
2. 如果没有 `role_id`，只允许 router 或兼容旧 dev 行为。
3. deny 时保存 tool message，明确告诉模型当前角色不能调用该工具，并提示可 handoff 的目标角色。
4. `forbidden_tools` 优先级高于 `allowed_tools`。
5. 高风险工具必须显式允许：`write_go_file`、`search_replace_file`、`delete_file`、`build_workspace`、`run_*`、`create_directory`。

示例：

```text
产品经理调用 write_go_file
-> 后端阻断
-> 返回：当前角色「产品经理」只负责 PRD，不能写代码。请先等待用户确认 PRD，再交接给「应用开发工程师」。
```

## 12. 迁移策略

### 阶段一：角色命名和 catalog

目标：不改变现有执行链路，只建立新角色语义。

任务：

1. 新增 `RoleCatalog`，维护 `role_id`、中文展示名、工具 allowlist、prompt docs。
2. Dev 主提示词、角色文档、前端 handoff 参数都直接使用新角色 ID。
3. `change_role` 返回新 `role_id` 和 `display_name`，兼容旧字段。
4. 前端展示中文角色名。

当前状态：已落地。`workspace_role_catalog.go` 维护角色目录；`change_role` 返回 `role_id`/`display_name`；会话列表已展示 `role_display_name`；模型主链路不再使用旧 `app.*` ID。

### 阶段二：工具门禁

目标：让角色边界从 prompt 约束变成后端约束。

任务：

1. 在工具执行入口增加 `checkRoleToolPermission`。
2. session 当前角色来自 `role_id` 或 handoff target role。
3. 为产品经理、开发工程师、测试工程师、构建修复工程师先配 allowlist。
4. 增加测试：产品经理不能 `write_go_file`，开发工程师不能 `write_prd`，测试工程师不能 `write_go_file`。

当前状态：已落地。工具执行入口会按当前 session 角色做后端门禁；角色来源优先级为 `role_id`、`handoff_target_role`、历史 `change_role` 工具结果。

### 阶段三：handoff 原子化

目标：避免“已归档来源会话，但目标会话首条消息发送失败”的中间态。

任务：

1. `CreateWorkspaceHandoff` 同一事务内创建目标 session 和首条 artifact message。
2. 返回目标 session 后前端直接订阅执行。
3. handoff packet 落库。
4. 旧 handoff 文本继续兼容，但结构化 packet 成为权威输入。

当前状态：已落地 handoff 原子化。`CreateWorkspaceHandoff` 已在同一事务内归档来源会话、创建目标 session、写入首条 `artifact` 用户消息，并落库 `workspace_handoff_packets`；前端随后用 `resume=true` 续跑，避免重复落库。通用 artifact 表尚未实现。

### 阶段四：artifact 正式化

目标：PRD、实现结果、测试报告都成为可校验产物。

任务：

1. `agent_app_prd` 增加 `schema_version`。
2. 后端提供 canonical normalize/validate。
3. 前端 TS 类型从 JSON schema 生成或与后端 schema 同源。
4. `write_prd` 成功后创建 artifact 记录。
5. `app_developer` 从 artifact ID 读取 PRD，而不是从长文本中解析。

### 阶段五：状态机执行器

目标：主工作台成为显式角色流程 runtime。

任务：

1. 新增 `RoleStateMachine`。
2. 定义 `RoleEvent`：`prd_generated`、`user_confirmed`、`build_success`、`build_failed`、`qa_failed`、`done`。
3. 状态机根据事件创建下一个角色 run。
4. 每个角色 run 构建自己的 prompt、工具集和上下文。
5. 用户可以手动 override 流转，但 override 也要落库。

## 13. 第一批落地范围

优先只覆盖新建应用主链路：

```text
product_manager
-> waiting_user_confirm
-> app_developer
-> build_engineer?
-> qa_engineer
```

本阶段暂不深改：

- 平台 OpenAPI 全量角色。
- 所有修改专项二级任务。
- 完整角色流程可视化。

原因：

1. 新建应用链路收益最大。
2. 当前已有 PRD 和 handoff 基础，改造成本最低。
3. 能最快验证角色状态机是否明显降低上下文污染。

## 14. 验收标准

### 产品体验

1. 用户看到的是“产品经理、应用开发工程师、测试工程师”等角色。
2. PRD 生成后明确进入“等待用户确认”状态。
3. 用户确认后，开发工程师只看到 PRD artifact 和备注，不再看到完整 PRD 讨论历史。
4. build 成功后可以明确交接给测试工程师。
5. 测试失败时可以明确交接给应用维护工程师或构建修复工程师。

### 工程约束

1. 产品经理调用写代码、build、运行类工具会被后端阻断。
2. 开发工程师不能重新调用 `write_prd`。
3. 测试工程师不能写文件。
4. 旧会话归档后不进入模型上下文，但 UI 仍能查看。
5. handoff packet 有结构化记录，可追溯来源角色、目标角色、事件和 artifact。

### 稳定性

1. 现有 `write_prd` 测试继续通过。
2. 现有 `CreateWorkspaceHandoff` 兼容测试继续通过。
3. 新增角色工具门禁单测。
4. 新建应用 E2E 链路至少覆盖 PRD 确认到 build 成功。

## 15. 关键取舍

1. 角色可以很多，但状态机主节点不要太碎。
2. 中文角色名用于展示，英文 `role_id` 用于代码和状态机。
3. prompt 仍然重要，但只能描述角色行为，不能承担工具边界控制。
4. handoff 是结构化交接，不是角色之间自由聊天。
5. 开发阶段不保留旧内部 ID 的模型侧兼容；发现旧 ID 应直接修提示词或调用方。
