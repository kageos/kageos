# 关于如何写 kageos_manifest.go

`kageos_manifest.go` 用来给一个 KageOS package 声明出厂默认资产。第一版只放两类东西：

- `runbook.docs`：目录级运行手册。
- `AgentTask`：某个具体无人值守任务的默认模板。

它们都是 seed，不是长期权威源。build/update 后，平台会把缺失的文档和默认 Agent 任务挂到 Service Tree；后续运行态以树上的 `runbook.docs` 和平台里的任务配置为准。代码里的 `kageos_manifest.go` 只负责首次创建，不应覆盖线上人工维护过的内容。

## 核心区别

`runbook.docs` 是目录级运行契约。任何 Agent 进入这个目录，都应该能靠它理解业务背景、核心资源、标准 SOP、异常处理、通知规则和禁止事项。它覆盖的不只是定时任务，还包括用户临时提问、移动端回复通知、人工要求分析数据、外部事件触发后的接续会话。

`AgentTask.Message` 是某个具体无人值守任务的执行单。它描述一次定时或自动任务如何闭环，例如每天生成公众号草稿、每小时巡检证书、定时搜索新闻并入库。它必须写清本轮任务目标、时间窗口、工具、分页、幂等、去重、写入规则、失败处理和通知规则。

一句话：`runbook.docs` 管“这个目录遇到任何事怎么做”，`AgentTask.Message` 管“这个任务到点后这一轮怎么跑”。

## 资源引用

文档和任务说明里引用当前目录资源时，使用轻量资源标记：

- 当前目录表格：`<./profiles.table>`
- 当前目录表单：`<./send_notice.form>`
- 当前目录图表：`<./risk_report.chart>`
- 当前目录文档：`<./runbook.docs>`
- 跨目录资源：`</system/tools/html/render.form>`
- 内置 Agent 工具：`<tool:send_notification>`

不要写 `./profiles.table`，也不要写 `<profiles.table>`。相对资源必须带 `./`，否则阅读态和工具解析容易不一致。引用内置工具时不要写 `<send_notification>`，因为它不是 Service Tree 资源路径；需要回显工具 chip 时写 `<tool:send_notification>`，真实工具调用名仍是 `send_notification`。

轻量资源标记只提供导航和语义引用，不会自动查询数据。真正查询表格时，Agent 仍要调用 table 工具，并按分页读完。

## runbook.docs 应该写什么

高质量 `runbook.docs` 应该像业务目录的操作宪法，不是 README、PRD 或某个定时任务 prompt。

建议结构：

```markdown
# <业务目录>运行手册

## 业务背景

说明这个目录解决什么问题、为什么存在、人的目标是什么、AI 应该承担哪些后台复杂度。

## 核心资源

- <./xxx.table>：做什么。
- <./yyy.form>：什么时候允许调用。
- <./runbook.docs>：本手册。

## 主流程

1. 正常业务如何开始。
2. AI 可以自动做什么。
3. 哪些步骤需要人工确认。
4. 最终产物在哪里查看。

## 状态机

列出每个关键状态的含义、允许流转、禁止流转。

## 常见场景 SOP

- 用户新增一条记录时怎么处理。
- 用户让你分析数据时怎么处理。
- 移动端回复通知时怎么处理。
- 外部系统通知或监控告警触发时怎么处理。

## 异常处理

- 数据缺失怎么办。
- 查询失败怎么办。
- 发现重复数据怎么办。
- 外部工具失败怎么办。

## 通知规则

- 哪些结果需要通知用户。
- 哪些普通状态不要打扰用户。
- 通过通知工具回复时应包含哪些字段。

## 禁止事项

- 不允许自动发布、付款、审批通过等高风险动作。
- 不允许编造数据。
- 不允许只看第一页就下结论。
- 不允许绕过表格回调直接写不一致状态。

## 执行后自检

- 数据是否分页读完。
- 状态是否符合状态机。
- 是否产生重复记录。
- 是否留下需要人工处理的事项。
```

runbook 里要写稳定规则，不要写某个 cron 的细碎执行安排。比如“黄金报价单位默认是元，不是盎司”“本目录不提供投资建议”“分析库存必须读完全部分页”，这些属于目录长期规则，应该放 runbook。

## AgentTask.Message 应该写什么

AgentTask 是无人值守任务，运行时用户不在线，所以不能写“到时候问我”。任务必须自己闭环，遇到不能决定的事要降级、记录、通知或留下人工待办。

高质量 AgentTask 必须先分析再执行。每轮开跑前先分页读取输入，算清真实工作量，制定执行方案：执行前缺口快照、真实总缺口、单轮上限、选择对象、预计产出、是否需要 `web_search` 或外部数据、执行后如何验证。

执行方案要把“执行前缺口”和“执行后剩余缺口”分开。不要用执行后的数据解释执行前计划，也不要把本轮选择处理的对象数量当作真实总缺口。若任务有单轮上限，计划新增数通常应等于 `min(执行前真实总缺口, 单轮上限)`；如果少于这个数，必须写明素材不足、重复风险、写入失败或其他跳过原因。若执行后发现仍有缺口且不超过上限、也没有跳过原因，应继续补齐再验证。

不要让模型长期口算可由后端确定的工作量。像目标数、已有数、缺口数、完成率、待处理数、逾期数这类反复用于自动任务计划的数字，优先在主工作台 Table 行里用 `gorm:"-"` 展示字段或后端查询补齐，例如“已有草稿数 / 待补篇数 / 生产进度”。比例、完成率和进度优先使用 `widget:"type:progress;min:0;max:100;unit:%"`，不要用普通文本让模型再解释。AgentTask 应要求读取这些确定性字段，再用明细表复核标题、失败项和重复风险。

生成子记录时必须在新增时绑定上游业务对象，例如从选题生成草稿、从合同生成节点、从证书生成续期任务。不要先创建未绑定的子记录，再靠更新回调补外键或上下文；如果写入后发现上游展示名称为空，要把它视为写入不合格，不计入成功。

内容生产类任务要明确事实和表达规则：需要公开事实、新闻、产品信息、行业数据时可以使用 `web_search`；使用外部资料时必须记录来源。没有来源时不要编造数据、案例、引用或第一人称经历。还要写清反 AI 味要求，例如避免空泛套话、同质化结构和无场景的正确废话。

建议结构：

```markdown
## 执行身份

说明这是无人值守任务，不能向用户提问，必须按 <./runbook.docs> 执行。

## 绑定范围

- 运行规则：<./runbook.docs>
- 输入资源：<./xxx.table>
- 输出资源：<./yyy.table>
- 外部工具：web_search / <tool:send_notification> / 其他连接器

## 本轮目标

说明这一次定时任务要完成什么，不要泛泛写“优化业务”。

## 时间窗口和幂等

说明本轮读取哪个时间范围、如何避免重复处理、唯一键是什么、遇到已存在记录怎么办。

## 预期工具

列出预计使用的工具，例如 table 查询、table 新增、table 更新、web_search、send_notification。写入文档或任务说明时，内置通知工具可标成 `<tool:send_notification>`。

## 执行步骤

1. 先读 <./runbook.docs>。
2. 分页读取输入数据，不能只看第一页。
3. 制定本轮执行方案：优先使用后端已计算的执行前缺口快照、真实总缺口、单轮上限、选择对象、预计产出、事实来源策略、验证口径。
4. 按业务规则过滤和去重。
5. 写入或更新目标数据；新增子记录时必须绑定上游对象。
6. 执行后重新读取目标数据验证，不要只相信写入接口返回。
7. 若执行前缺口不超过上限但执行后仍有缺口，且没有明确跳过原因，继续补齐并再次验证。
8. 汇总本轮结果，确保执行前缺口、计划新增、实际新增、执行后剩余缺口和分项明细一致。
9. 按通知规则通知或静默结束。

## 质量控制

列出本任务特有的质量规则，例如新闻入库前必须判断 URL 或标题是否重复。

## 失败处理

说明关键失败、非关键失败、部分成功、无数据时分别怎么做。

## 输出格式

规定最终日志或通知包含哪些字段。
```

任务说明里可以重复 runbook 的关键硬边界，但不要复制整本 runbook。AgentTask 应该引用 `<./runbook.docs>`，并补充该任务的具体执行细节。

## Goodcase

### runbook goodcase

```markdown
# 证书运维运行手册

## 业务背景

本目录用于维护公司域名证书、到期节点和续期动作。目标是在证书到期前发现风险，让 AI 自动整理待处理事项，但续期、替换生产证书和通知客户必须人工确认。

## 核心资源

- <./certificates.table>：证书台账。
- <./renewal_tasks.table>：续期任务。
- <./send_notice.form>：人工确认后发送提醒。

## 主流程

1. 新增证书时，先在 <./certificates.table> 登记域名、证书来源、到期时间、负责人。
2. 系统或 Agent 扫描到 30 天内到期时，在 <./renewal_tasks.table> 生成续期任务。
3. 人工确认后，才允许调用 <./send_notice.form> 发送正式提醒。

## 禁止事项

- 不要自动替换生产证书。
- 不要自动向客户发送提醒。
- 分析证书风险时必须分页读取全部证书，不能只看第一页。
```

为什么好：它描述了业务背景、资源、SOP、人工确认边界和分析规则。无论用户临时问“哪些证书风险最高”，还是移动端回复通知“这个先别续”，Agent 都有上下文。

### AgentTask goodcase

```markdown
## 执行身份

你正在执行证书每日巡检任务。用户不在线，不能向用户提问。先阅读 <./runbook.docs>，并严格遵守人工确认边界。

## 绑定范围

- 运行规则：<./runbook.docs>
- 证书台账：<./certificates.table>
- 续期任务：<./renewal_tasks.table>
- 通知工具：<tool:send_notification>

## 本轮目标

扫描未来 30 天内到期的证书，为缺失续期任务的证书生成待处理任务；对已经逾期的证书通知负责人。

## 时间窗口和幂等

以任务执行时的 Asia/Shanghai 日期为准。对同一 certificate_id 和 due_date，若已存在未关闭续期任务，不再重复创建。

## 执行步骤

1. 阅读 <./runbook.docs>。
2. 分页读取 <./certificates.table> 全部启用证书。
3. 找出 30 天内到期和已逾期证书。
4. 分页读取 <./renewal_tasks.table>，按 certificate_id 去重。
5. 为缺失任务的证书创建续期任务。
6. 对已逾期证书发送通知；普通无变化结果不通知。
7. 输出本轮扫描证书数、新增任务数、逾期数、通知状态。
```

为什么好：它是一个具体任务，有时间窗口、幂等规则、分页、写入目标、通知规则和输出格式。

## Badcase

### runbook badcase

```markdown
# 运行手册

每天看看证书，有问题就处理。可以发通知。
```

问题：没有资源、没有状态、没有 SOP、没有异常处理、没有禁止事项。Agent 遇到移动端回复或临时分析请求时只能猜。

### AgentTask badcase

```markdown
每天帮我搜集新闻，写入表格，有问题问我。
```

问题：无人值守任务不能问用户；没有数据源、主题、去重、分页、入库字段、失败处理和通知规则，极容易重复写入或乱写。

### 资源引用 badcase

```markdown
读取 ./profiles.table，然后写 drafts.table。
```

问题：资源引用不可点击，也不利于工具解析。应该写 `<./profiles.table>` 和 `<./drafts.table>`。

## 检查清单

写 `runbook.docs` 前检查：

- 是否说明业务背景和痛点。
- 是否列出核心资源，并使用 `<./xxx.table>` 资源标记。
- 是否覆盖正常 SOP、异常 SOP、通知规则、禁止事项。
- 是否说明哪些动作可以自动做，哪些必须人工确认。
- 是否写清数据分析必须分页读完。
- 是否避免写某个具体定时任务的细碎 cron 流程。

写 `AgentTask.Message` 前检查：

- 是否第一步要求阅读 `<./runbook.docs>`。
- 是否说明本轮目标、时间窗口和幂等规则。
- 是否列出预期使用工具；需要回显内置工具时，是否使用 `<tool:...>` 标记。
- 是否说明分页读取、去重、写入、更新、通知规则。
- 是否区分执行前缺口快照和执行后剩余缺口。
- 如果单轮上限内没有补齐全部缺口，是否要求写明跳过原因。
- 新增子记录时是否要求绑定上游业务对象，而不是先写无归属记录再补。
- 是否能在用户不在线时自行闭环。
- 是否明确失败处理和无数据处理。
- 是否避免自动执行发布、付款、审批通过等高风险动作。

写 `kageos_manifest.go` 前检查：

- 文件名必须是 `kageos_manifest.go`，不要用 `_init_data.go`。
- 默认文档使用 `packageContext.AddDocs(app.DocManifest{Code: "runbook", ...})`。
- 默认 Agent 任务使用 `packageContext.AddAgentTask(app.AgentTask{...})`。
- 不要给 AgentTask 填 `Policy`，默认就是缺失才创建。
- build/update 后才会把 seed 同步到 Service Tree。
