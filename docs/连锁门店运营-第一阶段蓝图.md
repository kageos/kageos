# 连锁门店运营第一阶段蓝图

> 文档目标：把“连锁门店运营”作为 AI-Agent-OS 第一个重点打穿的垂直方向来拆清楚，明确为什么选它、第一阶段做什么、怎么映射到当前代码、平台能力如何落地、后续如何扩展。  
> 文档定位：不是产品宣传稿，而是 **平台收口完成后用于选型、架构、交付、生成规范和 Agent 上下文的行业蓝图**。  
> 判定原则：第一阶段目标是 **打穿门店运营协同层**，不是替代 POS、ERP、供应链、财务核心系统。

---

## 1. 为什么优先打连锁门店运营

### 1.1 这是一个和平台当前骨架天然同构的领域

AI-Agent-OS 现在最强的不是“深专业引擎”，而是：

- 多层级目录组织
- 统一的 `Form / Table / Chart`
- Widget 协议驱动的动态渲染
- 目录级 Agent 工作台
- 快速承接非标变化

连锁门店运营恰好具备这些特征：

- 组织天然分层：总部 / 区域 / 门店 / 店员 / 督导
- 流程天然协同：巡检、报修、整改、工单、培训、活动执行
- 变化天然频繁：不同品牌、区域、门店、专项活动经常要调流程
- 外围系统天然零散：Excel、群消息、飞书表单、小程序、外包工具并存

换句话说，这个领域不是在逼平台补一个深引擎，而是在放大平台现有优势。

### 1.2 我们要打的是“变化层”和“协同层”

和成熟专业软件相比，平台不应该正面拼：

- POS 核心
- 供应链核心
- 财务结算
- 会员营销引擎
- 价格 / 库存 / 订单核心主系统

第一阶段应该占住的是：

- 总部到区域到门店的运营协同层
- 高频变化的巡检 / 整改 / 异常 / 工单 / 看板
- 过去靠 Excel 和群聊维护的长尾运营流程

### 1.3 对外定位应该怎么讲

不要把自己定义成：

> 一个还不够深的零售行业软件

应该定义成：

> 一个面向连锁门店运营协同层的 AI 原生平台，负责承接变化最快、最碎、最难持续改进的那一层业务。

这个定位能避开和成熟核心系统拼深度，也能发挥平台“改得快、统一、可复制、可被 AI 持续迭代”的优势。

## 2. 第一阶段业务边界

### 2.1 第一阶段只做什么

第一阶段聚焦 5 个系统：

1. 巡检任务
2. 异常上报
3. 整改闭环
4. 门店工单
5. 区域 / 总部运营看板

它们共同覆盖：

- 总部布置任务
- 区域督导执行
- 门店填报和处理
- 问题闭环跟踪
- 管理层看分析结果

### 2.2 第一阶段明确不做什么

以下内容不进入第一阶段主线：

- 收银 / POS 核心
- 商品中心 / 主数据核心
- 进销存核心
- 采购与供应链核心
- 财务结算与对账核心
- 会员 CRM 深引擎
- 深度营销自动化引擎
- 复杂排班 / 薪酬核算

这些能力不是永远不做，而是不该作为平台打穿第一个垂直领域时的主战场。

### 2.3 第一阶段北极星目标

第一阶段不是“把零售做全”，而是让一个连锁品牌能在平台上完整跑通：

- 总部发起任务
- 区域拆解执行
- 门店提交结果
- 异常自动进入闭环
- 整改与工单跟踪到完成
- 看板能按总部 / 区域 / 门店钻取
- Agent 能参与新增页面、改字段、改流程、补文档

## 3. 为什么这个领域最适合 AI-Agent-OS

### 3.1 Service Tree 和组织结构天然贴合

当前平台的 [`service_tree.go`](../core/app-server/model/service_tree.go) 与 `full_code_path` 本质上是在解决“目录组织 + 身份稳定 + 权限继承”的问题。  
连锁门店运营天然存在这种结构：

- 总部
- 区域
- 门店
- 门店内功能模块

这比很多单体业务更适合平台当前的骨架。

### 3.2 `Form / Table / Chart` 足以覆盖主流运营协同场景

这一领域大量功能并不需要新模板：

- `Form`：填报、上报、确认、处理、申请、回执
- `Table`：台账、任务池、问题池、工单池、整改列表
- `Chart`：汇总趋势、完成率、逾期率、区域对比、门店排名

这说明平台不需要为这个领域发明第四种模板，而是用现有协议就能打。

### 3.3 Widget 能承接复杂表单与主从结构

这个领域非常依赖：

- 附件上传
- 人员 / 部门选择
- 多选项与枚举
- 时间字段
- 嵌套表格
- 评分 / 打分
- 进度 / 状态

这些都能直接映射到当前 SDK Widget 和前端动态渲染链：

- 后端定义：[`sdk/agent-app/widget/`](../sdk/agent-app/widget)
- 解码：[`sdk/agent-app/widget/decode.go`](../sdk/agent-app/widget/decode.go)
- 前端注册：[`web/src/architecture/infrastructure/widgetRegistry/`](../web/src/architecture/infrastructure/widgetRegistry)
- 前端组件：[`web/src/architecture/presentation/widgets/`](../web/src/architecture/presentation/widgets)

### 3.4 Agent 工作台能真正参与交付

这个领域变化多，特别适合目录级 Agent：

- 新增一类巡检项
- 调整整改流程
- 新增一个区域看板
- 把某个门店试点流程复制到别的区域
- 生成专项活动执行模块

这类变化如果还得按传统交付节奏排开发，平台优势就浪费了。  
而当前工作台链路：

- [`core/agent-server/service/workspace_chat_service.go`](../core/agent-server/service/workspace_chat_service.go)
- [`core/agent-server/service/tool_registry.go`](../core/agent-server/service/tool_registry.go)

恰好就是为这种“持续演进型系统”准备的。

## 4. 第一阶段平台打法

### 4.1 不替代核心系统，先包住外围协同层

第一阶段的竞争策略不是：

> 替代门店所有软件

而是：

> 把专业软件之外那层最碎、最难改、最需要统一治理的运营协同层吃下来。

典型替代对象其实不是强行业软件，而是：

- Excel 台账
- 飞书 / 企业微信表单
- 微信群协同
- 低代码拼出来的小系统
- 外包做的一堆松散工具

### 4.2 商业价值来自“持续变化承接能力”

客户不一定会为了一个“新平台”付钱，但会为了这几件事付钱：

- 规则改动能快速上线
- 总部和区域口径能统一
- 巡检、异常、整改不再断链
- 数据不再散落在多个工具里
- 一个行业包能快速复制给多个区域 / 子品牌

所以第一阶段卖点应该是：

- 行业模板
- 快速落地
- 持续迭代
- AI 辅助运维与开发

不是“平台概念”本身。

## 5. 服务树蓝图

### 5.1 推荐的顶层目录结构

建议第一阶段先用一个清晰、少分叉的目录结构：

```text
总部运营
├── 基础资料
├── 巡检管理
├── 异常与整改
├── 门店工单
├── 运营看板
├── 知识库
└── 工作台
```

如果需要按区域或门店挂载，可以继续扩成：

```text
总部运营
├── 区域A
│   ├── 门店1
│   └── 门店2
├── 区域B
└── 公共模板
```

### 5.2 服务树和代码包的映射原则

服务树不是纯 UI 菜单，应该和业务包结构尽量同构：

- 一个目录节点尽量对应一个 package
- 一个函数节点尽量对应一个具体业务系统
- 公共能力和具体门店能力分层放置

建议的代码包示意：

```text
api/
└── store_ops/
    ├── base/
    ├── inspection/
    ├── issue/
    ├── rectification/
    ├── workorder/
    └── dashboard/
```

这样做的好处是：

- `full_code_path` 稳定
- Agent 能围绕目录工作
- 后续复制一个行业包时结构清楚
- 区域 / 门店定制更容易做边界控制

### 5.3 `full_code_path` 在这个领域里的意义

在连锁门店场景里，`full_code_path` 不只是技术标识，还能成为：

- 权限定位键
- 文档归属键
- 工作台上下文键
- 模板复制与发布键
- 问题追踪与日志关联键

所以这个领域越往下打，越应该坚持用 `full_code_path` 做单一身份。

## 6. 五个核心系统蓝图

## 6.1 巡检任务

### 业务目标

- 总部定义巡检计划
- 区域 / 督导领取或下发任务
- 门店按检查项填报
- 结果进入问题池和看板

### 推荐模板组合

- `Table`：巡检任务台账
- `Form`：巡检提交表单
- `Chart`：巡检完成率 / 得分趋势

### 关键字段建议

- 任务编号
- 巡检主题
- 巡检类型
- 适用区域
- 适用门店
- 截止时间
- 负责人
- 状态
- 得分
- 明细检查项
- 附件

### 关键 Widget

- `select`：巡检类型、状态
- `timestamp`：截止时间、巡检时间
- `user` / `department`：负责人、区域
- `files`：现场照片
- `table`：检查项明细
- `rate` / `number`：评分

### 技术映射

- SDK 定义 Request / Response struct
- 用 `widget` tag 标巡检项、附件、门店、督导等字段
- 通过 `OnTableAddRow`、`OnTableUpdateRows` 承接任务新增与批量更新
- 通过 `ChartTemplate` 汇总任务完成率、异常率

## 6.2 异常上报

### 业务目标

- 门店或督导快速上报问题
- 自动分类、自动归口
- 进入后续整改与工单

### 推荐模板组合

- `Form`：异常上报
- `Table`：异常问题池
- `Chart`：异常类别分布 / 高频门店

### 关键字段建议

- 异常编号
- 异常类别
- 来源任务
- 所属门店
- 上报人
- 严重等级
- 问题描述
- 现场图片
- 是否需整改
- 是否转工单

### 关键 Widget

- `select`：异常类别、严重等级
- `files`：现场照片、视频
- `text_area`：问题描述
- `link`：关联巡检任务
- `switch`：是否转整改 / 是否转工单

### 技术映射

- `FormTemplate` 负责上报入口
- 提交成功后进入异常池
- 可通过 callback 在提交后自动创建整改记录或工单记录

## 6.3 整改闭环

### 业务目标

- 对异常发起整改
- 指定责任人、截止时间
- 跟踪整改过程、复检结果
- 最终闭环

### 推荐模板组合

- `Table`：整改任务池
- `Form`：整改反馈 / 复检确认
- `Chart`：逾期整改率 / 闭环率

### 关键字段建议

- 整改单号
- 来源异常
- 责任区域 / 责任门店
- 责任人
- 截止时间
- 整改动作
- 反馈说明
- 复检结果
- 闭环状态

### 关键 Widget

- `user`：责任人、复检人
- `timestamp`：截止时间、反馈时间、复检时间
- `progress`：整改进度
- `files`：整改前后照片
- `radio` / `select`：复检结果

### 技术映射

- `Table` 作为整改主台账
- 用状态机式字段控制流程
- 回调中处理“提交整改反馈 -> 更新状态 -> 触发复检”

## 6.4 门店工单

### 业务目标

- 接住门店现场的维修 / 支持 / 协调需求
- 让总部、区域、门店之间形成标准流转
- 打通异常到工单的衔接

### 推荐模板组合

- `Table`：工单池
- `Form`：工单提交 / 处理回执
- `Chart`：工单处理时效 / 类型占比

### 关键字段建议

- 工单编号
- 工单类型
- 来源
- 门店
- 提单人
- 指派对象
- SLA 截止时间
- 当前状态
- 处理记录
- 关闭原因

### 关键 Widget

- `select`：工单类型、状态
- `user` / `department`：指派对象
- `table`：处理记录
- `files`：过程附件

### 技术映射

- 工单列表天然适合 `TableTemplate`
- 处理记录可用嵌套 `table/form`
- 看板可按工单类型、区域、门店维度汇总

## 6.5 区域 / 总部运营看板

### 业务目标

- 总部看整体执行质量
- 区域看门店差异
- 门店看本店待处理项

### 推荐模板组合

- `Chart`：总览图表
- `Table`：明细钻取

### 关键指标建议

- 巡检完成率
- 异常总数与类型分布
- 整改闭环率
- 逾期任务数
- 工单处理时长
- 区域排名
- 门店排名

### 技术映射

- `ChartTemplate` 提供图表视图
- 通过标准 API 拉取统计结果
- 明细钻取仍落回 `Table`

## 7. 权限与角色蓝图

### 7.1 第一阶段建议角色

建议先收敛成 5 类角色：

1. 总部运营管理员
2. 区域负责人
3. 区域督导
4. 门店店长
5. 门店店员

### 7.2 权限原则

这一阶段最重要的是“层级继承 + 范围收缩”，而不是做特别复杂的权限矩阵。

建议原则：

- 总部能看全局、定义模板、发布任务
- 区域只能看所属区域和下属门店
- 门店只能看本店数据
- 督导可以被授权跨若干门店巡检

### 7.3 平台映射

这里要尽量复用平台现有主线：

- 用户 / 部门来自 [`core/hr-server/`](../core/hr-server)
- 权限绑定到 `service_tree` / `full_code_path`
- Widget 字段级读写控制继续沿用现有 `permission` tag 能力

这样后续无论是做更多目录隔离，还是做区域模板复制，都不会偏离平台主线。

## 8. Widget 设计建议

### 8.1 第一阶段优先复用现有 Widget

优先用现有类型吃掉 80% 场景，不要先发明新 Widget：

- `input`
- `text_area`
- `select`
- `multiselect`
- `timestamp`
- `user`
- `department`
- `files`
- `table`
- `form`
- `number`
- `rate`
- `progress`

### 8.2 第一阶段可能最先补的 Widget 能力

如果连锁门店场景真要补扩展，建议优先看这几类：

1. 更友好的附件预览
2. 门店 / 区域专用选择器
3. 多级检查项录入
4. 更清晰的状态标签与进度展示

注意：优先做成现有 Widget 的增强，而不是新增第四套渲染协议。

### 8.3 Widget 扩展路径

若未来真要新增行业 Widget，建议坚持当前端到端扩展链：

1. SDK 增加类型
2. `decode.go` 输出 schema
3. 前端注册组件
4. 补 initializer / extractor
5. 检查 `edit / response / table-cell / detail / search`

这个领域的需求变化快，更要避免在组件层堆临时特判。

## 9. Agent 工作台在这个领域里的角色

### 9.1 工作台不是附加聊天框，而是行业交付加速器

这个垂直领域特别适合把工作台真正用起来：

- 新增一个专项巡检模块
- 调整某个区域的流程字段
- 生成总部运营周报看板
- 为试点门店复制一套新流程
- 自动补业务文档和 SOP

### 9.2 第一阶段建议给 Agent 的固定上下文

建议在这个领域里，把以下文档和约束逐步固化到 Prompt / 知识库：

- 连锁门店运营蓝图
- 字段命名规范
- 五个核心系统的标准数据结构
- 角色与权限边界
- 哪些能力禁止越界到核心系统

### 9.3 理想状态

理想状态不是 Agent 帮你随便生成点代码，而是：

- 能根据当前目录理解这是巡检、工单还是整改
- 能在该目录下补函数、补文档、补看板
- 能沿用统一字段和 Widget 规范
- 能减少交付和迭代的人力成本

## 10. 代码落地映射

### 10.1 后端建议的包结构

建议新行业样板尽量贴近 SDK 注册模式：

```text
api/store_ops/
├── base/
├── inspection/
├── issue/
├── rectification/
├── workorder/
└── dashboard/
```

每个目录内部尽量保持：

- 一个目录负责一个稳定业务域
- Table / Form / Chart 拆清楚
- 公共 struct 和 callback 放在同域内聚合

### 10.2 前端建议关注的真实落点

如果第一阶段开始真做这个行业包，前端优先关注这些目录：

- [`web/src/architecture/presentation/views/`](../web/src/architecture/presentation/views)
- [`web/src/architecture/presentation/widgets/`](../web/src/architecture/presentation/widgets)
- [`web/src/architecture/infrastructure/widgetRegistry/`](../web/src/architecture/infrastructure/widgetRegistry)
- [`web/src/core/stores-v2/extractors/`](../web/src/core/stores-v2/extractors)

原因很简单：这个领域是否顺手，最终会体现在表单录入、台账操作、明细抽屉、附件展示、图表钻取这些体验上。

### 10.3 后端平台主链要重点验证的地方

这个行业包一旦开始落，会强依赖：

- `service_tree` 的稳定性
- `full_code_path` 的一致性
- 标准 `table/form/chart` API
- 运行时编译和启动
- Agent 工作台读写代码与构建

也就是说，这个行业本身就是你们“稳基本盘”的最好压力测试场。

---

## 11. 未来扩展蓝图

### 11.1 第二阶段可扩的方向

当第一阶段跑顺后，可以继续向外扩：

- 培训与考核
- 活动执行追踪
- 门店开闭店检查
- 陈列 / 物料管理
- 门店资产台账
- 供应商协同
- 运营知识库与 SOP

### 11.2 什么时候再往深处吃

只有满足以下条件，再考虑向更深系统延伸：

- 行业包复用度已经足够高
- 五个核心系统已经稳定
- 平台协议层没有被行业特判污染
- 客户真的有强牵引，而不是“顺手帮忙做一下”

### 11.3 不要急着碰的深水区

即便第二阶段开始扩，也仍要谨慎对待：

- POS
- 商品 / 库存 / 订单核心
- 深 CRM 营销
- 财务对账
- 复杂供应链引擎

这些能力更像外围生态对接对象，而不是第一批必须内建的主系统。

## 12. 验收标准

### 12.1 业务验收

如果第一阶段做对了，至少应该满足：

1. 总部能配置并下发巡检任务
2. 区域 / 门店能完成上报和处理
3. 异常能自动进入整改或工单
4. 看板能按总部 / 区域 / 门店查看
5. 一个试点品牌跑通后，第二个品牌能复用大部分结构

### 12.2 平台验收

如果第一阶段真起到了“验证平台”的作用，还应该满足：

1. 新增一个模块时不需要绕开 `Form / Table / Chart`
2. 新增一个字段时不需要前后端各写一套协议
3. 新增一个看板时标准 API 链路稳定
4. Agent 能在目录级上下文里完成增量修改
5. 不需要为了行业需求到处打平台特判

### 12.3 商业验收

从业务角度更现实的判断是：

1. 客户愿意为“快速上线 + 持续改”付钱
2. 第二个客户不再像重做一套系统
3. 交付周期明显短于传统定制
4. 平台能开始形成行业模板，而不是一次性交付

---

## 13. 一句话总结

连锁门店运营适合作为 AI-Agent-OS 第一个重点垂直方向，不是因为它最“专业”，而是因为它最能放大平台当前的真实优势：

> 多层级组织、快速变化流程、统一 Widget 协议、标准 `Form / Table / Chart`、目录级 Agent 工作台、以及可复制的行业模板能力。

第一阶段只要把巡检、异常、整改、工单、看板这 5 个系统打通，平台就不再只是“能生成系统”，而会开始成为一个 **能持续承接连锁运营变化的 AI 原生行业平台**。
