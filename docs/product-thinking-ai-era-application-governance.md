## 给 AI 的快速上下文

如果把这份文档发给 AI，可以先让 AI 记住下面这些事实：

- 项目名称是 Kageos，正文、UI、官网、SDK 文档和对外材料都必须写作 Kageos；Go 包名、路径名保留小写 `kageos`，环境变量和配置键可以保留全大写 `KAGEOS_*`。
- Kageos 是一个 source-available、可自托管、也提供托管 SaaS 的业务应用目录运行时、AI 工作台、目录治理平台和目录分发平台。
- Kageos 的核心不是“用 AI 便宜地生成一个应用”。这是最低价叙事，容易被卷进普通 app builder。Kageos 的核心是把成熟业务能力做成开箱即用的目录：用户可以从 Hub 安装、私有运行、按需改造、复制派生，再把稳定能力发布回生态。
- 当前阶段产品与工程重点是 namespace 场景包生态：把更多可运行、可试用、可安装、可派生、可发布的场景目录做扎实。不要新增平台横切能力；已有 Service Tree、权限、审计、日志、消息、定时和运行时能力作为场景包底座复用。
- Kageos Hub 正在建设中。Hub 上架的不是静态模板，也不是 prompt 或代码片段，而是一个个开箱即用的可运行目录。用户应该先看到能解决问题的目录，再决定安装到自己的私有空间。
- 用户既可以消费目录，也可以创造目录。一个目录可以从 Hub 安装而来，也可以由用户在工作区里从零创建、用 AI 改造、复制派生，最后发布回 Hub，成为别人可安装的成熟能力。
- Kageos 的长期护城河不是单个模板，而是“挂树即治理”：能力只要进入 Service Tree，就自动获得权限、审计、版本、日志、AI 理解、跨应用调用等横切能力；定时和消息通知已接回主线，workflow、评论、通用审批等仍是未上线路线储备。
- Kageos 目录和函数不仅能给人使用，也能在 AI 工作台里被直接调用。例如工作台可以通过 run form submit 这类工具直接执行 Form 背后的函数。一个能力进入 Kageos 后，同时是人可用的轻应用、AI 可调用的函数节点、平台可治理的资源。
- Kageos 和 Agent Skills 不是同一层。Skills 更像给 AI 的说明包/工具包；Kageos 目录是可运行、可试用、可私有安装、可持久化数据、可被人和 AI 同时使用、可被平台治理的业务能力单元。

一句话说：

> Kageos is a ready-to-run business directory network: install proven capabilities from Hub, customize them in your private workspace, create new ones, and publish stable directories back to the ecosystem.

## 叙事优先级

对外叙事必须按下面的顺序展开：

1. Hub 开箱即用：用户先看到已经能跑的业务目录，而不是先面对空白 prompt。
2. 私有安装和运行：有价值的目录可以安装到自己的空间，用自己的数据、权限、算力和团队流程长期运行。
3. 创造、派生和发布：用户可以自己创建目录，用 AI 修改目录，复制派生目录，并把稳定能力发布回 Hub。
4. 挂树即治理：目录进入 Service Tree 后自动获得权限、审计、日志、版本、消息、定时和 AI 可调用能力。
5. AI 生成应用：这是降低创造门槛的手段，不是产品定位。不要把 Kageos 讲成“更便宜的 AI app builder”。

## 项目形态

Kageos 由三种形态组成：

1. Source-available 核心

Kageos 当前核心采用 BSL 1.1，是 source-available 项目，不是 OSI open source。用户可以自己本地部署，也可以部署到团队服务器或企业内网；第三方不能直接把核心做成商业 SaaS、MSP 托管、白标、OEM、嵌入、改名转售或竞品化产品/服务提供给外部用户。各版本发布四年后转 Apache-2.0。核心版本提供轻应用运行时、Service Tree、标准资源、权限、审计、运行日志、AI 工作台、目录安装和能力治理等基础能力。

源码可见和可自托管的价值不只是免费，而是信任、可控和可扩展。用户可以用自己的数据、自己的机器、自己的算力运行目录，适合处理图片、视频、文档、表格、内部文件、私有数据和企业内网任务。

2. 托管 SaaS

Kageos 也会提供官方托管版本。托管版本的核心价值是降低首次使用成本：用户不用自己部署，不用处理环境、下载、依赖和服务器配置，打开即可试用目录，安装到私有空间也可以很快完成。

托管 SaaS 是更适合商业化的形态。用户为省时间、省部署、省运维、自动更新、备份、私有空间、团队权限和稳定运行付费。

3. Kageos Hub

Kageos Hub 是开箱即用的目录分发平台。Hub 上的每个目录都应该尽量是可试用、可安装、可复制、可派生、可再次发布的。

目录不是普通模板，也不是一段代码片段。一个目录可以包含表单、表格、文档、函数、页面、数据结构、运行逻辑、AI 提示词、能力描述和权限边界。用户看到一个目录有用，可以先在线试用，再安装到自己的空间里长期使用；如果改造出了更稳定、更通用的版本，也可以发布回 Hub。

## 用户怎么用

Kageos 的理想使用链路是：

1. 用户进入 Kageos Hub，浏览具体场景目录，而不是先面对一个空白开发平台或空白 prompt。
2. 用户点击某个目录的试用入口，直接在线体验已经部署好的试用版本。
3. 用户确认目录有价值后，点击安装到自己的私有空间。
4. 在托管 SaaS 中，私有安装预计 1 分钟内完成；在自托管环境中，用户可以把目录安装到自己的本地或内网实例。
5. 安装后，用户可以用自己的数据运行目录，也可以复制、派生、修改字段、改逻辑、加功能。
6. 如果需要个性化，用户可以让 Kageos 的 AI 工作台基于目录上下文进行修改，而不是从零生成一个不可控应用。
7. 如果用户自己创造了新的稳定目录，也可以发布到 Hub，变成别人开箱即用的能力。
8. 目录进入用户空间后，会自动进入平台治理体系，获得权限、审计、日志、版本、AI 理解和跨应用调用能力。

这个链路的核心是：

> 先试用，再安装；先消费成熟目录，再创造和发布自己的目录。

这和普通 AI 生成应用有明显差异。普通 AI app builder 往往从空白 prompt 开始，容易生成半成品，也容易制造新的孤岛。Kageos 更强调从已经能运行、已经被组织好的目录开始，让用户先获得确定价值，再用 AI 改造；当用户创造出新能力时，也能把它沉淀为可安装、可治理、可分发的目录资产。

## 和 Agent Skills 的区别

Kageos 需要和 Claude/OpenAI/Codex 这类 Agent Skills 区分开。二者都可以分发能力，但它们不是同一层产品。

### 表面差异

Agent Skills 通常是给 AI 的能力包。它可以包含说明文档、脚本、资源和调用约定，让 AI 在合适的时候知道"应该怎么做某类任务"。Skills 的优势是轻、标准化、传播快，适合让 AI 学会一类重复任务。

但从业务软件角度看，单个 skill 很容易变成"一锤子买卖"：它能帮 AI 完成一次任务，却不天然形成一个长期运行的业务空间，也不天然沉淀成可被其他应用发现、组合、编排和治理的工具网络。skill 可以作为编排里的一个节点，但 skill 本身通常不是完整的编排平台。

Kageos 的目录和函数更像平台里的真实业务能力节点。一个 Kageos 目录可以包含 UI、Form、Table、Chart、Docs、函数、数据结构、运行逻辑、权限边界、操作记录和 AI 上下文。它不仅能被 AI 理解，还能被人直接打开使用，也能被 AI 工作台直接调用。

例如，Kageos 的 Form 不是普通页面表单。它背后有结构化 schema 和可执行函数。人可以打开页面填写表单提交，AI 也可以在工作台里通过 run form submit 直接提交这个 Form，从而执行背后的函数。这样同一个能力不需要做两套入口：一套给人用，一套给 AI 用。

可以这样理解：

| 维度 | Agent Skills | Kageos 目录/函数 |
| --- | --- | --- |
| 核心对象 | 给 AI 的说明包、脚本包或工具包 | 挂在 Service Tree 上的可运行业务能力节点 |
| 使用入口 | AI 在聊天或 Agent 环境中自动调用 | 人可以点 UI 用，AI 可以在工作台直接按 schema 调用 |
| UI | 通常依赖宿主 AI 产品，没有完整业务 UI | 可以有 Form、Table、Chart、Docs、页面和工作台 |
| 执行 | 多依赖宿主环境和 skill 内脚本 | 由 Kageos 运行时执行，具备函数、数据和调用记录 |
| 数据 | 往往偏临时上下文或文件处理 | 可以有持久化 DB、提交记录、表格数据和业务状态 |
| 治理 | 主要依赖宿主平台 | 挂树后获得权限、审计、日志、版本、Trace 和跨应用调用 |
| 分发 | 安装 skill 给 AI 使用 | Hub 在线试用，安装到私有空间，人和 AI 都能用 |
| 商业化 | skill 本身容易变成免费能力包 | 可以围绕托管空间、私有安装、团队协作、运行额度和高级目录收费 |

因此，Kageos 不应该和 Skills 比谁更轻。Skills 更适合成为 AI 的技能说明层；Kageos 更适合承载真实业务运行。一个更准确的判断是：

> Skill teaches an AI how to do a task. Kageos directory gives both humans and AI a governed runtime for that task.

或者中文表达：

> Skills 让 AI 学会一类任务；Kageos 把任务变成一个人能用、AI 能调、平台能治理的目录能力。

### 根本差异：确定性 vs 不确定性

表面差异之上，目录和 Skills 有一个更根本的分野：**确定性**。

Skills 的底层依赖是 AI 模型。模型的输出不确定、成本不确定、存续不确定：

- 模型能力参差不齐，同一个 Skill 在 GPT-4 和 Claude 上行为可能完全不同
- 每次 Skill 执行都消耗 token，成本跟调用量线性增长，没有规模效应
- Skills 绑死在 AI 模型上，模型厂商改 API、涨价或关停，下游全部受影响
- 模型理解力是编排的瓶颈——Skill A 的自然语言输出到 Skill B 的结构化输入，靠 AI 理解力做类型转换，每一步都可能出错

目录的底层依赖是代码和运行时。接口确定、成本确定、存续确定：

- 每个函数有明确的 Go 结构体签名，输入输出是代码定义的，不是靠模型理解力猜测的
- 代码在容器中执行，固定成本，不随 AI 模型调用量增长
- 目录跟 AI 模型无关——今天用 GPT-4 当 agent，明天换 Claude，后天换国产模型，目录里的代码、数据、权限、日志一个字都不用改
- 编排靠标准接口确定性连接，不需要 AI 理解力做类型转换

企业决策的底层逻辑不是"哪个功能更强"，是"哪个我能依赖"。一个 CIO 选型时想的是：这东西会不会明天就挂了？换个人来能不能接着用？模型升级了会不会全崩？一年下来要花多少钱？对这四个问题，Skills 的答案全是"不确定"，目录的答案全是"确定"。

| 维度 | Skills 生态 | Kageos 目录 |
| --- | --- | --- |
| 核心依赖 | AI 模型 | 代码 + 运行时 |
| 确定性 | 不确定（依赖模型理解力） | 确定（标准入参出参） |
| 成本模型 | token 随调用线性增长 | 代码执行，固定成本 |
| 模型切换 | 需要重写 prompt | 换个 agent 就行，目录不动 |
| 没有 AI | 完全不能工作 | 人在页面上照样用 |
| 编排 | 靠 AI 理解力拼接 | 靠标准接口确定性连接 |
| 数据积累 | 无状态 | 有状态，可审计，可查询 |
| 企业信任度 | 低（不确定性太高） | 高（确定性做底座） |

### AI 只是目录的一个用户

这个认知彻底翻转了人和 AI 的关系：

```
Skills 的世界观：人 → AI → 工具
                  （AI 是中间层，人必须通过 AI）

目录的世界观：人 ←→ 目录 ←→ AI
              （人和 AI 是平等的用户，目录是共享的基础设施）
```

在 Skills 的世界里，AI 是瓶颈——AI 挂了，人啥也干不了。AI 理解错了，结果就错了。AI 换了个模型，行为就变了。

在目录的世界里，AI 是增强——AI 在的时候帮你自动化，AI 不在的时候你自己点页面，结果一样。AI 让你更快，但不决定你能不能做。

这对企业意味着：他可以先用起来，再决定要不要接 AI。他不用赌"AI 能力会不会继续进步"，因为他不管 AI 进不进步，目录都在那。这也意味着企业不会因为模型厂商的任何变动（涨价、关停、API 变更）而失去自己的业务能力。

### 标准入参出参：确定性编排的基础

Skills 生态的编排为什么走不通？因为没有契约。

```
Skill A 输出："今天天气不错，温度25度"
Skill B 期望输入：{ temperature: number, condition: string }
```

A 的输出是自然语言，B 的输入是结构化数据。谁来翻译？AI。AI 翻译准不准？看运气。这就是为什么现在的 multi-agent 编排又慢又贵又不稳——每一步都在靠模型理解力做类型转换。

Kageos 的目录函数有明确的结构体签名：

```go
func SearchArticles(ctx *app.Context, req *SearchRequest) (*SearchResponse, error)

type SearchRequest struct {
    Keyword  string `json:"keyword"`
    PageSize int    `json:"page_size"`
}

type SearchResponse struct {
    Articles []Article `json:"articles"`
    Total    int       `json:"total"`
}
```

这不是 AI 猜的，是代码定义的。编排的时候不需要模型理解力来做类型转换——直接接就行。SearchArticles 的输出 Articles 可以直接映射到 SendMarkdown 的输入 Content，这个映射是确定性的、可验证的、不需要 token 的。

Agent 任务的跨目录调用已经验证了这一点：热点情报推送每天执行 32 次（每 15 分钟一次），连续运行超过 486 次执行 0 失败，跨了 3 个目录（hot_news + weixin + wecom），调了 4 个函数（web_search + search_articles + read_article + send_markdown），每一步的输入输出都是确定的，不是靠模型理解力拼凑的。

### 目录吞噬 Skills

Kageos 不需要跟 Skills 对着干。市场上已经有大量的 Skills 生态——OpenAI、Anthropic、各种 Agent 框架。正确的做法是：**目录是核心，但目录可以暴露为 Skill。**

每个目录天然可以对外表现为一个 Skill——AI 看到的是函数签名 + 描述，背后跑的是完整的目录运行时。这样：

- AI 用 Skill 的方式调用目录 → 低门槛，跟生态兼容
- 调用进来的东西有状态、有治理、有数据、可组合 → 高天花板
- 用户不需要选"用 Skill 还是用目录" → 目录就是更强的 Skill

这不是 Skills vs 目录，是目录吞噬 Skills。这也跟"挂树即治理"完全一致：能力进目录就自动获得一切——包括对 AI 的 Skill 化暴露。

### 确定性做底座，不确定性做加速

把以上所有论点收拢为一句话：

> 目录是确定性的基础设施，AI 是不确定性的增强层。确定性做底座，不确定性做加速，这是唯一能在生产环境站住的架构。

反过来——不确定性做底座——就是现在 Skills 生态的困境：GPT-4 能跑的 Skill 换了 GPT-4o 可能跑不了，换了 Claude 全部重写 prompt，模型厂商改个 API 下游全部崩溃。这不是"目前还不够成熟"的问题，是架构上的根本缺陷。

别人的思路是让 AI 更强，让 AI 能做更多事。Kageos 的思路是让能力更确定，让 AI 和人都能可靠地使用它。前者赌的是 AI 会持续进步，后者赌的是确定性永远是刚需。哪个赌注更安全，一目了然。

这也是 Kageos 面向 AI 时代的核心价值之一：

> Every Kageos directory is both human-usable and AI-callable.

进一步看，未来软件会越来越走向“编排为主，编程为辅”。传统软件经常把大量功能写死在一个应用里；AI app builder 又容易不断生成新的孤立应用。Kageos 更希望把软件拆成像乐高积木一样的原子能力：每个能力都足够小、可解释、可调用、可观察、可治理，也能被人、AI 和其他能力编排。

这意味着，未来的应用不一定总是从零编程出来，而可能是从已有能力网络里组合出来：

- Form 负责收集和提交结构化输入。
- Table 负责承载和查询业务数据。
- Function 负责执行一个明确动作。
- Chart 负责表达数据洞察。
- Docs 负责沉淀说明、上下文和知识。
- Workflow 负责把多个能力按条件、顺序、时间和事件编排起来。
- AI 工作台负责理解目录上下文，并在需要时调用、修改或组合这些能力。

在这种模式下，编程仍然重要，但更多用于创造新的原子能力；日常业务变化更多通过复制、派生、配置、连接和编排完成。Kageos 的目标不是让每个需求都重新生成一个新应用，而是让每个能力都成为可解释、可复用、可编排的节点。

可以这样表达：

> 未来软件不是一个个封闭应用，而是一张可解释、可调用、可编排的能力网络。

或者：

> Kageos turns apps into composable atoms: human-usable, AI-callable, and ready for future workflow orchestration.

## Hub 的转化逻辑

Kageos Hub 的关键不是让用户“买一个模板”，而是让用户快速经历一次完整价值闭环：

- 在线试用：用户不需要安装就能看到目录能做什么。
- 私有安装：用户觉得有用后，把目录安装到自己的空间。
- 私有数据：用户在自己的空间里处理自己的文件、表格、业务数据和团队流程。
- 持续使用：目录不只是一次性工具，而可以沉淀为个人或团队的长期工作台。
- 复制派生：用户可以从一个目录复制出自己的版本，低成本做个性化。
- 横切治理：目录自动获得权限、审计、日志、版本和 AI 修改能力。

因此，Hub 的增长不应该只靠“模板数量”，而应该靠一批能被明确搜索、明确试用、明确解决问题的目录。每个目录都可以成为一个独立落地页和获客入口。

适合早期优先做的目录包括：

- 文档转换、PDF 处理、OCR、摘要、批量重命名、格式转换。
- 图片压缩、格式转换、批量水印、尺寸裁剪、素材整理。
- 视频处理、音频提取、字幕生成、转写、切片和内容复用。
- CSV/Excel 清洗、去重、合并、报表生成、数据检查。
- 轻量工单、客户反馈、Bug 收集、内容日历、审批记录、团队任务跟进。
- 面向 freelancer、agency、indie hacker、小团队的客户管理、交付管理和内容运营目录。

这些目录的共同点是：用户能立刻理解，不需要复杂销售，不需要先相信 Kageos 的宏大叙事，只要点击试用就能感受到价值。

## 当前计划

产品策略上，不应该一开始就把 Kageos 讲成一个很大的企业平台，而应该先用具体目录获客：

> Try a ready-to-run directory online. Install it privately when it helps.

早期更应该卖“具体问题的解决方案”，而不是卖“简单管理系统”这个泛概念。简单管理系统本身不一定有吸引力，但具体场景有吸引力，例如 client portal、ticket tracker、PDF toolkit、image batch processor、content calendar、CSV cleaner、invoice extractor 等。

商业模式可以分层：

- 免费试用：Hub 上的目录可以在线试用，降低信任成本和体验门槛。
- 免费/source-available 自托管：给开发者、隐私敏感用户和企业内网用户使用，扩大影响力。
- 托管个人版：为个人和小团队提供私有空间、快速安装、自动更新和稳定运行。
- 托管团队版：提供多人协作、权限、私有目录、更多存储、更多运行额度和团队管理。
- 高级目录包：对高质量场景目录、行业目录、自动化包和生产力包收费。
- 未来企业版：提供私有 Hub、SSO、审计增强、内网部署支持、组织架构、审批流和 SLA。

早期赚钱的重点不应该是单卖一次性目录包，而应该是托管空间、私有安装、持续使用、团队协作、自动更新、运行额度和高质量目录包。

## 一句话判断

AI 会让企业内部应用的生产成本快速下降，但也会让应用数量、数据孤岛和智能孤岛一起爆炸。Kageos 要解决的不是“如何再多生成一个应用”，而是让企业可以放心安装、创造、复制、派生、发布和运行大量业务目录，同时仍然保持可理解、可治理、可复用。

Kageos 是一个品牌，不再使用“新 OS”的叙事。它更准确的方向是：AI 时代的开箱即用业务目录网络、私有运行时和目录治理平台。

## 背景观察

在大型企业内部 IT、运营开发和研发效能场景里，系统数量通常很多，但系统之间往往各自为政。不同组织建设自己的内部工具，权限逻辑、页面交互、数据模型、接口契约和发布方式都不统一。

这会带来一个很现实的问题：企业拥有了很多软件，但软件整体并没有变得更容易使用。一个员工可能只想完成一个很小的动作，却需要理解一个庞大系统的导航、权限、配置和隐藏规则。很多时候，学习如何使用软件的成本，已经超过了开发软件本身的成本。

当一个权限入口复杂到需要多人开会才能找到时，问题不只是“功能没做好”，而是软件形态本身出了问题。

## 旧范式的问题

传统企业软件常常试图用一个全家桶满足所有人的需求。为了覆盖 A 部门、B 部门、C 部门的差异化诉求，系统不断加功能、加配置、加页面、加兼容逻辑，最后变成一个巨大而笨重的应用。

这个模式有几个典型后果：

- 每个用户只使用系统的一小部分，却被迫理解整个系统。
- 组织之间的系统无法自然交互，形成数据孤岛。
- 每个系统的权限、数据、接口、UI 和运维方式都不一样。
- 人很难理解这些系统，AI 也很难理解这些系统。
- 系统越成熟，越像黑盒，越难被改造。

在这个范式下，做加法很容易，做减法很难。功能不断被塞进同一个应用，短期看满足了需求，长期看会把复杂度转嫁给所有用户和维护者。

## AI 带来的新问题

AI 工具降低了应用开发成本。未来，一个员工、一个小团队、一个业务组织，都可以很快生成自己的内部工具。

这件事本身是好事，但它会带来新的复杂度：

- 应用数量会快速膨胀。
- 每个应用可能都有自己的展示逻辑和交互习惯。
- 每个应用可能都有自己的数据结构和权限模型。
- 每个应用都需要单独接入 AI、日志、发布、监控和排障能力。
- 企业会从“没有足够的软件”走向“软件太多，不知道该用哪个”。

也就是说，AI 提升了生产速度，但如果没有治理层，它也会制造新的混乱。过去的问题是数据孤岛，AI 时代还会出现智能孤岛：每个应用都像一个黑盒，AI 无法统一理解、调用、修改和组合它们。

## Kageos 的核心假设

Kageos 的核心假设是：未来企业不应该依赖少数巨大的全家桶应用，而应该拥有大量小而清晰、可复制、可派生、可治理的轻应用。

这些轻应用应该像目录一样被组织：

- 可以被浏览和搜索。
- 可以被复制和派生。
- 可以保留来源关系和变更差异。
- 可以用统一的 Form、Table、Chart、Docs 等形态承载。
- 可以用统一的权限、运行时、日志、版本和发布机制管理。
- 可以被人理解，也可以被 AI 理解。

Kageos 不应该只是帮助企业“多造应用”，而是帮助企业在应用大量增加之后，仍然知道它们在哪里、是什么、怎么用、谁能用、改了什么、出了问题怎么排查、能不能复用。

## 挂树即治理：横切能力的平台复利

Kageos 的 Service Tree 不只是一个展示目录，而是企业轻应用的治理锚点。一个能力只要挂到树上，就不再是孤立的代码、页面或接口，而会自然进入平台的治理体系。

这意味着，每个新应用、每个新函数、每个新文档和每个新能力包，都可以直接获得平台提供的横切能力，而不是由业务应用重复造轮子。

这些横切能力包括：

- 权限：基于资源路径的 Owner、Admin、Member、Viewer 等角色和 read、write、update、delete、admin、owner 等权限点。
- 权限继承：目录天然具有层级关系，子节点可以复用父级授权语义，避免每个应用单独设计权限模型。
- 操作记录：表格新增、更新、删除，表单提交，目录/函数/文档变更，权限授予和移除，都可以进入统一审计。
- 版本与 diff：应用和能力变更可以沉淀为可追踪的版本历史，而不是散落在各个系统内部。
- 运行状态与日志：应用运行、调用、耗时、成功失败、Trace 等信息可以被平台统一观察。
- 搜索与发现：能力挂在树上后，人可以通过目录和搜索找到它，AI 也可以通过结构化上下文理解它。
- 跨应用调用：树上的应用可以按目录路径发现和调用其他目录里的能力，调用链里的登录态、用户身份、租户、来源和 Trace 由平台传递，业务应用不需要各自处理登录、鉴权和上下文适配。
- AI 工作台：AI 不需要面对一堆黑盒系统，而是面对可读的目录、代码、文档、接口、权限和操作历史。
- 复用与分发：能力可以从树上导出为能力包；Hub 安装、验证、定价和分发链路属于建设中/商业路线，不是当前主线完整能力。

这就是 Kageos 的一本万利之处：平台每补强一个横切能力，所有挂在树上的轻应用都会受益。传统内部系统里，每个团队都要分别实现权限、日志、搜索、AI 接入、发布、排障和治理；在 Kageos 里，这些能力应该由平台统一提供，业务应用只专注自己的业务逻辑。

所以 Kageos 的树不是“文件夹 UI”，而是轻应用的平台协议。挂上树，才意味着这个能力进入了企业软件治理网络。

更重要的是，树让应用之间不再是彼此隔离的黑盒。一个工单应用可以调用另一个目录下的通知能力、文件处理能力或数据查询能力，而不用重新处理对方系统的登录态、账号体系、权限校验和调用约定；通用审批能力属于未来路线，当前未上线。平台统一承载身份、权限、请求上下文和调用链追踪，应用只需要声明自己要调用哪个能力。

这会把企业内部应用从“网页入口集合”变成“可组合能力网络”。每个轻应用既可以独立运行，也可以成为其他应用和 AI 工作台可调用的能力节点。

## MVP 收敛不是能力边界

当前版本的 Kageos 是为了 MVP 做过大规模收敛之后的形态，不代表平台能力的上限。主线已经把定时任务、Agent 任务和消息通知重新作为平台横切能力接回；历史分支里还探索过更完整的横切能力：AI 编排 workflow、Form 与 Form 串联、讨论区、权限审批、开放组织架构、Hub 推送与拉取、工作区事件记录等。

这些能力不应该被理解成散落的功能点，而应该被理解成同一种平台模式：

> 只要能力被目录和资源路径组织起来，平台就可以把横切能力一次建设，提供给所有挂树资源复用。

从产品含义上看，这些横切能力可以这样理解：

| 横切能力 | 当前状态 | 对 Kageos 的意义 |
| --- | --- | --- |
| workflow 编排 | 未上线，路线储备 | 把 Form、Table、Chart、Agent、审批、HTTP 调用等小能力串成业务流程，让 AI 不只是生成单点应用，而是编排企业自动化。 |
| Form 与 Form 串联 | 未上线，路线储备 | 证明标准资源可以作为可组合节点，一个表单的输出可以自然成为另一个表单的输入。 |
| 定时任务 | 已上线 | 把“时间”变成平台触发器，所有挂树能力都可以被周期性或一次性调度。 |
| Agent 任务 | 已上线 | 让 AI 从即时问答变成持续运营者，可以在未来某个时间主动检查、执行和汇报。 |
| 消息通知 | 已上线站内信；外部渠道未上线 | 把通知从应用私有逻辑变成统一平台能力，所有目录资源都可以复用同一套触达和收件箱。 |
| 函数/资源讨论区 | 未上线，路线储备 | 给每个能力节点附上协作上下文，让讨论、反馈、问题定位和知识沉淀跟着资源走。 |
| 点赞、评论、评分 | 未上线，路线储备 | 为目录资源提供低成本反馈信号，帮助能力发现、质量治理和模板筛选。 |
| 流程审批 | 未上线，路线储备 | 将高风险动作统一拦截、审批、执行和审计，而不是每个业务应用重做审批流。 |
| 开放组织架构增强 | 未上线，路线储备 | 用户、部门、岗位、归属关系成为平台上下文，权限、审批、通知和统计都能复用。 |
| Hub 推送与拉取 | 建设中/商业路线 | 让目录能力可以被打包、分发、复用和商业化，形成企业内部或跨企业的能力流通。 |
| 工作区事件记录 | 部分已有操作日志；AI 构建事件治理未上线 | 把 AI 构建过程中的失败、缺口、模糊需求和高频操作记录下来，反哺产品治理和模板演进。 |

例如，未来 workflow 不应该是一个孤立的“流程编辑器”，而是把 Form、Table、Chart、Agent、审批、HTTP 调用、定时触发等能力编排成业务自动化；当前已经上线的定时任务不是某个应用自己的 cron，而是平台提供的时间触发器；当前已经上线的消息通知先落到站内信，外部渠道后续扩展；讨论区、评论、点赞、通用审批等仍是未上线路线储备。

这也是 Kageos 和普通低代码、AI 应用生成器的关键区别。普通工具生成的是一个个应用，Kageos 要沉淀的是一个可以不断增加横切能力、支持 Hub 安装和生态发布的平台协议。当前已经有权限、审计、运行日志、AI 工作台、定时和站内信通知，未来还可以继续挂上工作流、评论、点赞、通用审批、SLA、告警、质量评分、使用统计和依赖血缘。能力越多，目录里的每个应用收益越大。

所以，删减后的 MVP 应该被讲成“先证明最小闭环”，而不是“只做这些能力”。最小闭环是：目录组织、标准资源、统一运行时、权限治理、AI 修改与复制派生。只要这个闭环成立，workflow、board、approval 等能力可以继续作为平台横切层逐步挂回来；scheduler 和 message 已经回到主线，成为当前能力的一部分。

更准确地说，Kageos 的路线不是不断做大某个单体应用，而是不断增强目录协议：

- 未来增加 workflow 能力后，所有 Form、Table、Agent 都可以被编排。
- 已接回定时能力，所有目录能力都可以被时间触发。
- 已接回消息能力，所有应用都可以统一发站内信通知用户。
- 未来增加讨论和评论能力后，所有资源都可以拥有协作上下文。
- 未来增加流程审批能力后，所有高风险动作都可以被统一拦截、审批和审计。
- 未来增强开放组织架构能力后，权限、通知、审批和归属关系可以复用同一套用户与部门上下文。

这就是“挂树即治理”的更深一层含义：树不是当前功能的集合，而是未来横切能力持续复利的基础设施。

## Source-available 自托管与目录分发

Kageos 还应该坚持 source-available 和可本地部署。它不应该只是一个中心化 SaaS，而应该是一个任何个人、团队或企业都可以安装到自己环境里的业务目录运行时、工作台和治理协议。

这件事会带来几个重要价值：

- 数据可以留在本地或企业内网，不必为了使用 AI 应用和自动化能力把敏感文件上传到外部系统。
- 算力可以使用本地机器或企业自己的服务器，适合图片转换、视频处理、文档转换、OCR、批处理、报表生成、内部文件处理等场景。
- 用户可以把 Kageos 当成自己的个人/团队工作台，在本地沉淀常用目录、脚本、表单、表格、文档和自动化流程。
- 企业可以在自己的私有环境里运行 Kageos，把权限、审计、组织架构、日志和 AI 接入都控制在内部。
- 平台可以托管更多公共目录、能力包和模板，但执行和数据可以发生在用户自己的空间里。

这会形成一种类似“目录市场 + 本地运行时”的模式。Kageos 官方或社区可以维护大量高质量目录，例如图片处理目录、视频处理目录、文档转换目录、数据清洗目录、工单目录、审批目录、知识库目录、研发效率目录等。用户看到一个目录有用，就可以安装到自己的空间里，再按自己的需求复制、派生和改造。

这种模式和传统 SaaS 市场不同。传统 SaaS 往往要求用户进入供应商的系统和数据边界；Kageos 更像是把能力目录分发给用户，让用户在自己的 Kageos 实例里运行。平台负责托管、发现、版本、能力描述、安装和更新，用户负责选择、部署、执行和二次改造。

这也强化了 Kageos 的 source-available 价值：源码可见不是单纯降低使用门槛，而是让目录协议、运行时、横切能力和 AI 工作台都能被用户验证、复用和扩展。未来 Kageos 可以同时存在公共 Hub、企业私有 Hub 和个人本地空间，目录在这些空间之间流动，能力在本地执行，治理仍然由同一套树和资源协议承载。

## 目录化与派生，而不是全家桶

传统 SaaS 的思路通常是把所有功能塞进一个大系统：支持企业微信、钉钉、飞书；支持各种审批、通知、字段和配置；支持所有组织的特殊流程。这样系统会越来越大，最终难以理解、难以维护。

Kageos 的思路相反：先有一个简单、好用、可运行的底座，然后允许团队低成本复制和派生。

例如，一个基础工单管理应用只需要几个字段和一套清晰流程。某个团队需要在新增工单时拉企业微信群，可以复制这个应用并加入企业微信逻辑。另一个团队需要拉钉钉群，也可以复制并加入钉钉逻辑。两个应用互不干扰，不必把所有集成能力都塞回同一个巨型系统。

这种模式更接近 Git 分支：

- 先复用一个已验证的基础版本。
- 再在自己的分支上低成本改造。
- 改造后与原应用物理隔离，互不影响。
- 必要时通过能力包、模板或目录关系沉淀可复用部分。

底层上，Kageos 使用代码、运行时和数据库隔离来支撑这种派生。应用可以复制，代码可以改，数据可以隔离，运行可以独立，治理仍然收口在同一个平台里。

## Kageos 与 Kubernetes 的类比

Docker 让应用打包和运行变得简单，但当容器数量变多之后，企业真正需要的是调度、服务发现、扩缩容、监控、发布和治理。Kubernetes 的价值不是“再启动一个容器”，而是让大量容器可管理。

AI 让应用生成变得简单，但当应用数量变多之后，企业真正需要的是目录、权限、版本、差异、运行时、日志、复用、发布和治理。Kageos 的价值不是“再生成一个应用”，而是让大量 AI 生成的轻应用可管理。

可以这样表达：

> Docker 让容器数量爆炸，Kubernetes 让容器可治理。
> AI 让轻应用数量爆炸，Kageos 让轻应用可治理。

这个类比不是说 Kageos 要做基础设施意义上的 Kubernetes，而是强调同一个结构性问题：生产成本下降之后，治理能力会成为新的瓶颈。

## Kageos 应该坚持的产品原则

### 1. 复杂度默认不暴露给用户

用户不应该为了完成一个小动作，被迫理解一个完整系统。Kageos 应该鼓励小应用、小入口、小流程，让用户面对自己真正需要的能力。

### 2. 复制和派生优先于巨型配置

当不同组织有差异化诉求时，不要优先把所有差异塞进同一个全家桶。更好的方式是让应用可以复制、派生和局部改造。

### 3. 标准化底座优先于自由发挥

页面审美、表单行为、表格交互、权限模型、运行日志、版本 diff 和发布流程应该尽量标准化。个性化应该发生在业务能力层，而不是让每个应用重新发明一套使用方式。

### 4. 应用必须同时对人和 AI 可读

旧软件经常是黑盒：人看不懂，AI 也看不懂。Kageos 应该让应用的目录、代码、接口、文档、数据和运行状态都尽量结构化，使 AI 可以搜索、理解、修改和组合。

### 5. 治理能力是护城河

生成只是入口，治理才是长期价值。Kageos 的核心能力应该沉淀在应用目录、权限、运行时、日志、版本、diff、能力包、模板市场和跨应用协作上。

### 6. 横切能力必须平台化

权限、操作记录、运行日志、版本历史、搜索、AI 理解和能力分发，不应该由每个轻应用重复实现。它们应该作为平台能力挂在 Service Tree 之上，所有业务能力只要进入目录，就自动获得这些治理能力。

### 7. 应用互通必须目录化

树上的应用不应该通过临时 URL、重复登录、私有 token 和点对点脚本互相集成。跨应用对接应该基于目录路径、统一身份、统一权限和统一调用上下文完成，让一个应用调用另一个应用像调用平台能力一样自然。

### 8. MVP 收敛不等于能力上限

MVP 阶段应该聚焦最小闭环，但产品叙事不能把 Kageos 讲窄。定时和站内信通知已经接回主线；workflow、讨论、点赞、评论、通用审批、开放组织架构增强和使用统计仍是可以逐步挂回目录协议的未上线横切能力。

### 9. 每个横切能力都应该带来平台复利

一个能力如果只能服务一个应用，它就是业务功能；一个能力如果能被所有目录、资源、应用和 AI 工作台复用，它才是 Kageos 的平台能力。Kageos 应该优先建设后者。

### 10. Source-available 和本地运行是重要分发方式

Kageos 应该允许用户把平台安装到自己的本地机器、团队服务器或企业内网里。公共平台负责目录托管、发现和分发，本地实例负责数据、执行和二次改造。这样 Kageos 才能覆盖个人工具、团队效率、企业内网和商业分发等不同场景。

## 可以对外使用的表达

Kageos 不是新的 OS，也不是一个通用聊天机器人。Kageos 是 AI 时代的开箱即用业务目录网络和企业能力治理平台。

更短的表达：

> AI 让每个人都能生成应用，Kageos 让团队能够安装、创造、治理和分发这些能力。

或者：

> Kageos 让企业内部能力像目录一样安装、创建、复制、派生、运行、治理和发布。

再产品化一点：

> 用 Kageos，把一个业务需求变成可安装、可运行、可复制、可派生、可治理、可发布的目录能力。

强调平台复利时，也可以这样说：

> 在 Kageos 里，能力挂上树，就自动拥有权限、审计、版本、搜索、运行时和 AI 工作台。

强调跨应用互通时，可以这样说：

> 挂在 Kageos 树上的应用，可以无缝调用其他目录里的能力，不再为每个系统重复处理登录、权限和上下文。

强调横切能力扩展时，可以这样说：

> Kageos 的每个横切能力都是一次建设、全目录复用。

或者：

> 今天挂权限和审计，当前接回定时和站内信通知，未来再挂工作流、评论和审批；能力越多，目录里的每个应用越强。

强调 source-available 和本地部署时，可以这样说：

> Kageos 是 source-available、可自托管的业务目录运行时；当前核心采用 BSL 1.1，限制未经授权的商业 SaaS、MSP 托管、白标、OEM、嵌入、改名转售和竞品化产品/服务，各版本发布四年后转 Apache-2.0。用户可以把 Hub 目录安装到自己的空间，用自己的数据和算力运行。

或者：

> 平台托管目录，用户安装目录；能力可以分发，数据和执行留在自己的环境里。

## 当前最重要的战略焦点

Kageos 不应该被讲成“AI 工具集合”，也不应该回到“新 OS”的宏大叙事。更清晰的焦点是：

- 以 Hub 开箱即用目录降低首次价值获取成本。
- 以 AI 工作台降低目录创造和修改成本。
- 以 Service Tree 组织企业内部能力，并作为权限、审计、版本、搜索和 AI 理解的统一治理锚点。
- 以 Form、Table、Chart、Docs 等标准形态降低用户学习成本。
- 以统一调用链打通树上应用，让轻应用可以跨目录组合，而不必重复处理登录态、权限和上下文传递。
- 以运行时、数据库隔离和版本机制支撑复制与派生。
- 以能力包和建设中的 Hub 路线支撑安装、复用、派生、发布和商业化。
- 以平台横切能力统一提供权限、操作记录、运行日志、diff、发布和排障，避免每个应用重复造轮子。
- 以已接回的定时任务、Agent 任务和消息通知证明横切能力路线，并继续将 workflow、讨论区、点赞评论、流程审批、开放组织架构等未上线能力逐步作为平台横切层挂回目录。
- 以 source-available 和本地部署扩大采用面，让用户可以把公共目录安装到自己的空间，用本地或企业算力处理图片、视频、文档、数据和内部自动化任务。

最终，Kageos 要解决的是 AI 时代企业内部软件的新矛盾：

> 应用会越来越容易生成，但企业会越来越难复用、管理、连接和分发这些能力。

Kageos 的位置就在这里。
