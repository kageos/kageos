# AI-Agent-OS 产品减法与主链路打深计划

> 时间：2026-05-16
> 状态：MVP 开源前减法执行口径
> 核心结论：当前阶段以个人用户和小团队可用为准，保留 AI 创建、修改、运行轻应用主链路；没有进入 MVP 的企业治理、通用工作流、消息中心、备份控制面等实现直接删除，不再只做入口隐藏。

---

## 1. 背景

AI-Agent-OS 曾经按平台型产品扩张，代码里包含过企业版、权限审批、全局消息、备份控制面、通用工作流等横切能力。这些能力会显著放大实现、测试、文档和部署成本，也会让开源用户误以为项目当前已经承诺完整企业治理能力。

当前阶段的真实目标收缩为：

> 用户可以用 AI 稳定创建、修改、运行一个企业轻应用。

因此本轮减法不是简单隐藏菜单，而是同步删除没有 MVP 使用路径的代码、配置、文档和种子数据。Table 更新日志保留，因为它直接服务 Table 的可追溯修改场景，个人用户和小团队也能直接用上。

---

## 2. 本次减法目标

### 2.1 产品目标

将当前产品收缩为：

> **AI 生成企业轻应用的工作台。**

第一阶段面向个人用户或小团队，优先解决：

1. 用户进入工作空间。
2. 用户通过自然语言描述需求。
3. 工作台生成 PRD。
4. 用户确认 PRD。
5. Agent 创建或修改应用代码。
6. 系统构建并注册应用。
7. 用户可以直接运行 Form / Table / Chart。
8. Table 修改过程可以查看更新日志。
9. 出错时 Agent 可以定位、修复、重建、验证。

### 2.2 工程目标

- 非 MVP 代码直接删除，避免开源后读者误判产品承诺。
- 前端入口收敛到主链路，降低用户认知负担。
- 后端删除没有对应产品路径的企业版、权限审批、全局消息、备份控制面、通用工作流壳子。
- 保留工作空间、服务树、工作台、Form、Table、Chart、构建运行闭环。
- 保留 Table 更新日志，删除 Form 操作日志和企业审计实现。

### 2.3 心智目标

用户打开系统时，不应该首先感受到“大而全企业后台”，而应该清楚感受到：

> 这里是一个可以帮我做内部业务应用的 AI 工作台。

---

## 3. 减法原则

### 3.1 删除无主链路能力

处理策略：

- 没有 MVP 使用路径的前端页面、API、模型、部署配置直接删除。
- 已删除能力不继续保留旧 Swagger、部署配置、角色文档和示例。
- 测试、seed、prompt、README 随功能边界同步调整。
- 不通过“隐藏入口”假装减法，避免继续维护不可达实现。

### 3.2 保主链路，保少量真实底座

保留直接支撑“AI 创建轻应用”的能力：

- 工作空间
- 服务树
- 工作台 Agent
- Form
- Table
- Chart
- 文件上传与输出
- 构建、运行、错误修复
- Table 更新日志
- Docs 基础能力
- LLM 管理

### 3.3 默认个人和小团队友好

第一阶段先以个人或小团队为默认场景：

- 当前用户默认管理自己的工作空间。
- 新创建应用默认当前用户可读写。
- 不在 UI 中展示复杂授权、审批、组织概念。
- 不要求用户理解企业治理能力才能完成主流程。

### 3.4 百米深，而不是一公里宽

当前阶段不追求功能广度，追求主链路深度。

判断标准：

- 能否稳定创建一个 Table 应用？
- 能否稳定创建一个 Form 工具？
- 能否稳定上传文件并返回结果？
- 能否稳定修改字段、选项、查询条件？
- 能否查看 Table 修改痕迹？
- 能否构建失败后自动定位并修复？
- 能否让用户少学习、少配置、少跳转？

## 4. 第一阶段保留能力

| 能力 | 状态 | 原因 |
|---|---:|---|
| 登录 / 注册 | 保留最小版 | 需要识别当前用户和工作空间归属 |
| 用户设置 | 保留最小版 | 只保留昵称、密码等基础设置 |
| 工作空间 | 保留 | 产品主舞台 |
| 服务树 | 保留 | 项目核心抽象，组织所有应用能力 |
| 工作台 Agent | 保留并打深 | 项目差异化核心 |
| Form | 保留并打深 | 一次性工具、文件处理、报告生成等高价值场景 |
| Table | 保留并打深 | 台账、CRUD、查询、管理系统核心场景 |
| Table 更新日志 | 保留 | 直接服务表格修改追溯，小团队也有价值 |
| Chart | 保留基础能力 | 优先作为 Table 的统计展示 |
| 文件上传 / 输出文件 | 保留并打深 | 能快速体现 AI 应用价值 |
| 构建 / 运行 / 错误修复 | 保留并打深 | 决定产品是否可信 |
| Docs | 保留轻量版 | 作为需求、说明和沉淀入口 |
| LLM 管理页面 | 保留 | 支持模型配置和本地调试 |

## 5. 第一阶段已删除能力

这些能力不再作为 MVP 代码和文档的一部分保留。

| 能力 | 处理结果 |
|---|---|
| 企业版 License | 删除企业版接口、客户端、前端升级入口和相关文档 |
| 权限审批 / 角色治理 | 删除权限模型、审批服务、权限中间件、权限字段和前端入口 |
| 全局消息中心 | 删除 message-server、全局消息 DTO、SDK SendMessage 和部署配置 |
| 备份控制面 | 删除 backup-service、备份入口、健康检查和恢复流程文档 |
| 控制面服务 | 删除 control-service、License 控制面和独立配置 |
| Form 操作日志 | 删除 Form 日志模型、服务、API、前端 tab 和 replay 逻辑 |
| 企业审计实现 | 删除 enterprise / enterprise_impl 目录 |
| 通用工作流 / 审批流 | 删除当前没有产品路径的壳子和文档承诺 |
| 已无调用方的历史能力 | 删除已无调用方的实现、seed 和引用 |
| Table 创建批处理钩子 | 删除相关逻辑 |

## 6. 第一阶段主链路要打深的内容

### 6.1 工作台链路

目标：

```text
用户描述需求
-> 工作台理解需求
-> 生成结构化 PRD
-> 用户确认
-> 生成或修改应用代码
-> 构建
-> 注册到服务树
-> 前端可运行
-> QA 验证核心功能
-> 出错后自动修复
```

重点打磨：

- PRD 输出结构稳定。
- 用户确认动作明确。
- 生成代码位置稳定。
- 构建结果清楚。
- 工具调用过程可理解。
- 失败原因能被归纳。
- 修复后能再次验证。

### 6.2 Form 深度

重点场景：

- 文件上传处理
- 文本/表单输入处理
- 输出文件返回
- 报告生成
- 数据转换

重点能力：

- 字段渲染稳定。
- 校验提示清楚。
- 文件上传进度和失败提示可靠。
- 输出文件展示和下载可靠。
- Agent 能根据需求正确选择 widget。
- Agent 能修复常见 SDK / schema / validate 错误。

### 6.3 Table 深度

重点场景：

- 台账、客户、订单、工单、库存、招聘、任务类应用
- CRUD
- 查询筛选
- 详情查看
- 行编辑
- 更新日志查看

重点能力：

- 新建记录顺畅。
- 查询和分页稳定。
- 筛选条件好用。
- 行详情清晰。
- 字段修改后前后端同步正确。
- 新增、修改、删除写入 Table 更新日志。
- Agent 能增删字段、调整选项、修改校验、补充查询条件。

### 6.4 Chart 深度

第一阶段 Chart 不独立扩张，优先作为 Table 的延伸。

重点场景：

- 基于 Table 做统计。
- 趋势、占比、分组汇总。
- 简单仪表盘预览。

暂不追求：

- 复杂 BI。
- 拖拽式图表设计器。
- 多数据源联邦分析。

### 6.5 构建与错误修复

这是产品可信度的关键。

重点能力：

- 构建日志可读。
- 常见错误可定位。
- Agent 能自动读取相关文件。
- Agent 能进行最小修改。
- 修复后自动重新构建。
- 构建成功后能立即运行验证。

## 7. 实施方式

### 7.1 代码真实删除

当前采用真实删减：

- 删除无产品路径的服务目录、DTO、模型、中间件、前端 store、API 封装和组件。
- 删除生产和开发部署中的独立服务配置。
- 删除旧迁移脚本和恢复文档中与已删服务绑定的内容。
- 删除 prompt / seed / ability bundle 中已删能力的示例。

### 7.2 前端入口收敛

默认 UI 只展示主链路能力：

- 工作空间
- 服务树
- 工作台
- Form / Table / Chart 运行视图
- Table 更新日志
- Docs
- LLM 管理

不再展示：

- 企业升级入口
- 权限申请与角色管理入口
- 消息中心入口
- 备份控制面入口
- Form 操作日志入口
- 通用工作流入口

### 7.3 后端围绕 MVP 收口

后端策略：

- App Server 承担 MVP 核心业务。
- Agent Server 负责工作台、LLM、工具循环和构建修复。
- App Runtime / SDK 保留运行应用所需能力。
- Table 更新日志作为普通能力保留，不依赖企业版开关。
- 不再保留企业版 License、权限审批、消息中心、控制面、备份控制面实现。

### 7.4 文档同步

需要保持一致的对外口径：

> 项目当前面向开源 MVP，优先打磨 AI 轻应用创建和运行主链路。没有进入 MVP 的企业治理、全局消息、控制面、备份控制面、Form 操作日志和通用工作流等能力已从代码和文档中移除。Table 更新日志保留。

## 8. 阶段计划

### 阶段 1：删除历史包袱

目标：

- 默认 UI 只展示主链路能力。
- 用户不会被企业治理、审批、消息、备份控制面等非主链路能力干扰。
- 开源读者不会在代码中看到大量不可参与、不可运行的历史实现。

验收：

- 关键残留关键词扫描只剩合法协议元数据或通用术语。
- 生成 Swagger 不再暴露已删能力。
- Go 测试、前端 type-check、前端单测和 build 通过。

### 阶段 2：主链路稳定

目标：

- 从自然语言创建 Form/Table 应用可以稳定完成。
- 构建失败可以被定位和修复。

任务：

- 打磨工作台 PRD 确认流程。
- 打磨 app_developer 生成代码流程。
- 打磨 build 和 QA 回流。
- 固化 3 到 5 个标准 demo。
- 增加核心链路测试或脚本。

验收：

- 至少 3 个 Table demo 可稳定创建、运行、修改。
- 至少 3 个 Form demo 可稳定创建、运行、修改。
- Table 修改可以看到更新日志。
- 常见构建错误能通过工作台修复。

### 阶段 3：体验打磨

目标：

- 产品体验从“能跑”变成“顺手”。

任务：

- 优化工作空间空状态。
- 优化服务树创建和节点切换体验。
- 优化 Form/Table 的字段展示、错误提示、加载状态。
- 优化文件上传和输出文件展示。
- 优化构建日志和工具调用展示。

验收：

- 用户第一次进入能自然知道下一步做什么。
- 应用生成后能立即找到并运行。
- 表单提交、表格新增、查询、编辑都有清楚反馈。
- 出错时有明确下一步。

### 阶段 4：按真实需求扩展

恢复或新增高级能力必须重新立项：

- 必须明确服务哪条主链路。
- 必须有 demo 和验收标准。
- 每次只恢复一个能力面。
- 不为了“平台完整”而恢复功能。

## 10. 风险与应对

### 10.1 风险：删掉后未来恢复成本高

应对：

- 当前先服务开源 MVP，不为未验证需求背维护成本。
- 未来若恢复，按独立能力重新设计、重新验收。
- 保留必要的数据迁移说明，不保留不可达实现。

### 10.2 风险：主链路仍然不够稳定

应对：

- 用固定 demo 驱动开发。
- 每个 demo 都覆盖创建、修改、构建、运行、验证。
- 不再同时推进大块横切能力。

### 10.3 风险：文档和代码口径不一致

应对：

- README、部署文档、seed、prompt、Swagger 随代码一起更新。
- 删除能力不再出现在对外能力清单。
- Table 更新日志单独说明，避免和企业审计混在一起。

## 12. 最终判断

AI-Agent-OS 的长期方向仍然是 AI 原生企业应用操作系统，但当前阶段更应该把产品收缩成：

> **AI 生成企业轻应用的工作台。**

先做到：

- 用户一看就懂。
- 应用一建就能跑。
- 出错以后能修。
- Form/Table 足够好用。
- Table 修改有更新日志可追溯。
- 服务树组织清楚。
- 工作台真的能完成开发闭环。

当前不再为企业治理、权限审批、全局消息、备份控制面和通用工作流保留实现。等主链路足够深、真实用户提出明确需求后，再按新的产品边界重新设计。
