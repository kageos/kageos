# AI-Agent-OS 产品减法与主链路打深计划

> 时间：2026-05-13  
> 状态：阶段性产品决策文档  
> 核心结论：当前阶段以 MVP 为准做真实减法；保留 AI 创建、修改、运行轻应用这一条主链路，删除没有进入主链路的历史包袱。

---

## 1. 背景

AI-Agent-OS 当前已经具备比较完整的平台骨架：

- 工作空间与服务树
- Agent 工作台
- Form / Table / Chart 动态应用形态
- SDK 与应用运行时
- 文件上传与输出文件
- 权限、组织、消息、操作日志、备份恢复等平台能力

这些能力共同支撑了“AI 原生企业应用操作系统”的长期方向。但从当前实际推进节奏看，功能面已经明显超过单人开发和打磨能力。

尤其是近期尝试推进工作流能力后，可以看到一个现实问题：

> 平台横切能力每增加一层，都会显著放大设计、实现、测试、前端交互、文档和运维成本。

因此当前阶段需要主动收缩产品面，避免继续横向扩张。项目短期目标不再是证明“平台能做很多事”，而是证明：

> 用户可以用 AI 稳定创建、修改、运行一个企业轻应用。

这条链路如果足够顺、足够稳，后续权限、组织、消息、能力包复用才有恢复和扩展的基础。

---

## 2. 本次减法的目标

### 2.1 产品目标

将当前产品暂时收缩为：

> **AI 生成企业轻应用的工作台。**

第一阶段面向单用户或小团队场景，优先解决：

1. 用户进入工作空间。
2. 用户通过自然语言描述需求。
3. 工作台生成 PRD。
4. 用户确认 PRD。
5. Agent 创建或修改应用代码。
6. 系统构建并注册应用。
7. 用户可以直接运行 Form / Table / Chart。
8. 出错时 Agent 可以定位、修复、重建、验证。

### 2.2 工程目标

- 非 MVP 代码直接删除，避免开源后读者误判产品承诺。
- 前端入口收敛到主链路，降低用户认知负担。
- 后端删除没有对应产品路径的调度、Board、工作流壳子。
- 通过产品模式或功能开关控制少量仍有实现但非默认展示的能力。
- 把开发精力集中到工作空间、工作台、服务树、Form、Table、Chart、构建运行闭环。

### 2.3 心智目标

用户打开系统时，不应该首先感受到“企业后台管理系统”或“大而全平台”，而应该清楚感受到：

> 这里是一个可以帮我做内部业务应用的 AI 工作台。

## 3. 减法原则

### 3.1 删除无主链路能力，保留真实底座

当前已经进入清理代码阶段，而不只是隐藏入口。

处理策略：

- 没有 MVP 使用路径的前端页面、API、模型、部署配置直接删除。
- 有真实底座价值的能力保留最小实现，例如账号、部门、消息发送底座、操作日志、权限实现。
- 已删除能力不继续保留旧 Swagger、部署配置、角色文档和示例。
- 测试随功能边界同步调整。

### 3.2 保主链路，藏横切能力

保留直接支撑“AI 创建轻应用”的能力：

- 工作空间
- 服务树
- 工作台 Agent
- Form
- Table
- Chart
- 文件上传与输出
- 构建、运行、错误修复

隐藏暂时不会增强主链路体验、但会显著增加理解成本的能力：

- 权限管理
- 组织架构
- 审批 / 工作流
- 消息中心
- 操作日志查询
- Hub 市场

### 3.3 默认单用户友好

第一阶段先以单用户或小团队为默认场景。

建议默认行为：

- 当前用户默认拥有自己工作空间的管理权。
- 新创建应用默认当前用户可读写。
- 权限校验走宽松模式或只保留最小保护。
- 不在 UI 中展示复杂授权、审批、组织概念。

### 3.4 百米深，而不是一公里宽

当前阶段不追求功能广度，追求主链路深度。

判断标准：

- 能否稳定创建一个 Table 应用？
- 能否稳定创建一个 Form 工具？
- 能否稳定上传文件并返回结果？
- 能否稳定修改字段、选项、查询条件？
- 能否构建失败后自动定位并修复？
- 能否让用户少学习、少配置、少跳转？

## 4. 第一阶段保留能力

这些能力继续作为产品可见主线。

| 能力 | 是否保留入口 | 原因 |
|---|---:|---|
| 登录 / 注册 | 保留最小版 | 需要识别当前用户和工作空间归属 |
| 用户设置 | 保留最小版 | 只保留昵称、密码等基础设置 |
| 工作空间 | 保留 | 产品主舞台 |
| 服务树 | 保留 | 项目核心抽象，组织所有应用能力 |
| 工作台 Agent | 保留并打深 | 项目差异化核心 |
| Form | 保留并打深 | 一次性工具、文件处理、报告生成等高价值场景 |
| Table | 保留并打深 | 企业台账、CRUD、查询、管理系统核心场景 |
| Chart | 保留但降级为延伸能力 | 优先作为 Table 的统计展示，不单独扩复杂场景 |
| 文件上传 / 输出文件 | 保留并打深 | 能快速体现 AI 应用价值 |
| 构建 / 运行 / 错误修复 | 保留并打深 | 决定产品是否可信 |
| Docs | 可保留轻量版 | 可作为需求、说明和沉淀入口 |
| LLM 管理页面 | 保留为开发/管理员入口 | 当前阶段需要支持模型配置和本地调试，但不作为普通业务主线宣传 |

## 5. 第一阶段隐藏能力

这些能力代码保留，但从默认产品入口中隐藏。

### 5.1 权限管理

隐藏内容：

- 权限申请页面
- 角色管理页面
- 权限分配入口
- 服务树中的授权、申请权限等高级动作
- 工作空间中“仅展示有权限资源”“权限强制”等复杂配置入口

保留策略：

- 后端权限模型和接口保留。
- 默认当前用户为 owner/admin。
- 默认当前用户对自己工作空间拥有读写管理能力。
- 权限相关字段继续兼容，但 UI 不主动暴露。

恢复条件：

- Form/Table 主链路稳定。
- 存在明确多人协作或私有化部署需求。
- 操作日志、消息通知、组织架构至少具备基础可用状态。

### 5.2 组织架构

隐藏内容：

- 组织架构管理页面
- 部门管理入口
- 用户分配部门、负责人、上下级等复杂字段入口

保留策略：

- 用户系统保留最小能力。
- 部门相关接口和数据结构保留。
- 前端组件里如果已有用户选择、部门选择，短期只在必要场景保留，不作为全局管理入口展示。

恢复条件：

- 权限管理恢复前后。
- 用户开始明确需要部门授权、部门通知、部门负责人审批。

### 5.3 审批 / 工作流

隐藏内容：

- 通用工作流入口
- 审批流配置入口
- 资源操作审批能力
- 工作流设计器类能力

保留策略：

- 当前阶段不继续推进通用工作流。
- 若需要风险控制，优先使用简单确认、操作日志、回滚提示，不引入完整审批引擎。

恢复条件：

- 权限、组织、消息三者都具备稳定基础。
- 有明确高频审批场景，例如 Table 删除、关键字段变更、目录发布。

### 5.4 消息中心

隐藏内容：

- 全局消息中心入口
- 收件箱面板
- 复杂通知订阅配置

保留策略：

- 页面内提示继续保留。
- 构建完成、构建失败、运行结果等局部反馈继续保留。
- message-server 代码和接口不删除。

恢复条件：

- 多人协作或后台长任务进入主线。
- 用户确实需要异步通知和待办。

### 5.5 操作日志查询

隐藏内容：

- 操作日志查询页
- Form/Table 操作日志可视化入口
- 审计报表类入口

保留策略：

- 后端可以继续记录关键操作。
- 不在默认 UI 中展示审计和日志能力。

恢复条件：

- 产品进入多人或企业部署阶段。
- 权限能力恢复。
- 需要合规、追溯、审计展示。

### 5.6 Hub / 应用市场

隐藏内容：

- 发布到 Hub
- 从 Hub 拉取
- Hub 收藏、详情、版本、市场浏览
- 外部市场化入口

保留策略：

- 代码保留。
- 短期可将能力收缩为“本地模板 / 能力包导入导出”的开发者功能。
- 默认用户路径不出现市场概念。

恢复条件：

- 本地应用创建和修改体验稳定。
- 已有足够高质量模板。
- 用户开始需要复用、分发和迁移应用。

## 6. 第一阶段主链路要打深的内容

### 6.1 工作台链路

目标：

```text
用户描述需求
-> 工作台理解需求
-> 生成结构化 PRD
-> 用户确认
-> 生成或修改应用代码
-> 构建
-> 注册到服务树
-> 前端可运行
-> QA 验证核心功能
-> 出错后自动修复
```

重点打磨：

- PRD 输出结构稳定。
- 用户确认动作明确。
- 生成代码位置稳定。
- 构建结果清楚。
- 工具调用过程可理解。
- 失败原因能被归纳。
- 修复后能再次验证。

### 6.2 Form 深度

重点场景：

- 文件上传处理
- 文本/表单输入处理
- 输出文件返回
- 报告生成
- 数据转换

重点能力：

- 字段渲染稳定。
- 校验提示清楚。
- 文件上传进度和失败提示可靠。
- 输出文件展示和下载可靠。
- Agent 能根据需求正确选择 widget。
- Agent 能修复常见 SDK / schema / validate 错误。

### 6.3 Table 深度

重点场景：

- 企业台账
- 客户、订单、工单、库存、招聘、任务类应用
- CRUD
- 查询筛选
- 详情查看
- 行编辑

重点能力：

- 新建记录顺畅。
- 查询和分页稳定。
- 筛选条件好用。
- 行详情清晰。
- 字段修改后前后端同步正确。
- Agent 能增删字段、调整选项、修改校验、补充查询条件。

### 6.4 Chart 深度

第一阶段 Chart 不独立扩张，优先作为 Table 的延伸。

重点场景：

- 基于 Table 做统计。
- 趋势、占比、分组汇总。
- 简单仪表盘预览。

暂不追求：

- 复杂 BI。
- 拖拽式图表设计器。
- 多数据源联邦分析。

### 6.5 构建与错误修复

这是产品可信度的关键。

重点能力：

- 构建日志可读。
- 常见错误可定位。
- Agent 能自动读取相关文件。
- Agent 能进行最小修改。
- 修复后自动重新构建。
- 构建成功后能立即运行验证。

## 7. 实施方式

### 7.1 增加产品聚焦模式

建议引入一个统一概念：

```text
Focused Mode / 产品聚焦模式
```

默认开启聚焦模式。

聚焦模式下：

- 只显示主链路能力。
- 隐藏企业治理、生态、协作、调度等高级能力入口。
- 后端保持兼容，不大规模删除接口。

未来可以通过配置恢复完整模式：

```text
focused: 默认模式，面向单用户/小团队 AI 轻应用创建
full: 完整平台模式，面向企业治理和生态能力
```

### 7.2 前端优先隐藏

第一阶段主要改前端：

- 路由 meta 增加功能标记。
- 侧边栏、头像菜单、工作空间动作菜单按功能标记过滤。
- 组件内部高级按钮用统一 feature flag 控制。
- 保留直接访问隐藏路由时的兼容处理，可跳转工作空间或展示“该能力暂未开放”。

优先处理入口：

- `/organization`
- `/permissions/apply`
- `/permissions/roles`
- 消息中心入口
- Hub 发布/拉取入口
- 操作日志入口

保留入口：

- `/agent/llm`，作为开发者或管理员配置入口保留。

### 7.3 后端保持默认宽松

后端围绕 MVP 做真实删减。

建议策略：

- 权限校验默认不过度阻塞主链路。
- 当前用户默认拥有自己工作空间管理权。
- 创建应用自动设置当前用户为管理员。
- 操作日志可继续异步记录，但不影响主流程。
- 消息发送底座可以继续存在，但收件箱入口不主动暴露。

### 7.4 文档同步

需要同步更新：

- README 中的“当前阶段重点”
- 项目状态文档
- 开发启动文档
- 前端 README 中关于新入口的说明

避免外部读者误以为已删除能力仍是当前产品承诺。

推荐表述：

> 项目当前默认运行在产品聚焦模式，优先打磨 AI 轻应用创建和运行主链路。没有进入 MVP 的调度、Board、通用工作流等能力已从代码和文档中移除。

## 8. 阶段计划

### 阶段 1：入口减法

目标：

- 默认 UI 只展示主链路能力。
- 用户不会被权限、组织、审批、Hub、消息等非主链路能力干扰。

任务：

- 梳理前端所有全局入口。
- 引入功能开关或聚焦模式配置。
- 隐藏权限、组织、Hub、消息、操作日志入口。
- 保留 LLM 管理入口，用于模型配置和本地调试。
- 保证现有核心工作空间路径不受影响。

验收：

- 登录后默认进入工作空间。
- 主菜单不出现权限、组织、Hub、消息等入口。
- 用户可以创建、进入、浏览自己的工作空间。
- 已有隐藏路由不会影响主链路运行。

### 阶段 2：主链路稳定

目标：

- 从自然语言创建 Form/Table 应用可以稳定完成。
- 构建失败可以被定位和修复。

任务：

- 打磨工作台 PRD 确认流程。
- 打磨 app_developer 生成代码流程。
- 打磨 build 和 QA 回流。
- 固化 3 到 5 个标准 demo。
- 增加核心链路测试或脚本。

验收：

- 至少 3 个 Table demo 可稳定创建、运行、修改。
- 至少 3 个 Form demo 可稳定创建、运行、修改。
- 常见构建错误能通过工作台修复。
- 用户不需要理解权限、组织、Hub 等高级能力也能完成主流程。

### 阶段 3：体验打磨

目标：

- 产品体验从“能跑”变成“顺手”。

任务：

- 优化工作空间空状态。
- 优化服务树创建和节点切换体验。
- 优化 Form/Table 的字段展示、错误提示、加载状态。
- 优化文件上传和输出文件展示。
- 优化构建日志和工具调用展示。

验收：

- 用户第一次进入能自然知道下一步做什么。
- 应用生成后能立即找到并运行。
- 表单提交、表格新增、查询、编辑都有清楚反馈。
- 出错时有明确下一步。

### 阶段 4：按需恢复高级能力

恢复顺序建议：

1. Chart 深化
2. 本地模板 / 能力包导入导出
3. 操作日志查询
4. 简单多人共享
5. 权限
6. 组织架构
7. 能力包复用

恢复原则：

- 每次只恢复一个能力面。
- 恢复前必须明确它服务哪条主链路。
- 恢复后必须有 demo 和验收标准。
- 不为了“平台完整”而恢复功能。

## 10. 风险与应对

### 10.1 风险：隐藏入口后代码仍然复杂

应对：

- 第一阶段接受内部复杂度存在。
- 不急着重构全部历史功能。
- 先通过产品入口减法降低认知复杂度。
- 等主链路稳定后，再做工程清理。

### 10.2 风险：未来恢复高级功能时成本高

应对：

- 不删代码。
- 功能开关统一管理。
- 隐藏时保留路由和 API 的兼容性。
- 文档记录隐藏原因和恢复条件。

### 10.3 风险：用户误以为能力缺失

应对：

- 对外描述为“当前默认聚焦模式”。
- 不强调隐藏了哪些能力。
- 只在开发者文档说明完整平台能力后续恢复。

### 10.4 风险：主链路仍然不够稳定

应对：

- 用固定 demo 驱动开发。
- 每个 demo 都覆盖创建、修改、构建、运行、验证。
- 不再同时推进大块横切能力。

## 11. 近期执行建议

## 12. 最终判断

AI-Agent-OS 的长期方向仍然是 AI 原生企业应用操作系统，但当前阶段更应该把产品收缩成：

> **AI 生成企业轻应用的工作台。**

先做到：

- 用户一看就懂。
- 应用一建就能跑。
- 出错以后能修。
- Form/Table 足够好用。
- 服务树组织清楚。
- 工作台真的能完成开发闭环。

当这条主链路足够深，权限、组织、消息、能力包复用这些能力再恢复，才会变成加分项。否则它们只会过早消耗开发精力，并稀释产品心智。
