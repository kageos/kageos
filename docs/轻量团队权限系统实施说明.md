# 轻量团队权限系统实施说明

> 用途：后续从 `main` 新开分支实现轻量 Team RBAC 时使用。  
> 背景：项目准备出海，目标先服务海外中小企业、小团队、agency 和 self-hosted 用户，不做大企业复杂合规。  
> 重要原则：这不是企业版权限系统，不要恢复旧的企业治理/审批/组织架构复杂实现。该能力应直接进入社区版。

## 1. 背景

AI-Agent-OS 当前准备从“大而全 Agent OS”收敛为：

> 开源轻应用工作台：一个登录，一个 workspace，安装、复制、运行和用 AI 修改各种轻应用。

目标用户不是大企业 IT 采购，而是：

- 海外中小企业。
- 10-100 人的小团队。
- agency / 顾问 / 外包团队。
- self-hosted 开源用户。
- 需要工单、问卷、投票、文件工具、数据分析、CRM Lite、库存、资产管理等轻应用的团队。

这类用户不一定要求 SOC2、SCIM、复杂审批流，但会关心最基本的团队安全：

- 谁能进入 workspace。
- 谁能看应用。
- 谁能运行应用。
- 谁能修改或删除应用。
- 谁能增删改数据。
- 谁能管理成员。
- 谁做过关键操作。

因此，项目需要补一个**轻量团队权限系统**，让产品从“个人开源工具”升级为“small-team ready”。

## 2. 为什么不能直接恢复旧权限系统

仓库里有旧权限系统可参考：

- `backup/permission-before-removal`
- `feature/permission-org`

旧系统包含较完整的 RBAC 和企业治理能力：

- role / role_permission / role_assignment。
- action 权限点。
- 用户授权。
- 部门授权。
- 权限申请。
- 审批流。
- 权限有效期。
- 企业版 `enterprise_impl/permission`。
- 前端权限申请和角色管理页面。
- middleware 权限检查。
- 服务树权限计算。

这些代码可以参考，但**不要原样搬回**。

原因：

- 当前产品定位是轻应用工作台，不是企业治理平台。
- 旧系统包含组织架构、审批、自定义角色等复杂能力，会重新扩大产品边界。
- 旧系统曾经拆到企业版，但现在我们需要的能力是社区版基础能力。
- 海外 small team 第一阶段只需要固定角色和基础权限，不需要复杂审批。

## 3. 本次目标

实现一个社区版内置的轻量 Team RBAC。

核心能力：

1. 固定四个角色：`Owner`、`Admin`、`Member`、`Viewer`。
2. 支持给指定用户在 workspace / 目录 / 应用节点上赋权。
3. 使用 `full_code_path` 作为资源路径。
4. 支持父节点权限继承到子节点。
5. 服务树接口只返回用户可见节点，或返回节点级权限状态。
6. 后端关键 API 必须做权限判断。
7. 权限点统一收敛为 `read`、`write`、`update`、`delete`、`admin`、`owner`。
8. 新增通用操作日志表，权限变更和关键操作必须写入审计日志。
9. 授权支持到期时间，过期后权限自动失效。
10. 权限能力必须封装为统一 SDK / service，禁止在各业务接口里零散拼 SQL 或手写判断。

## 4. 非目标

本阶段明确不做：

- 自定义角色。
- 部门/组织架构授权。
- 权限申请。
- 审批流。
- 字段级权限。
- SCIM。
- SAML。
- SOC2/ISO 级合规能力。
- 企业版 license gating。
- `enterprise_impl/permission` 复活。
- 复杂权限矩阵 UI。

后续如果有企业客户真实需求，再另行设计。

## 5. 社区版定位

该权限系统应直接作为社区版基础能力实现。

不要再拆成：

- `enterprise/permission.go`
- `enterprise_impl/permission/**`
- license feature gate

推荐放在 app-server 常规模块中，例如：

- `core/app-server/model/team_access.go`
- `core/app-server/repository/team_access_repository.go`
- `core/app-server/service/team_access_service.go`
- `core/app-server/api/v1/team_access.go`
- `pkg/permission` 可保留轻量通用常量/路径工具。

命名可以是：

- `team_access`
- `workspace_member`
- `workspace_role_assignment`
- `access_control`

避免重新使用过于企业化的产品词，例如 `approval`、`enterprise permission`。

## 6. 角色定义

第一版只保留四个角色。

| 角色 | 说明 |
| --- | --- |
| Owner | workspace 创建者/拥有者，拥有所有权限，不能被普通管理员移除 |
| Admin | 管理成员、安装/删除应用、导入/导出应用包、修改应用、查看日志 |
| Member | 运行应用、提交表单、查询/新增/修改表格数据、查看图表；不允许删除记录 |
| Viewer | 只读查看表格、图表、文档和可见应用 |

未来如果需要，可以新增 `Builder`，把“能修改应用代码”和“能操作业务数据”拆开。但第一版先不要加。

## 7. 资源模型

资源路径继续使用现有 `full_code_path`。

示例：

```text
/alice/ops
/alice/ops/helpdesk
/alice/ops/helpdesk/tickets.table
/alice/ops/surveys/customer_feedback.form
```

授权范围：

- workspace 根：`/alice/ops`
- package 目录：`/alice/ops/helpdesk`
- function 节点：`/alice/ops/helpdesk/tickets.table`

继承规则：

- 父节点授权对子节点直接生效。
- 如果用户拥有 `/alice/ops/helpdesk` 的权限，那么 `/alice/ops/helpdesk/sub` 以及下面的 docs/table/form/chart 节点都继承这些权限。
- 子目录继续继承父目录权限，例如 `/user1/app1/ticket` 的权限自动覆盖 `/user1/app1/ticket/sub`。
- 父节点有的权限，子节点默认直接拥有。
- 用户对子节点有权限时，父目录应作为路径容器展示。
- 没权限的兄弟节点不展示。
- 前端隐藏按钮只是体验优化，后端 API 必须强校验。

示例：

```text
用户 A 在 /user1/app1/ticket 上拥有 read 权限
```

则用户 A 可以查看：

- `/user1/app1/ticket` 目录。
- `/user1/app1/ticket/sub` 子目录。
- 该目录和子目录下的 Docs。
- 该目录和子目录下的 Chart。
- 该目录和子目录下的 Table。
- 该目录和子目录下的 Form。

```text
用户 A 在 /user1/app1/ticket 上拥有 write 权限
```

则用户 A 可以在该目录和所有子目录下：

- Table 新增记录。
- Form 提交。
- Chart 查询。
- Docs 新增文档。

```text
用户 A 在 /user1/app1/ticket 上拥有 update 权限
```

则用户 A 可以在该目录和所有子目录下：

- Table 更新记录。
- Docs 更新文档。
- 更新允许普通成员编辑的业务内容。

```text
用户 A 在 /user1/app1/ticket 上拥有 delete 权限
```

则用户 A 可以在该目录和所有子目录下：

- Table 删除记录。
- Docs 删除文档。
- 删除允许删除的节点或资源。

注意：虽然 `delete` 权限支持继承，但默认角色矩阵中只有 `Admin` 和 `Owner` 拥有 `delete`。`Member` 不拥有删除权限。

## 8. 统一权限点

权限点必须保持简单统一，不要为每类资源造一套复杂动作。

本阶段统一使用以下 6 个权限点：

| 权限点 | 用途 |
| --- | --- |
| `read` | 查看 workspace、服务树节点、表格、图表、文档、应用详情 |
| `write` | 提交 Form、新增 Table 记录、查询 Chart、新增 Docs、上传文件、执行普通业务写入 |
| `update` | 修改 Table 记录、修改 Docs、修改允许普通成员更新的业务内容 |
| `delete` | 删除 Table 记录、删除 Docs、删除节点、删除应用、删除文件等危险操作 |
| `admin` | 管理成员、授权、安装/导入/导出应用包、查看/导出日志、执行管理操作 |
| `owner` | workspace 所有者最高权限，包含全部权限，不能被普通管理员移除 |

说明：

- 不再引入 `run`、`edit` 等额外动作。运行类操作按语义映射到 `read` 或 `write`。
- 查看 Chart、查看 Table、查看 Form schema、查看 Docs 属于 `read`。
- 查询 Chart、提交 Form、新增 Table 记录、新增 Docs 属于 `write`。
- 修改 Table 记录、更新 Docs 属于普通 `update`。
- AI 修改应用、构建/发布应用、目录结构管理属于管理级操作，第一版建议使用 `admin`，默认只允许 `Admin` 和 `Owner`。
- 删除 Table 记录、删除 Docs、删除节点/应用统一属于 `delete`，只允许 `Admin` 和 `Owner`。
- 管理成员、导入导出应用包、查看审计日志属于 `admin`。
- `owner` 是最高权限，不建议作为普通赋权动作暴露给 Admin。

## 9. 角色权限矩阵建议

| 能力 | Owner | Admin | Member | Viewer |
| --- | --- | --- | --- | --- |
| 查看服务树可见节点 | yes | yes | yes | yes |
| 查看 Form/Table/Chart/Docs | yes | yes | yes | yes |
| 运行/提交 Form | yes | yes | yes | no |
| 查询/刷新 Chart 数据 | yes | yes | yes | no |
| 新增 Docs | yes | yes | yes | no |
| 更新 Docs | yes | yes | yes | no |
| 删除 Docs | yes | yes | no | no |
| 新增/修改 Table 记录 | yes | yes | yes | no |
| 删除 Table 记录 | yes | yes | no | no |
| 新增目录 | yes | yes | no | no |
| 编辑目录 | yes | yes | no | no |
| 移动目录 | yes | yes | no | no |
| 删除目录 | yes | yes | no | no |
| 创建/删除函数节点 | yes | yes | no | no |
| 创建/修改应用代码 | yes | yes | no | no |
| AI 修改应用 | yes | yes | no | no |
| 安装应用包 | yes | yes | no | no |
| 导入/导出应用包 | yes | yes | no | no |
| 删除应用/节点 | yes | yes | no | no |
| 管理成员和角色 | yes | yes | no | no |
| 查看/导出操作日志 | yes | yes | no | no |
| 删除 workspace | yes | no | no | no |

注意：

- 第一版明确规定 `Member` 不支持删除记录。删除操作只放在 `Admin` 和 `Owner` 中。
- 目录结构管理属于管理员能力，包括新增目录、编辑目录、移动目录、删除目录、创建/删除函数节点等，默认只允许 `Admin` 和 `Owner`。
- `Member` 的 `update` 只表示业务数据更新，例如 Table 记录和 Docs 内容，不表示可以编辑目录结构或应用代码。

## 10. 数据模型建议

因为角色固定，不需要恢复 `role`、`role_permission`、`action` 多表模型。

最小表可以是：

```text
workspace_role_assignment
- id
- tenant_user
- app
- username
- role_code      owner/admin/member/viewer
- resource_path  full_code_path
- expires_at     nullable，到期时间；为空表示永久有效
- created_by
- created_at
- updated_at
- deleted_at
```

可选字段：

```text
source          manual/system/import
note            备注
```

Owner 来源：

- workspace 创建者默认是 Owner。
- 也可以在创建 workspace 时写入一条 Owner assignment。
- 为避免数据不一致，权限判断中也应保留“app owner 永远有所有权限”的兜底规则。

唯一约束建议：

```text
(tenant_user, app, username, resource_path, role_code)
```

说明：

- 允许同一个用户在同一个资源路径拥有多条不同角色记录，但一般 UI 默认只分配一个角色。
- 如果出现多条角色记录，权限按并集计算，取用户拥有的最大权限集合。
- 修改角色可以先删除旧角色再插入新角色，也可以按 role_code 维度更新。
- 权限判断时必须过滤已过期记录。

## 11. 服务接口建议

### 11.1 成员列表

```text
GET /workspace/api/v1/team_access/members?resource_path=/alice/ops
```

返回当前 workspace 或资源节点的成员授权列表。

### 11.2 添加/修改成员角色

```text
POST /workspace/api/v1/team_access/assign
```

请求：

```json
{
  "resource_path": "/alice/ops",
  "username": "bob",
  "role_code": "member",
  "expires_at": null
}
```

可支持批量授权：

```text
POST /workspace/api/v1/team_access/batch_assign
```

请求：

```json
{
  "resource_paths": [
    "/alice/ops/helpdesk",
    "/alice/ops/surveys"
  ],
  "usernames": ["bob", "carol"],
  "role_codes": ["member"],
  "expires_at": "2026-12-31T23:59:59Z"
}
```

说明：

- `role_codes` 支持多个固定角色，但同一个资源上通常只需要一个角色。
- 多角色同时存在时按权限并集计算。
- `expires_at` 为空表示永久有效。

### 11.3 移除成员角色

```text
POST /workspace/api/v1/team_access/remove
```

请求：

```json
{
  "resource_path": "/alice/ops",
  "username": "bob",
  "role_code": "member"
}
```

如果 `role_code` 为空，可以移除该用户在该资源路径上的所有角色。

### 11.4 当前用户权限

```text
GET /workspace/api/v1/team_access/my_permissions?resource_path=/alice/ops/helpdesk
```

返回：

```json
{
  "resource_path": "/alice/ops/helpdesk",
  "role_code": "member",
  "permissions": {
    "read": true,
    "write": true,
    "update": true,
    "delete": false,
    "admin": false,
    "owner": false
  },
  "expires_at": "2026-12-31T23:59:59Z"
}
```

## 12. 服务树权限展示

服务树接口应支持返回用户可见节点，并附带当前用户对节点的权限。

推荐响应中包含：

```json
{
  "full_code_path": "/alice/ops/helpdesk/tickets.table",
  "name": "Tickets",
  "type": "function",
  "template_type": "table",
  "permissions": {
    "read": true,
    "write": true,
    "update": true,
    "delete": false,
    "admin": false,
    "owner": false
  }
}
```

过滤规则：

- 有节点权限：展示节点。
- 只有子节点权限：父目录作为容器展示，但父目录操作按钮禁用。
- 没权限：不展示。
- Owner/Admin 可以看到完整服务树。
- 目录权限继承给子目录和子节点，前端展示时应体现继承来源，例如可选返回 `inherited_from` 字段。

注意：

- 服务树过滤是用户体验和数据最小化。
- 真正安全必须靠每个关键 API 的后端权限判断。

### 12.1 前端赋权交互

前端赋权可以参考旧权限系统的服务树式设计，但要简化。

建议：

- 在成员/权限管理弹窗中直接展示服务树。
- 每个节点展示当前用户或目标用户在该节点上的角色和权限。
- 支持选择单个节点。
- 支持勾选多个节点后批量赋权。
- 支持选择一个或多个固定角色：Owner / Admin / Member / Viewer。
- 支持设置到期时间，默认为永久。
- 展示继承权限来源，例如“继承自 /user1/app1/ticket”。
- 对继承权限只展示来源，不直接在子节点生成重复授权记录。
- 当用户在子节点单独赋权时，子节点权限与父节点继承权限做并集。

## 13. 后端必须检查的关键操作

第一版不要求每个普通读取接口都复杂配置，但所有敏感操作必须检查。

权限检查必须通过统一 SDK / service 入口完成。业务代码只传入用户、资源路径和权限动作，不直接关心角色矩阵、父路径继承、过期时间、Owner 兜底等细节。

必须检查：

- 服务树查询：只返回可见节点。
- 打开 function 详情：`read`。
- Form 提交：`write`。
- Table 查询：`read`。
- Table 新增/修改：`write`。
- Table 删除：`delete`，仅 Admin/Owner 默认拥有。
- Chart 查看/打开：`read`。
- Chart 查询/刷新数据：`write`。
- Docs 查看/新增/更新/删除：`read` / `write` / `update` / `delete`。
- 新增目录：`admin`。
- 编辑目录：`admin`。
- 移动目录：`admin`。
- 删除目录：`delete`，仅 Admin/Owner 默认拥有。
- 创建函数节点：`admin`。
- 删除函数节点：`delete`，仅 Admin/Owner 默认拥有。
- AI 修改应用：`admin`。
- 构建/发布应用：`admin`。
- 安装能力包/应用包：`admin`。
- 导入/导出能力包：`admin`。
- 删除节点/应用：`delete`，仅 Admin/Owner 默认拥有。
- 邀请/移除成员：`admin`。
- 修改成员角色：`admin`。
- 查看/导出操作日志：`admin`。

不需要权限检查或只需要认证：

- 登录。
- 注册。
- 刷新 token。
- 当前用户信息。
- 健康检查。

## 14. 权限 SDK / 服务层设计要求

权限相关代码会被高频调用，必须做成项目基础能力，不能散落成重复判断。

建议新增统一包，例如：

```text
pkg/access
```

或：

```text
pkg/teamaccess
```

后端业务服务只依赖这个包暴露的能力，不直接读写权限表。

建议核心接口：

```go
type PermissionAction string

const (
    PermissionRead   PermissionAction = "read"
    PermissionWrite  PermissionAction = "write"
    PermissionUpdate PermissionAction = "update"
    PermissionDelete PermissionAction = "delete"
    PermissionAdmin  PermissionAction = "admin"
    PermissionOwner  PermissionAction = "owner"
)

type Checker interface {
    Check(ctx context.Context, tenantUser, app, username, resourcePath string, action PermissionAction) error
    Can(ctx context.Context, tenantUser, app, username, resourcePath string, action PermissionAction) (bool, error)
    Resolve(ctx context.Context, tenantUser, app, username, resourcePath string) (*PermissionResult, error)
}

type Manager interface {
    Assign(ctx context.Context, req AssignRoleRequest) error
    BatchAssign(ctx context.Context, req BatchAssignRoleRequest) error
    Remove(ctx context.Context, req RemoveRoleRequest) error
    ListMembers(ctx context.Context, tenantUser, app, resourcePath string) ([]MemberAccess, error)
}
```

建议统一封装这些逻辑：

- 固定角色到权限点的映射。
- 父路径继承计算。
- 多角色并集计算。
- `expires_at` 过期过滤。
- Owner 兜底。
- 服务树节点权限计算。
- 权限变更操作日志。
- 常用 HTTP middleware / helper，例如 `RequirePermission(action)`。
- 前端权限 helper 的类型定义和响应结构约定。

业务代码推荐写法：

```go
if err := access.Check(ctx, tenantUser, app, username, resourcePath, access.PermissionAdmin); err != nil {
    return err
}
```

或：

```go
router.POST("/directories", access.RequirePermission(access.PermissionAdmin), handler.CreateDirectory)
```

禁止写法：

- 在 handler 里直接查询 `workspace_role_assignment`。
- 在多个 service 里重复写角色矩阵。
- 用字符串散落判断，例如 `if role == "admin" || role == "owner"` 到处复制。
- 每个业务模块自己实现一套父路径继承。
- 前端组件里到处写 `roleCode === "admin"` 这类散落判断。
- 前端隐藏按钮后，后端不再检查权限。

前端也应有统一 helper / composable，例如：

```text
web/src/architecture/presentation/composables/useAccessControl.ts
```

前端只消费后端返回的 `permissions`，用于按钮显示、菜单禁用和无权限提示。安全判断仍以后端为准。

推荐前端调用方式：

```ts
const canCreateDirectory = can(node.permissions, 'admin')
const canDeleteRecord = can(row.permissions, 'delete')
```

第一版不需要设计成复杂插件系统，但包边界必须清晰。以后 Table、Form、Docs、服务树、应用包、成员管理都会调用它，所以宁可现在多封装一层，也不要后面补救。

## 15. 操作日志要求

本次应新增通用操作日志表，用于记录平台级审计事件。现有 `TableOperateLog` 可以继续保留，专注记录 Table 数据变更；新的通用操作日志用于记录成员、权限、应用包、应用修改、文件等关键事件。

建议表名：

```text
operate_logs
```

或：

```text
audit_events
```

推荐字段：

```text
id
tenant_user
app
actor_user
action
resource_type
resource_path
resource_name
target_user
target_id
summary
details_json
old_values_json
new_values_json
status
source
ip_address
user_agent
trace_id
created_at
```

说明：

- `action` 使用稳定枚举，例如 `team.role.assigned`、`app.deleted`、`bundle.exported`。
- `summary` 存人类可读文案，方便前端直接展示。
- `details_json` 存扩展结构化数据，方便筛选和后续合规导出。
- `old_values_json` / `new_values_json` 用于记录变更前后值。
- `status` 记录 `success` / `failed`。
- 不建议只存纯字符串日志，否则后续筛选、导出、国际化和前端渲染都会变困难。

权限系统上线时，至少记录以下事件：

- 成员被邀请。
- 成员被移除。
- 成员角色被修改。
- 应用包被导入。
- 应用包被导出。
- 应用被安装。
- 应用/节点被删除。
- 目录被新增/编辑/移动/删除。
- 函数节点被创建/删除。
- AI 修改应用。
- 构建应用。
- Table 新增/修改/删除。
- 文件上传/下载。

日志格式建议：

- 结构化字段。
- 人类可读 summary。

例如：

```json
{
  "actor": "alice",
  "action": "team.role.assigned",
  "resource_path": "/alice/ops",
  "target_user": "bob",
  "summary": "Alice assigned Member to Bob on /alice/ops",
  "details": {
    "role_code": "member"
  }
}
```

现有 `TableOperateLog` 可以继续保留，作为 Table 变更日志。  
新增的 `operate_logs` / `audit_events` 记录平台级事件。两者可以先并存，后续再考虑统一查询视图。

## 17. 建议实施步骤

### 第一步：模型和服务

- 在 SDK / service 内写 `CheckPermission(ctx, username, resourcePath, action)`。
- 在 SDK / service 内写父路径继承、过期过滤和 owner 兜底。

### 第二步：API

- 成员列表。
- 赋权。
- 移除。

### 第三步：服务树

- 查询服务树时计算当前用户权限。

### 第四步：后端关键 API 检查

- Table/Form/Chart。
- service tree mutation。

### 第五步：前端

- 简单成员管理 UI。
- 节点操作按钮按权限显示。

## 18. 测试要求

至少覆盖：

- Owner 永远有所有权限。
- Admin 可以管理成员和应用。
- Member 可以运行和写业务数据，但不能管理成员/导出应用包。
- Member 不允许删除记录。
- Member 不允许新增、编辑、移动、删除目录。
- Member 不允许创建或删除函数节点。
- Admin/Owner 可以管理目录结构。
- Viewer 只能读。
- 父目录授权对子节点生效。
- 子节点授权时父目录作为容器展示。
- 无权限节点不出现在服务树中。
- 后端敏感 API 无权限时拒绝。
- 权限判断统一走 SDK / service，业务接口不直接复制角色判断。
- 多角色并集、过期权限过滤、Owner 兜底都有单元测试。
- 移除成员后权限立即失效。
- 权限变更写入操作日志。

## 19. 对外口径

可以说：

> Built-in role-based access control for small teams.

或：

> Team access with Owner, Admin, Member, and Viewer roles.

不要说：

> Enterprise compliance-ready.
> SOC2-ready.
> Full enterprise RBAC.

更稳的表达：

> Designed for small teams with role-based access control and basic auditability. Enterprise compliance features are on the roadmap.

## 20. 最终判断

这个轻量权限系统值得做，也不会把项目拖成企业版。

它的目标不是满足大企业合规采购，而是让项目具备海外中小企业最基本的团队使用安全：

- 有角色。
- 有授权。
- 有后端权限判断。
- 有可见范围控制。
- 有通用操作日志表，关键操作都能被审计。

这足以让产品从个人开源 preview 进入 small-team beta。
