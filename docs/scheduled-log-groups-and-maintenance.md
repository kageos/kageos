# 任务调用日志与日志归档

操作日志主要回答谁做了什么、结果如何。定时任务调用不再混入普通操作日志，不再生成每日摘要、结果分组、正文去重或逐次投影。

## 存储与入口

- `operate_logs`：人工操作、Agent 代执行的变更、任务创建/修改/启停/立即执行等管理记录。
- `scheduled_execution_logs`：带定时来源的 Form、Function、Table 调用记录；包含原始发生时间、实际操作者、来源引用、Trace、耗时、已脱敏的请求和响应。自动任务内的调用写到这里，手动点击立即执行也通过同一任务执行链记录结果。
- 定时任务详情 → 任务调用日志：逐条查看近期调用，按任务 ID 精确筛选。调度器原有执行记录继续显示排队、运行、跳过、失败等状态；它属于调度控制数据，本次归档针对上述两张业务日志表，不自动删除调度器执行记录。
- 目录 / 函数详情 → 操作日志 → 日志归档（与「当前日志」切换，默认展示当前日志）：所属目录或函数管理员进入归档清单，可看到归档时间、日志类型、工作空间、原文时间范围、条数、大小、成功/失败计数、涉及路径、状态，下载 `JSONL.gz` 原文。系统设置不再展示或管理归档文件；平台维护任务仍负责每日执行归档。

普通日志查询默认只读操作表；`GET /workspace/api/v1/operate_log/general?log_kind=scheduled&task_id=123&resource_path=...` 读取独立调用表，复用原来的路径访问授权。两张表的 ID 分别生成，不能跨表使用。管理记录不因来源是 scheduled_task 而被隐藏。

## 每日归档规则

默认北京时间每天 03:20 检查一次，有符合条件的记录才生成归档：

| 配置 | 默认 | 含义 |
| --- | --- | --- |
| `KAGEOS_LOG_ARCHIVE_SCHEDULED_RETENTION_DAYS` | 7 | 定时调用成功和失败记录统一保留最近 7 天 |
| `KAGEOS_LOG_ARCHIVE_RETENTION_DAYS` | 90 | 普通操作日志至少在线保留 90 天 |
| `KAGEOS_LOG_ARCHIVE_MIN_RECORDS` | 1000 | 同一精确资源路径的过期普通日志达到该数量才归档 |
| `KAGEOS_LOG_ARCHIVE_BATCH_SIZE` | 10000 | 每个归档文件最多记录数 |
| `KAGEOS_LOG_ARCHIVE_MAX_BATCHES` | 1000 | 单轮最多批次，达到后下次继续 |
| `KAGEOS_LOG_ARCHIVE_CRON` | `20 3 * * *` | 每日检查时间 |
| `KAGEOS_LOG_ARCHIVE_TIMEZONE` | `Asia/Shanghai` | 调度时区 |

数量按租户、工作空间、精确资源路径计算。目录自己的日志、各个子目录和函数分别计数，不递归叠加，避免热门函数带走低频目录的历史。一天一条的路径可以长期在线保留。达到门槛只归档过期记录；近期记录、结果尚未确认的 pending 记录不归档。批次完成后不足门槛的剩余普通记录等待后续积累。

旧的 `KAGEOS_LOG_ARCHIVE_SCHEDULED_SUCCESS_RETENTION_DAYS` 不再生效；新配置同时覆盖调用成功和失败。不存在每日都生成空归档或必须每天生成一个文件的要求。

## 完整性、失败恢复和旧数据

1. 选定一批原始 ID 并持久化批次。
2. 流式导出 `JSONL.gz`，校对条数。
3. 上传对象存储，下载校验大小及 SHA256，确认对象入库。
4. 持久化已校验状态后，仅删除该批所属日志表中的选定 ID。
5. 保存完成状态；断线和中途失败按照持久化阶段重试。校验失败不删除原文，清理后完成状态写入失败可以幂等重试。

启动时在归档互斥锁下分批迁移旧表中的自动调用，每批在同一事务内复制及删除，保留 `original_log_id`、发生时间和原文，不会与新表独立生成的 ID 冲突。已有未完成归档选中的旧记录不迁移，由旧归档继续处理，完成后通过归档清单下载。大库首次升级的启动时间会受待迁移记录数影响；不要新旧版本混跑，否则旧写入端仍会写回操作表。

已有归档文件、归档索引以及旧分组数据库表不会被删除或重建。新版本不再读写分组表，不再自动建这些表；旧的两个分组定时任务在启动协调时取消。保留旧分组表是为了避免未经核对删除历史唯一副本；不再占用持续回填和汇总开销。后台迁移、归档失败会报错，不能当作处理完成。

## 下载后分析

文件每行是一条完整、已按原有规则脱敏的日志，JSON 字段代码保持不变。归档索引保存文件 SHA256，可校验后用 Python、jq 或其他支持 JSONL 的工具分析，无需恢复业务数据库。

```sh
gzip -dc downloaded-logs.jsonl.gz | jq -c 'select(.status == "failed") | {created_at, resource_path, source_ref, trace_id, details_json}'
```

批次 `summary_json` 仅保存确定性统计：`status_counts`、最多 20 个路径计数、格式版本和日志类型。它不是业务结果摘要，也不推断应用业务是否成功。

## 其他系统维护任务

系统设置 → 系统定时任务继续提供平台用量快照（02:00）、数据库与磁盘容量快照（02:30）、日志归档（03:20）、应用版本和临时文件清理（04:00）、孤立定时任务清理（04:30）、应用数据库软删除清理。系统备份复用原宿主机备份代理。系统任务的立即执行与暂停只允许 system 管理员，长任务使用心跳与持久化归档进度。

## 归档资源权限

归档索引保存 `resource_path`。列表、下载、重试使用 `/workspace/api/v1/log_archives` 下的资源接口，要求归档实际资源的 Admin/Owner 权限。目录列表覆盖自身及子路径，函数列表只包含该函数的文件，路径中的 `%`、`_` 按字面量处理。界面在「操作日志」内根据已有资源权限显示「日志归档」切换项，原 `_panel=logArchives` 链接仍直接打开归档视图，后端始终单独校验权限，不相信前端传来的批次编号或目录。

新批次每个文件只归档同一精确资源路径。历史文件仅在完整计数证明只包含一个路径时补齐资源归属；混合工作空间文件仍归属整个工作空间，只允许工作空间管理员访问，不把完整文件下放给其中某个子目录管理员。已有系统归档 API 保留兼容用途，不再提供系统设置中的归档页面。

### 归档批次详情

列表与详情时间统一按设备时区显示为 `YYYY-MM-DD HH:mm:ss`。展开批次展示日志起止时间、总条数、已有结果统计与占比、资源分布（最多前 20 项），以及文件名称、压缩大小、格式、SHA256、批次创建/归档完成/原文清理时间和重试信息。概览由批次元数据生成，统计使用归档时保存的数据；历史批次未保存的统计明确提示缺失，不补零或推断成功。
