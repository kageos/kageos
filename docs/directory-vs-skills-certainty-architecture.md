# 目录 vs Skills：确定性架构论证

> 状态：核心战略论证
> 日期：2026-06-17

本文从架构和商业两个维度，论证为什么 kageos 的目录模型在长期竞争中优于 Agent Skills 模型。这不是功能对比，是底层逻辑的论证。

## 一句话结论

> 目录是确定性的基础设施，AI 是不确定性的增强层。确定性做底座，不确定性做加速，这是唯一能在生产环境站住的架构。

## 问题起源

AI 降低了应用生产成本，催生了 Skills 生态——给 AI 一个 prompt + 工具定义，AI 就能完成一类任务。Skills 上手快、传播快、生态扩张快，但它的天花板也很明显：**Skills 的底座是 AI 模型，而 AI 模型是不确定的。**

kageos 选择了另一条路：**用确定性的代码和运行时做底座，让 AI 做增强。** 这不是"更保守"的选择，是"更可能站住"的选择。

## Skills 的五个根本缺陷

### 1. 没有状态——执行完就没了

一个 Skill 执行完就结束了。它不会记住上次的结果，不会积累数据，不会成长。

kageos 的 Agent 任务为什么能 486 次执行 0 失败？因为每次执行的结果存在 Table 里，历史存在日志里，配置存在目录里。Skill 做不到这个——它每次都是失忆的。

没有状态意味着没有积累。一家公司用了 100 次 Skill，跟用了 1 次，没有任何区别。没有数据沉淀，没有流程沉淀，没有组织记忆。

### 2. 不能可靠组合——靠 AI 理解力做类型转换

Skills 之间没有契约。A 输出自然语言，B 期望结构化数据，靠 AI 翻译，每一步都可能出错。

```
Skill A 输出："今天天气不错，温度25度"
Skill B 期望输入：{ temperature: number, condition: string }
```

谁来翻译？AI。翻译准不准？看运气。这就是为什么 multi-agent 编排又慢又贵又不稳——每一步都在靠模型理解力做类型转换，每一步都是潜在的失败点。

kageos 目录的每个函数都有标准入参出参：

```go
type SearchRequest struct {
    Keyword  string `json:"keyword"`
    PageSize int    `json:"page_size"`
}

type SearchResponse struct {
    Articles []Article `json:"articles"`
    Total    int       `json:"total"`
}
```

编排靠标准接口确定性连接，不需要 AI 理解力做类型转换，不需要 token，不会因为模型升级而失效。

### 3. 不积累资产——用完即弃

一家公司用了 100 次 Skill，什么也没留下。没有数据，没有流程，没有组织记忆。

一家公司用了 100 次目录，它有了：
- Table 里的数据（谁提交了什么、什么时候异常过）
- 权限记录（谁有权限访问什么）
- 审计日志（谁在什么时候做了什么）
- AI 上下文（这个目录是干什么的、怎么用）

这些是资产，Skill 产生不了资产。

### 4. 只有 AI 一个用户——人不能直接用

Skills 只有 AI 一个用户。人不能直接打开一个 Skill 去操作——你必须通过对话，让 AI 帮你做。

但现实中很多事是人要直接做的：看一眼今天的工单列表、手动改一个配置、查一下某个客户的历史记录。

目录同时服务于人和 AI。人可以打开 Table 直接看，AI 可以通过函数调用读。两条路径到达同一个数据源，不是两个割裂的系统。

### 5. 绑死在 AI 模型上——模型一变全崩

GPT-4 能跑的 Skill，GPT-4o 可能跑不了。换了 Claude 全部重写 prompt。模型厂商改个 API，下游全部崩溃。token 费用跟调用量线性增长，没有规模效应。

kageos 目录里跑的是 Go 代码，在容器中执行，跟 AI 模型无关。今天用 GPT-4 当 agent，明天换 Claude，后天换国产模型——目录里的代码、数据、权限、日志一个字都不用改。

企业不应该因为模型厂商的任何变动（涨价、关停、API 变更）而失去自己的业务能力。

## 确定性 vs 不确定性：底层逻辑

把 Skills 的所有缺陷拆开，底层都是同一个问题：**不确定性**。

| 你说的 | 底层逻辑 |
|---|---|
| 模型能力参差不齐 | Skills 的输出不确定 |
| Skills 消耗 token | Skills 的成本不确定 |
| 模型公司没了转不动 | Skills 的存续不确定 |
| 目录有标准入参出参 | 目录的接口确定 |
| 没有 AI 用户照样用 | 目录的价值确定 |

企业决策的底层逻辑不是"哪个功能更强"，是"哪个我能依赖"。一个 CIO 选型时想的是：这东西会不会明天就挂了？换个人来能不能接着用？模型升级了会不会全崩？一年下来要花多少钱？

对这四个问题，Skills 的答案全是"不确定"，目录的答案全是"确定"。

## AI 只是目录的一个用户

这个认知彻底翻转了人和 AI 的关系：

```
Skills 的世界观：人 → AI → 工具
                  （AI 是中间层，人必须通过 AI）

目录的世界观：人 ←→ 目录 ←→ AI
              （人和 AI 是平等的用户，目录是共享的基础设施）
```

在 Skills 的世界里，AI 是瓶颈——AI 挂了人啥也干不了，AI 理解错了结果就错了，AI 换了个模型行为就变了。

在目录的世界里，AI 是增强——AI 在的时候帮你自动化，AI 不在的时候你自己点页面，结果一样。AI 让你更快，但不决定你能不能做。

这意味着：
- 企业可以先不接 AI，只用目录的 UI——人点页面一样完成工作
- AI 在的时候是增强，不在的时候业务不停
- 换 AI 模型不影响任何目录里的代码、数据、权限、日志
- 企业不会因为模型厂商的任何变动而失去业务能力

## 生产验证：486 次执行 0 失败

热点情报定时推送是目录模型被真实生产环境验证的证据：

- **场景**：每 15 分钟自动搜索 AI/创业/行业热点 → AI 分析 → 推送到企微群
- **架构**：定时触发 → 跨目录调用（hot_news → weixin → wecom）→ AI 分析 → 外部渠道推送 → 手机收到
- **数据**：486 次执行，0 失败，连续运行超过 15 天
- **关键**：每一步的输入输出都是确定的，不是靠 AI 理解力拼凑的

这五步链路中，每一步都是 kageos 平台的核心能力，而且是**只有 kageos 的目录模型能一次性走通的**：

| 步骤 | 对应能力 | Skills 能不能做 |
|---|---|---|
| 定时触发 | timer-scheduler + Agent 任务 | 大部分不能，或者只能调 webhook |
| 跨目录调用 | namespace + Service Tree | 没人做这个 |
| AI 分析 | agent-server | 通用能力，但上下文是目录内的 |
| 外部渠道推送 | wecom connector | 需要自己接 API |
| 手机收到 | 企微群机器人 | 最终交付 |

单独看每一步都不稀奇，但串起来是一个完整的、不需要人介入的自动化流程。这个组合在市场上很难找到替代品。而它之所以能 486 次 0 失败，根本原因是**每一步的接口都是确定的**——不是靠 AI 理解力在运行时临时拼凑。

## 目录吞噬 Skills

kageos 不需要跟 Skills 对着干。市场上已经有大量的 Skills 生态——OpenAI、Anthropic、各种 Agent 框架。正确的做法是：**目录是核心，但目录可以暴露为 Skill。**

每个目录天然可以对外表现为一个 Skill——AI 看到的是函数签名 + 描述，背后跑的是完整的目录运行时。这样：

- AI 用 Skill 的方式调用目录 → 低门槛，跟生态兼容
- 调用进来的东西有状态、有治理、有数据、可组合 → 高天花板
- 用户不需要选"用 Skill 还是用目录" → 目录就是更强的 Skill

这不是 Skills vs 目录，是目录吞噬 Skills。

这跟"挂树即治理"完全一致：能力进目录就自动获得一切——包括对 AI 的 Skill 化暴露。这才是终局。

## 比喻：打车 vs 买车

Skills 是打车，目录是买车。

- 打车：立刻能用，不用维护，但每次都要重新叫，没有积累，不能改造，不能加配件
- 买车：前期投入大，要上牌要保养，但它是你的，可以改装，可以积累里程，可以借给别人用，可以卖掉

短期看打车合算。但一个每天都要出行的人，最终会买车。

**企业就是那个每天都要出行的人。**

## 完整对比

| 维度 | Skills 生态 | kageos 目录 |
|---|---|---|
| 核心依赖 | AI 模型 | 代码 + 运行时 |
| 确定性 | 不确定（依赖模型理解力） | 确定（标准入参出参） |
| 成本模型 | token 随调用线性增长 | 代码执行，固定成本 |
| 模型切换 | 需要重写 prompt | 换个 agent 就行，目录不动 |
| 没有 AI | 完全不能工作 | 人在页面上照样用 |
| 编排 | 靠 AI 理解力拼接，脆弱 | 靠标准接口确定性连接，可靠 |
| 数据积累 | 无状态 | 有状态，可审计，可查询 |
| 状态 | 执行完就没了 | 持久存在，可定时触发，可积累 |
| 人可操作性 | 只能通过 AI | 人可以点 UI，AI 可以调函数 |
| 治理 | 靠宿主平台 | 权限、审计、日志、版本、trace |
| 企业信任度 | 低（不确定性太高） | 高（确定性做底座） |
| 上手速度 | 快（5 分钟写一个 Skill） | 慢（需要写代码、编译、部署） |
| 天花板 | 低（无状态、不可靠、不可积累） | 高（有状态、可靠、可积累、可治理） |

## 对 kageos 产品定位的意义

目录不是一种更好的 Skill，目录是 **AI 时代的应用基础设施**。

它的定位不是"给 AI 用的工具"，而是"人机共享的能力基础设施"。AI 是用户之一，不是唯一用户。人也是用户，定时任务也是用户，未来的工作流引擎也是用户。

对外表达的时候：

> 别人的思路：让 AI 更强，让 AI 能做更多事
> 
> 我们的思路：让能力更确定，让 AI 和人都能可靠地使用它

前者赌的是 AI 会持续进步，后者赌的是确定性永远是刚需。哪个赌注更安全，一目了然。
