# kageos 平台边界

## 平台形态

kageos 工作空间应用只能由三种主要模板组合：

| 模板 | 用途 | 典型场景 |
|---|---|---|
| `TableTemplate` | 管理一批记录 | 合同台账、客户列表、工单、预约、配置 |
| `FormTemplate` | 一次提交执行一个动作 | 文件解析、生成报告、手动巡检、外部同步 |
| `ChartTemplate` | 从已有数据做标准图表 | 趋势、排行、分布、仪表盘单图 |

不要承诺或实现自定义 HTML/React/Vue 页面、CSS 布局、复杂前端交互、实时协同页面、长连接服务或任意 dashboard。若用户要纯展示 HTML 或一次性产物，可考虑 `/system/tools`；若要长期业务系统，必须落到 Form/Table/Chart。

Docs、runbook、AgentTask、通知、定时任务是辅助能力。它们可以帮助系统运行，但不改变用户界面的三种主要形态。

## 简单设计优先

默认从最小可用版本开始。先把用户说的“大系统”收成一个能马上用的小工具，再决定 Form/Table/Chart 组合。

每次设计前先问：

```text
用户真正要解决的一个问题是什么？
有没有更小、更直白的名字？
最少几个字段和入口能跑通？
哪些增强能力这次明确不做？
```

默认从一张主 Table 或一个主 Form 开始：

| 需求 | 默认设计 |
|---|---|
| 合同管理 | 先收成“合同到期提醒”：`contracts.table` + 可选 `scan_expiring.form`，字段只保留合同名、相对方、到期日、负责人、状态、下一步、附件 |
| 客户管理 | 先收成“客户跟进提醒”：`customers.table`，字段只保留客户名、联系人、阶段、负责人、下次跟进、备注 |
| 证书管理 | 先收成“证书到期提醒/巡检”：`certificates.table` + 可选 `scan_expiring.form`，字段只保留域名、证书、到期日、负责人、状态 |
| 工单管理 | `tickets.table`，字段含标题、状态、优先级、负责人、处理备注 |
| 收银系统 | `products.table` + `checkout.form` + 只读 `payments.table`，统计图后置 |

升级条件：

- 拆新 Table：对象有独立生命周期、独立历史、独立负责人、一个主对象下有多条明细，或需要跨对象聚合。
- 加 Form：动作不能自然表达为 Table 新增/编辑/状态更新，且需要临时参数、文件、确认或外部副作用。
- 加 Chart：已有数据后，用户确实需要趋势、分布、排行、汇总。
- 加 AgentTask：需要无人值守判断、跨工具查询、周期性维护长期数据。

不要为了“完整”默认创建申请表、节点表、日志表、审批表、队列表、批处理 Form、统计图、权限模型或配置中心。

字段默认控制在 6-10 个用户能理解的字段。系统字段、运行标记、通知次数、冷却时间、内部归属信息默认隐藏，不要暴露给用户当作业务字段。

## 应用侧和平台侧

应用侧能做：

- 字段、表格、表单、图表、业务状态、文件处理、数据写入和查询。
- 用 `ctx.GetGormDB()` 处理业务库。
- 用 SDK 通知能力发送业务通知。
- 用 Form schedule 或平台自动化触发已有函数。

平台侧不要在业务应用里重造：

- UI 渲染、组件样式、响应式布局、通用交互。
- 通用权限、审批、评论、收藏、操作日志。
- 通用通知队列、渠道投递、定时调度器。
- 自定义前端页面和复杂 dashboard 容器。

当前还不要主动暴露部门能力：新应用默认不生成 `department` / `departments` 组件、所属部门字段或 `ctx.GetRequestUserDept()`。部门相关能力还没完善，只有用户明确要求或维护已有部门逻辑时才使用。

## 文件边界

工作台路径不是磁盘路径：

```text
/<user>/<app>/<package...>
=> namespace/<user>/<app>/code/api/<package...>
```

只改这些位置：

- `namespace/<user>/<app>/code/api/<package...>/*.go`
- 必要时改 `namespace/<user>/<app>/code/cmd/app/main.go`
- 必要时改 `namespace/<user>/<app>/go.mod` / `go.sum`

不要改：

- `core/...`
- `kageos-sdk/...`
- kageos 主仓库根模块
- 其他 workspace 应用
- skill 自身，除非用户明确要求改 skill

## 开发前检查

动手前用一句话写清：

```text
本需求用哪些模板组合：Table / Form / Chart？
为什么不是一张主 Table 就够？
我参考了哪个完整案例？
本地 PRD 是否用 Markdown 表格并带示例数据？
```

如果不能回答，就先不要写代码。
