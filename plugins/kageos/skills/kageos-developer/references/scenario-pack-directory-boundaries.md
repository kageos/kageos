## 基本模型

把场景包、目录和目录内资源视为三个不同层级：

| 层级 | 负责什么 | 数据含义 |
|---|---|---|
| 场景包 | 面向同一类客户组织、推荐和组合安装产品 | 不拥有业务数据库，不隐含目录之间已经集成 |
| 目录 | 完成一个可独立运行的业务闭环 | 独立数据库、独立生命周期、独立 HTTP 边界 |
| 目录内资源 | 表达同一闭环里的台账、动作、统计和说明 | 可以共享本目录数据库并保持一致 |

目录嵌套或同属一个场景包只表达产品关系，不赋予跨库读写能力。不同目录之间不能使用数据库关联、共享事务或直接引用对方的运行态记录；如果需要协作，只能使用经过验证的 HTTP 能力。

## 拆分决策

先为每项能力写出核心业务对象，例如订单、维修工单、租赁单、合同、巡检问题。然后逐项判断：

| 问题 | 是 | 否 |
|---|---|---|
| 是否操作同一批核心记录？ | 倾向同一目录 | 可以继续评估拆分 |
| 一个动作是否必须同时更新两边？ | 倾向同一目录 | 可以拆分 |
| 短暂不一致是否会导致业务错误？ | 倾向同一目录 | HTTP 摘要或交接可能足够 |
| 任一部分能否独立安装并完成闭环？ | 可以拆成独立目录 | 合并或缩小功能 |
| 是否只是面向同一客户、但解决不同问题？ | 放入同一场景包的不同目录 | 继续判断数据内聚性 |
| 是否为了“以后可能联动”才设计通信？ | 先不通信 | 只实现已证实的交接 |

硬判断：

- 如果分成两个目录后，A 的首次使用必须先配置 B，通常应合并或重划边界。
- 如果两项功能只是可以互相跳转、互相推荐或由同一个负责人使用，不构成合并理由。
- 如果一个业务对象拥有独立负责人、独立状态、独立历史且能单独关闭，可以成为独立目录；否则优先留在原目录。
- 如果需要持续同步客户、商品、供应商、订单或库存主数据，当前方案已经接近 ERP 或集成平台，应主动收缩。

## 三种推荐结构

### 多个独立目录

默认结构。每个目录零集成也能成立，场景包负责共同定位和安装推荐。

```text
采购协作场景包
├── 采购询价
├── 供应商入驻材料
├── 采购到货催办
└── 到货差异处理
```

### 一个核心目录

核心对象和过程不可分，目录内部再用 Table/Form/Chart 组织入口。

```text
设备租赁目录
├── 设备台账
├── 租出登记
├── 续租处理
└── 归还验收
```

### 核心目录加独立工具

核心过程保持同库，周边低耦合能力成为可选目录。

```text
设备售后场景包
├── 售后维修（核心目录：报修、处理、配件、验收）
├── 维保到期提醒（独立目录）
└── 客户满意度（独立目录）
```

## 跨目录 HTTP 门禁

跨目录 HTTP 只有在真实业务交接已经被证实时才增加。设计前必须回答：

1. 为什么不能由用户在目标目录手工新建或导入？
2. HTTP 失败时，来源目录是否仍保持完整、可用和可重试？
3. 哪个目录是每个字段的唯一权威来源？
4. 请求重复发送时，目标目录如何避免重复记录？
5. 安装者在哪里配置 endpoint 和凭证，如何诊断连通性？
6. 用户在主表哪里看到未配置、处理中、成功、失败和重试结果？

实现约束：

- 每次只完成一个明确交接，不设计 A → B → C 的同步调用链。
- 先保存来源目录的有效记录，再执行远端交接；远端失败不得破坏来源记录。
- 使用稳定幂等键；超时后允许安全重试。
- 只传下游完成任务所需的最小字段，不复制完整业务对象。
- 不做跨库事务、循环回调、全量双向同步或隐藏式最终一致性承诺。
- 远端状态只能作为带更新时间的摘要缓存；修改仍由权威目录负责。
- token 不得进入代码、普通字段响应、日志、通知、文档、截图、示例数据或 Hub 包。
- 如果平台尚未提供可靠的目录发现、范围受限鉴权或失败恢复机制，就把互通列为后续增强，不得伪装成已可用能力。

## 设计输出模板

每次规划场景包时先输出下表，再进入单个目录 PRD：

| 场景包 | 目录 | 核心业务对象 | 独立闭环 | 是否独立安装 | 共享数据需求 | HTTP | 结论 |
|---|---|---|---|---|---|---|---|
| 示例 | 采购询价 | 询价单 | 收集报价并完成比较 | 是 | 无 | 不需要 | 独立目录 |

随后补充：

- 目标客户和共同问题。
- 推荐安装顺序，但不得伪装成强制依赖。
- 核心目录、可选目录和替代目录。
- 现有 democase 的复用方式。
- 每个目录的五分钟价值路径。
- V1 明确不做的共享主数据、跨目录同步和外部集成。

## 典型例子

### 应拆成多个目录

- 采购询价、供应商入驻、采购到货催办：服务同一采购团队，但各自有完整输入、处理和关闭结果。
- 访客预约、快递领取、会议室预约：同属行政后勤，但没有共享核心记录。
- 网站监控、域名到期、证书到期：同属 IT 运维，但每项监控可以独立安装。

### 应放在同一个目录

- 设备租出、续租、归还、损坏验收：共享设备和租赁单，状态必须一致。
- 客户报修、维修过程、配件使用、客户验收：共同围绕一张维修工单。
- 订单交付阶段、延期异常、催办记录：共同围绕订单交付事实。

### 应先停止并重划边界

- 两个目录需要实时共享全部商品、库存和订单数据。
- 一个目录安装后必须填写另一个目录的地址和 token 才能新增第一条记录。
- 为了在多个目录之间保证一次业务动作全部成功而设计分布式事务。

这些通常说明目录拆得太碎，或者产品已经越过轻量场景工具边界，正在变成 ERP 或集成平台。
