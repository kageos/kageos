# 工作流产品质量规则

用于内容工厂、审核流、发布包、自动复盘、个人生产力工具集等明确多表/多动作场景。不要用本文件把简单台账、简单提醒、简单附件管理升级成复杂系统。目标是做出“人只看少数清楚入口，AI 在后台跑必要流程”的目录，而不是暴露数据库后台。

## 简单优先

先判断最低可用产品形态：

- 一张主 Table 能解决的，就只做一张主 Table。
- 一张主 Table 加定时扫描/回调能解决的，不要拆节点表、日志表或今日待办。
- 只有独立生命周期、独立审计、多次历史、跨对象聚合、外部动作参数或明确多角色协同时，才拆新 Table/Form。
- Chart、AgentTask、runbook、审批流是增强，不是默认 MVP。

## 不延迟本可当场解决的问题

- 用户提交时可确定的必填、格式、附件、权限、关联存在性、状态合法性、确定性重复和计算错误，必须同步校验并当场反馈。
- 耗时校验如果决定记录是否有效，先进入“草稿/校验中”，通过后才进入“已受理”；不能先成功、后报错。
- 后台只承接后来才出现的状态、持续观察、外部回执、跨记录分析和语义调度。它的价值是减少盯守与查询，不是增加退回与补交。
- 自动化必须把结果回写主工作台并定义停止条件；没有后续动作的日报不算业务闭环。

## 产品建模顺序

1. 先判断最低复杂度：用户是否只需要一张类似 Excel 的智能表格？如果是，停在这里，不要继续拆系统。
2. 再画一条主流程：用户输入什么，AI/系统生产什么，人在哪里确认，发布后如何复盘。
3. 再分对象类型：
   - 配置表：账号、素材源、平台配置，可 CRUD。
   - 任务表：选题、生成任务，可人工创建，状态由系统流转。
   - 内容对象表：草稿、选题、素材等可由人或 AI 新增/编辑；优先用 `OnTableAddRow/OnTableUpdateRow` 承载，不要为同一件事另造 Form。
   - 事实/流水表：发布记录、复盘结果、外部回执等默认只读或只允许状态/备注动作；状态动作优先用 `OnTableUpdateRow`。预览这类“当前内容的派生产物”优先挂在内容对象表上，不要默认拆表。
   - 主工作台：待审、待发布、失败重试、今日任务，优先用 table/list 承载人的日常工作。
   - 后台动作：生成文件、发布包生成、跨系统发布、复盘统计，用 Form 或 AgentTask 承接；不要把普通新增、编辑、审核状态更新包装成 Form。
4. 最后落 SDK 路由，不要从“有哪些表”倒推产品。

## 上游选择与后端补全

只让用户选择业务上真正需要判断的上游对象。选择后能查到的字段，都由后端补齐：

- 选账号后，后端补作者、口吻、默认读者、CTA。
- 选任务后，后端补账号、负责人、目标读者、素材、目标篇数。
- 选草稿后，后端补任务、账号、标题、质量分、正文和预览样式默认值。
- 更新预览状态后，后端同步草稿状态和审核意见；如果平台已有操作日志，不要再建重复审核记录表。

`OnSelectFuzzy` 只用于边界选择，不用于把每个外键都暴露给用户。AI 后台 Form 可以接收上游 ID，但不要要求用户或 AI 重复提交下游 ID。需要联动候选项时使用 `depend_on:<field>`，参考投票案例。

## 外键展示与预加载

外键是系统内部协议，不是用户界面语言。字段可以叫 `profile_id`、`topic_id`、`draft_id`，但可见文案和列表展示必须是“公众号账号/任务主题/草稿标题”等业务名：

- `OnSelectFuzzy` 的 `Label` 要用名称、状态、关键上下文组合，不要只显示 `#1` 或 `ID 1`。
- `DisplayInfo` 至少带主名称和用户判断需要的上下文；`Statistics` 用 `statistics.Value(...)` 显示“选中公众号、选中任务、账号状态”等结果。
- 列表响应用 `Preload` 或二次查询补出 `gorm:"-" widget:"name:...;type:text" hide:"create,update"` 展示字段，例如 `AccountName`、`TopicTitle`、`DraftTitle`、`PreviewTitle`。
- 工作台行里的内部 ID 字段尽量 `widget:"-"`；动作链接通过后端 `ctx.BuildFunctionUrlWithText(...)` 携带 ID，用户只看标题、名称、状态和按钮。
- Form 响应里可以保留 ID 给 AI 或后续动作使用，但 UI 可见字段要优先返回名称/标题/链接；不要让用户读“公众号ID 1/任务ID 2”来理解结果。

## Table 与 Form 的边界

- 可编辑 Table 只给稳定配置或人工维护台账。
- 草稿、选题、配置这类“记录本身”用 Table 新增/编辑；AI 写入草稿也优先走草稿表 `OnTableAddRow`，不要另造 `ai_write_draft.form`。
- 预览如果只是某篇草稿的当前 HTML/PDF/图片产物，优先作为草稿表字段和状态自动落库；不要为“生成预览”单独造 Form 或预览表。
- 发布记录、复盘结果这类系统产物默认不允许手工新增；若人只是在审核、通过、退回、废弃，优先用产物表或主对象表 `OnTableUpdateRow` 更新状态和备注，不要另造 `review_xxx.form`。
- Form 只用于 Table 不能自然表达、且确实需要人工参数或确认的动作，例如调用外部发布接口、生成发布包、跑复盘报告。若生成 HTML/PDF/图片可以由新增记录或状态流转自动触发，就放进 `OnTableAddRow/OnTableUpdateRow` 后台执行。
- 主工作台优先是 Table/List，不是“提交一个 Form 再返回 table”。定时通知 Form 可以存在，但不应替代人的日常列表。
- 不要为 MVP 塞初始化、示例数据、今日清单、批量处理等演示入口；除非用户明确要演示/种子数据，否则让用户从真实表格开始。
- 不要为了“专业完整”默认拆出申请、节点、日志、图表。用户先能填、能筛、能提醒、能关闭，才算好用。
- 列表里用后端查询补出 `gorm:"-"` 的展示字段，例如名称、链接、状态文案、预览文件；不要让用户靠 ID 理解记录。

## 状态流转

- 状态字段尽量由动作函数改变，例如新增待预览草稿后自动生成预览并变“预览已生成”，渲染失败写“预览失败”和错误信息。
- 如果用户在表格里直接编辑状态，使用 `OnTableUpdateRow` 校验状态、同步关联表，并依赖平台操作日志追踪谁改了什么。
- 能实时计算的状态不要落库，例如会议案例按时间计算预约状态。
- 任务规划依赖的数量不要让模型长期口算。目标数、已有数、缺口数、完成率、待处理数、逾期数这类可确定统计，优先作为主工作台的 `gorm:"-"` 展示字段由后端计算，例如“已有草稿数 / 待补篇数 / 生产进度”，Agent 再用明细表复核。比例、完成率和进度优先用 `widget:"type:progress;min:0;max:100;unit:%"` 展示，不要用普通文本让模型再解释。
- 手工改状态只在明确是运营后台能力时开放；普通用户通过动作按钮或表单改变状态。
- 自动任务要幂等：发送前 claim，失败释放；生成/渲染/发布要避免重复执行或保留版本。

## 人与 AI 的界面分离

- 人的入口：维护账号、创建任务、查看草稿、点开草稿行里的预览文件、在草稿表更新通过/退回/废弃、查看复盘。
- AI 的入口：读取 runbook、往草稿表新增草稿或更新待预览草稿；预览生成由表回调自动完成；发布包和复盘报告走后台动作。
- 用户界面不要暴露 prompt、内部 ID、批处理细节和多余配置；这些放 runbook、AgentTask message、后台 Form 或隐藏字段。

## 设计自检

落代码前回答这些问题：

- 用户每天最常打开的一个页面是什么？
- 一张主 Table 是否已经足够？如果不够，具体卡在哪里？
- 哪些表是结果/流水，只能由系统产生？
- 用户选了一个上游对象后，还有哪些字段可以后端查出来？
- 哪些回调选择是必要的，哪些只是弥补了糟糕的信息架构？
- 是否有一个默认待办列表，而不是让用户先提交查询 Form？
- 是否把本该是 `OnTableAddRow` 或 `OnTableUpdateRow` 的事情错误拆成了 Form？
- 是否建了平台操作日志已经能覆盖的重复审核记录表？
- AI 后台可以复杂，但人的界面是否足够少、清楚、可点？
- 是否把提交时已经能发现的问题错误地延迟到后台，造成退回和重新提交？
- 无人值守是否处理了后来才出现的状态或跨记录信息，并把结果回写到有人接手的地方？
