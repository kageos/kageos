# kageos_manifest.go / runbook.docs / AgentTask 写法

`kageos_manifest.go` 用来给一个 kageos package 声明出厂默认资产。第一版只放两类东西：

- `runbook.docs`：目录级运行手册。
- `AgentTask`：某个具体无人值守任务的默认模板。

它们都是 seed，不是长期权威源。build/update 后，平台会把缺失的文档和默认 Agent 任务挂到 Service Tree；后续运行态以树上的 `runbook.docs` 和平台里的任务配置为准。代码里的 `kageos_manifest.go` 只负责首次创建，不应覆盖线上人工维护过的内容。

## 核心区别

`runbook.docs` 是面向业务人员的目录使用说明和稳定处理规则。不了解 kageos、数据库或 Agent 工具的人，也应该能看懂、敢于修改，并用它表达“公司希望事情怎么处理”。Agent 进入目录后，同样以这些业务规则作为判断依据。

`AgentTask.Message` 是某个具体无人值守任务的执行单。它描述一次定时或自动任务如何闭环，例如每天生成公众号草稿、每小时巡检证书、定时搜索新闻并入库。它必须写清本轮任务目标、时间窗口、工具、分页、幂等、去重、写入规则、失败处理和通知规则。

一句话：`runbook.docs` 管“公司希望这类事情怎么处理”，`AgentTask.Message` 管“Agent 到点后具体怎样安全执行”。

## 业务文档与技术执行的边界

`runbook.docs`、`docs/readme.docs` 和 `docs/*.docs` 默认由不懂技术的业务人员长期维护。业务文档写清：什么时候使用、需要哪些业务信息、公司认可的处理步骤、系统能做到哪一步、失败时找谁。不要要求维护者填写 schema、JSON 字段、参数映射、工具名、分页、认领、重试、幂等或数据库实现。

这些技术约束应写入 `AgentTask.Message`、代码或测试。Agent 执行前自行搜索真实资源和 schema，确认参数、权限、影响范围、去重和验证；无法确认就转人工。如果 Form/Table 字段改名后业务文档也必须跟着改，通常说明文档写得太技术化。

## 子目录文档种子

同一个业务 package 需要把文档放到子目录时，仍然使用原来的 `packageContext`，在 `DocManifest.Code` 中填写 package 内相对路径；不要为文档目录额外声明 `PackageContext`：

```go
packageContext.AddDocs(app.DocManifest{
	Code:    "./docs/readme.docs",
	Name:    "文档/目录说明",
	Content: "# 文档目录说明\n",
	Format:  "markdown",
})
```

build/update 时，SDK 自动把缺失的中间目录加入目录对账，并创建 `<当前 package>/docs/readme.docs`。`Name` 是文档展示名称，不是目录名称。`Code` 必须是安全的 package 内相对路径，不允许绝对路径、反斜杠、空路径段、`.` 或 `..`。源码中的新声明统一写 `.docs` 后缀；SDK 会规范化后参与 diff 和对账。

## 资源引用

文档和任务说明里引用当前目录资源时，使用轻量资源标记：

- 当前目录表格：`<./profiles.table>`
- 当前目录表单：`<./send_notice.form>`
- 当前目录图表：`<./risk_report.chart>`
- 当前目录文档：`<./runbook.docs>`
- 同一能力包内的兄弟目录资源：`<../shared/render.form>`
- 用户明确指定的跨工作空间资源：`</alice/support/tickets.table>`（不可移植，复制后需重新绑定）
- 内置 Agent 工具：`<tool:send_notification>`

不要写 `./profiles.table`，也不要写 `<profiles.table>`；所有资源引用都放在尖括号中。选择顺序是：当前目录 `<./...>`，同一可复制能力包的兄弟目录 `<../...>`，最后才是跨工作空间绝对标记 `</...>`。只有用户明确要求绑定其他工作空间，而且无法用稳定相对关系表达时才使用绝对路径；必须在说明中标记“不可移植，复制或安装到其他实例后需重新绑定”。不要为了省事把本可相对引用的资源写成绝对路径。引用内置工具时不要写 `<send_notification>`，因为它不是 Service Tree 资源路径；需要回显工具 chip 时写 `<tool:send_notification>`，真实工具调用名仍是 `send_notification`。

轻量资源标记只提供导航和语义引用，不会自动查询数据。真正查询表格时，Agent 仍要调用 table 工具，并按分页读完。

## runbook.docs 应该写什么

高质量 `runbook.docs` 是一份简短的“使用说明与处理规则”，不是 README、PRD、技术设计或某个定时任务 prompt。默认控制在一到两个屏幕能读完，复杂场景拆到 `docs/*.docs`。

使用用户界面上的业务名称和自然语言。可以用资源 chip 帮维护者点击查看“工单工作台”或“面试进度查询”等已有功能，但不要要求用户理解 `.table`、`.form`、schema、字段映射或工具名。

建议结构：

```markdown
# <业务目录>使用说明

## 这个工具能帮你做什么

## 怎么开始

## 提交后会发生什么

## 系统可以做到哪一步

## 什么情况会转人工

## 人工处理后如何留下解决方案

## 通知和结束
```

Runbook 只写稳定业务规则，不写某个 cron 的细碎安排。像“黄金报价单位默认是元”“本目录不提供投资建议”属于 Runbook；“分页读完、每轮最多处理 5 条、认领超时 30 分钟”属于 AgentTask。

## 文档优先的场景知识闭环

让 Agent 随人工经验成长时，默认使用 `runbook.docs + docs/*.docs`：

- `runbook.docs` 保存稳定业务规则：怎么开始、系统能做到哪一步、何时转人工、谁接手、怎样通知和结束。
- `<./docs/readme.docs>` 用普通人的语言说明目录用途、模板、启用标准和沉淀流程；其他 docs 一份文档对应一个具体场景。
- 场景文档写清状态、什么时候使用、需要哪些业务信息、怎么处理、系统可以做到哪一步、怎么回复和失败找谁。
- 只有人工审核且明确“已启用”的文档才能用于正式回复或执行；“待确认”和“已停用”不得使用。
- 文档可以通过 `/` 引用 Form/Table/Chart；业务人员只需说明业务用途，Agent 仍要自行搜索真实 schema，确认参数来源、权限、风险、幂等和执行后验证。

推荐场景模板：

```text
状态：待确认 / 已启用 / 已停用
什么时候使用
处理前需要什么信息
怎么处理
系统可以做到哪一步
可以使用的功能（通过 / 插入；没有则写无）
怎么回复
处理失败怎么办
```

推荐闭环：无可靠方案时记录证据并转人工；人工填写结论、解决方案和验证结果；处理人确认“无需沉淀/待沉淀”；有维护权限的人创建或更新 docs；人工启用后供后续相似问题复用。运行态没有 `write_doc` 时必须停在明确的人工接管状态，不得声称已经自动更新文档。

只有知识条目确实需要独立生命周期、结构化筛选、统计或批量治理时才增加 knowledge Table；不要让 Table 和 docs 保存同一份权威内容。

## AgentTask.Message 应该写什么

AgentTask 是无人值守任务，运行时用户不在线，所以不能写“到时候问我”。任务必须自己闭环，遇到不能决定的事要降级、记录、通知或留下人工待办。

高质量 AgentTask 必须先分析再执行。每轮开跑前先分页读取输入，算清真实工作量，制定执行方案：本轮要处理多少、最多处理多少、选择哪些对象、为什么选择它们、是否需要 web_search 或外部数据、执行后如何验证。方案用于约束无人值守执行，不是等待用户确认。

AgentTask 的方案要区分“执行前缺口快照”和“执行后剩余缺口”。不要用执行后的数据解释执行前计划，也不要把本轮选择处理的对象数量当作真实总缺口。若任务有单轮上限，计划新增数通常应等于 `min(执行前真实总缺口, 单轮上限)`；如果少于这个数，必须写明素材不足、重复风险、写入失败或其他跳过原因。若执行后发现仍有缺口且不超过上限、也没有跳过原因，应继续补齐再验证。

不要让模型长期口算可由后端确定的工作量。像目标数、已有数、缺口数、完成率、待处理数、逾期数这类反复用于自动任务计划的数字，优先在主工作台 Table 行里用 `gorm:"-"` 展示字段或后端查询补齐，例如“已有草稿数 / 待补篇数 / 生产进度”。比例、完成率和进度优先使用 `widget:"type:progress;min:0;max:100;unit:%"`，不要用普通文本让模型再解释。AgentTask 应要求读取这些确定性字段，再用明细表复核标题、失败项和重复风险。

生成子记录时必须在新增时绑定上游业务对象，例如从选题生成草稿、从合同生成节点、从证书生成续期任务。不要先创建未绑定的子记录，再靠更新回调补外键或上下文；如果写入后发现上游展示名称为空，要把它视为写入不合格，不计入成功。

内容生产类 AgentTask 要明确事实和表达规则：允许在需要公开事实、新闻、产品信息、行业数据时使用 web_search；使用外部资料时必须记录来源。没有来源时不要编造数据、案例、引用或第一人称经历。还要写清“反 AI 味”要求，例如避免空泛套话、同质化结构和无场景的正确废话。

建议结构：

```markdown
## 执行身份

说明这是无人值守任务，不能向用户提问，必须按 <./runbook.docs> 执行。

## 绑定范围

- 运行规则：<./runbook.docs>
- 输入资源：<./xxx.table>
- 输出资源：<./yyy.table>
- 外部工具：web_search / <tool:send_notification> / 其他连接器

## 本轮目标

说明这一次定时任务要完成什么，不要泛泛写“优化业务”。

## 时间窗口和幂等

说明本轮读取哪个时间范围、如何避免重复处理、唯一键是什么、遇到已存在记录怎么办。

## 预期工具

列出预计使用的工具，例如 table 查询、table 新增、table 更新、web_search、send_notification。写入文档或任务说明时，内置通知工具可标成 `<tool:send_notification>`。

## 执行步骤

1. 先读 <./runbook.docs>。
2. 分页读取输入数据，不能只看第一页。
3. 制定本轮执行方案：优先使用后端已计算的执行前缺口快照、真实总缺口、单轮上限、选择对象、预计产出、事实来源策略、验证口径。
4. 按方案过滤、去重、写入或更新目标数据；新增子记录时必须绑定上游对象。
5. 执行后重新读取目标数据验证，不要只相信写入接口返回。
6. 若执行前缺口不超过上限但执行后仍有缺口，且没有明确跳过原因，继续补齐并再次验证。
7. 汇总本轮结果，确保执行前缺口、计划新增、实际新增、执行后剩余缺口和分项明细一致。
8. 按通知规则通知或静默结束。

## 质量控制

列出本任务特有的质量规则，例如新闻入库前必须判断 URL 或标题是否重复。

## 失败处理

说明关键失败、非关键失败、部分成功、无数据时分别怎么做。

## 输出格式

规定最终日志或通知包含哪些字段。
```

任务说明里可以重复 Runbook 的关键硬边界，但不要复制整本 Runbook。AgentTask 应引用 `<./runbook.docs>`，并承担业务文档没有写出的工具选择、schema 确认、字段匹配、分页、认领、幂等、重试、写入和验证；不要反过来要求业务人员补技术说明。

## Goodcase

### runbook goodcase

```markdown
# 证书到期提醒使用说明

## 这个工具能帮你做什么

持续查看公司域名证书的到期时间，在风险出现时生成续期待办，避免负责人每天手工检查。

## 怎么开始

在 <./certificates.table> 登记域名、证书来源、到期时间和负责人。

## 提交后会发生什么

证书进入到期前 30 天时，系统在 <./renewal_tasks.table> 生成待处理事项；已经有未完成事项时不重复创建。

## 系统可以做到哪一步

可以自动整理续期待办和提醒内部负责人。续期、替换生产证书和向客户发送正式通知必须人工确认。

## 通知和结束

证书已经逾期时通知负责人；没有新增风险时不发送消息。续期完成并经人工确认后结束当前待办。
```

为什么好：业务人员不用理解工具、schema、分页或幂等，也能看懂入口、结果、自动化边界和结束条件；具体去重、分页和通知实现留在 AgentTask。

### AgentTask goodcase

```markdown
## 执行身份

你正在执行证书每日巡检任务。用户不在线，不能向用户提问。先阅读 <./runbook.docs>，并严格遵守人工确认边界。

## 绑定范围

- 运行规则：<./runbook.docs>
- 证书台账：<./certificates.table>
- 续期任务：<./renewal_tasks.table>
- 通知工具：<tool:send_notification>

## 本轮目标

扫描未来 30 天内到期的证书，为缺失续期任务的证书生成待处理任务；对已经逾期的证书通知负责人。

## 时间窗口和幂等

以任务执行时的 Asia/Shanghai 日期为准。对同一 certificate_id 和 due_date，若已存在未关闭续期任务，不再重复创建。

## 执行步骤

1. 阅读 <./runbook.docs>。
2. 分页读取 <./certificates.table> 全部启用证书。
3. 找出 30 天内到期和已逾期证书。
4. 分页读取 <./renewal_tasks.table>，按 certificate_id 去重。
5. 为缺失任务的证书创建续期任务。
6. 对已逾期证书发送通知；普通无变化结果不通知。
7. 输出本轮扫描证书数、新增任务数、逾期数、通知状态。
```

为什么好：它是一个具体任务，有时间窗口、幂等规则、分页、写入目标、通知规则和输出格式。

## Badcase

### runbook badcase

```markdown
# 运行手册

每天看看证书，有问题就处理。可以发通知。
```

问题：没有资源、没有状态、没有 SOP、没有异常处理、没有禁止事项。Agent 遇到移动端回复或临时分析请求时只能猜。

### AgentTask badcase

```markdown
每天帮我搜集新闻，写入表格，有问题问我。
```

问题：无人值守任务不能问用户；没有数据源、主题、去重、分页、入库字段、失败处理和通知规则，极容易重复写入或乱写。

### 资源引用 badcase

```markdown
读取 ./profiles.table，然后写 drafts.table。
```

问题：资源引用不可点击，也不利于工具解析。应该写 `<./profiles.table>` 和 `<./drafts.table>`。

## 检查清单

写 `runbook.docs` 前检查：

- 是否说明业务背景和痛点。
- 是否列出核心资源，并使用 `<./xxx.table>` 资源标记。
- 是否覆盖正常 SOP、异常 SOP、通知规则、禁止事项。
- 是否说明哪些动作可以自动做，哪些必须人工确认。
- 是否写清数据分析必须分页读完。
- 是否避免写某个具体定时任务的细碎 cron 流程。
- 涉及可成长知识时，是否区分稳定 Runbook 与具体场景 docs，并写明人工启用门禁和沉淀闭环。

写 `AgentTask.Message` 前检查：

- 是否第一步要求阅读 `<./runbook.docs>`。
- 是否说明本轮目标、时间窗口和幂等规则。
- 是否列出预期使用工具；需要回显内置工具时，是否使用 `<tool:...>` 标记。
- 是否说明分页读取、去重、写入、更新、通知规则。
- 是否区分执行前缺口快照和执行后剩余缺口。
- 如果单轮上限内没有补齐全部缺口，是否要求写明跳过原因。
- 新增子记录时是否要求绑定上游业务对象，而不是先写无归属记录再补。
- 是否能在用户不在线时自行闭环。
- 是否明确失败处理和无数据处理。
- 是否避免自动执行发布、付款、审批通过等高风险动作。
- 使用场景 docs 时，是否只允许“已启用”文档，无匹配时是否回写证据并转人工。

写 `kageos_manifest.go` 前检查：

- 文件名必须是 `kageos_manifest.go`，不要用 `_init_data.go`。
- 默认文档使用 `packageContext.AddDocs(app.DocManifest{Code: "runbook.docs", ...})`。
- 子目录文档使用原 `packageContext.AddDocs(app.DocManifest{Code: "./docs/readme.docs", ...})`；不要额外声明 `PackageContext`。
- docs 只是场景方案载体时，不要再创建保存同一内容的 knowledge Table。
- 默认 Agent 任务使用 `packageContext.AddAgentTask(app.AgentTask{...})`。
- 不要给 AgentTask 填 `Policy`，默认就是缺失才创建。
- build/update 后才会把 seed 同步到 Service Tree。
