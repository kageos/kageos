# kageos 场景解决方案设计原则

本文件用于把“写几个函数”提升成“交付一个可运营的场景目录”。设计时先想最低可用业务闭环，再落 SDK 代码。不要把“场景目录”理解成默认要做大而全系统。

## 默认策略

- 先给一张主表版本，让用户能录入、筛选、跟进、关闭。
- 再列可选增强，例如自动提醒、附件提取、统计图、无人值守任务。
- 只有用户确认需要增强，或业务对象确实有独立生命周期，再拆 Table/Form/Chart/AgentTask。
- 输出方案时区分“V1 必做”和“后续可加”，不要把后续能力塞进 MVP。

## 中小企业的可安装价值

默认客户没有专职研发、运维和数据团队。场景目录应优先使用 kageos 内置 Table/Form/Chart/Docs、附件、通知、调度和系统工具，安装后只需少量业务配置就能看到结果。

筛选 Demo 时优先满足：

1. 高频：真实团队每天或每周都要盯、等、查或协调。
2. 可见：结果回到一张主表、明确状态、待办或通知，用户能看到节省了什么。
3. 低风险：先从只读查询、内部回复、可逆操作和可验证动作开始。
4. 低集成：不依赖自建服务、复杂部署、登录态网页抓取或长周期定制集成才能成立。
5. 可成长：人工处理的新场景能够经过审核沉淀，下一次减少重复劳动。

主路径用“安装 → 打开主入口 → 产生有效业务记录 → 无人值守处理或转人工 → 可见结果 → 经验复用”描述。如果五分钟内讲不清这个路径，继续缩小范围。

## 后台价值判断

先区分“提交时已经知道的错误”和“后来才出现的业务状态”。前者必须在 Form/Table 回调里同步校验并给出可操作反馈；如果校验耗时较长，就使用明确的“草稿/校验中”状态，通过前不能算受理成功。不要先接受一条明知可能无效的记录，再靠后台任务退回用户补偿。

只有时间流逝、外部状态变化、持续观察、跨记录分析或多资源语义判断产生的新工作，才适合无人值守。例如 SLA 风险、无人接单、支付回执、设备告警恢复、相似工单聚类和跨客户事故识别。后台结果必须回到主表状态、建议字段、内部待办或通知，并写清人工接管点、幂等和停止条件；不能只把问题搬到后台或只生成无人处理的报告。

## 文档优先的经验闭环

组织经验默认用文档维护：

- `runbook.docs` 是稳定运行契约，由人工长期维护。
- `docs/readme.docs` 是场景方案目录说明和模板。
- `docs/*.docs` 是具体解决方案，优先用 `<./...>` 或 `<../...>` 可移植相对标记引用 Form/Table/Chart，让 Agent 不只会回答，也能在门禁内查询或执行。用户明确要求跨工作空间编排时可用 `</...>` 绝对标记，但要声明不可移植、复制后需重新绑定。
- 只有“已启用”文档可以复用；“待确认/已停用”不授权正式答复或执行。

未知问题不由 Agent 猜答案。Agent 留下已查证据并转人工；人工处理后填写原因、方案和验证；系统提醒处理人决定是否沉淀；有维护权限的人更新 docs 并人工启用。运行角色没有 `write_doc` 时，状态必须诚实停在“待确认/待沉淀”。

默认不再增加保存相同内容的 knowledge Table。只有知识条目需要独立负责人、生命周期、结构化筛选、统计或批量治理时，Table 才有独立价值，并且必须与 docs 划清唯一职责。

## 设计顺序

1. 最小主表：先识别用户每天要看的那张表，例如合同台账、证书台账、客户台账、设备台账。
2. 业务对象：再识别核心对象和事实记录，例如会议室、预约、证书域名、证书申请、资产归档。
3. 人工入口：用 Table 管理台账，用 Form 承接确实不能表格表达的动作，例如提交预约、查询空闲、申请证书、手动巡检。
4. 自动入口：固定巡检、提醒、续期用 `FormTemplate.Schedules`；跨工具分析、日报、情报整理用无人值守定时会话。
5. 经验闭环：需要复用人工处理经验时，设计 `runbook.docs + docs/*.docs` 和人工启用流程，不默认加重复知识表。
6. 分析反馈：用 Chart 或定时会话报告把数据变成运营判断，例如使用率、空置率、即将过期、失败率、TOP 列表。
7. 系统工具：文件处理、PDF、图片、音视频、HTML、消息、临时脚本和数据转换优先复用安装自带的 `/system/tools`，不要在每个业务目录重复造基础工具。
8. 平台能力：通知用 `ctx.SendNotification` 或定时会话通知工具；附件用平台文件引用，不要业务代码直连具体消息渠道，不要自造调度器。

## 目录组织思路

一个好目录不是功能堆叠，而是把人和 AI 都能操作的业务空间组织清楚：

- 台账目录：放稳定对象，例如资源、配置、客户、域名、设备、商品。
- 过程目录：放过程记录，例如预约、申请、续期、销售、入库、工单、执行记录。
- 动作入口：放可执行 Form，例如查询、提交、巡检、生成、同步、批处理。
- 分析入口：放 Chart 或日报会话，例如趋势、分布、排行、异常、容量预测。
- 自动化入口：放默认调度 Form 或定时会话，让系统能无人值守运行。

## 人机界面分层

- 人的主界面应是少数高频入口，例如创建任务、待办列表、审核工作台、配置台账。
- AI 和系统可以使用更细的后台 Form，例如写入草稿、批量渲染、生成发布包、复盘归档；这些不应成为普通用户的日常入口。
- 用户选择上游对象后，下游字段由后端查询补齐；不要让用户重复选择或手填可以推导出的 ID。
- 事实表、流水表、审核记录和生成结果默认只读；它们由动作函数或自动化写入，而不是人工新增。

## 不要过早复杂化

- 不要把通用审批、评论、权限、通知队列塞进每个业务系统。
- 不要为了“完整”给事实记录表加手工 CRUD；流水、执行记录、证书申请记录通常只读。
- 不要把“能建表、能增删改查”当成产品完成；先确认用户每天真正打开的是哪个工作台。
- 不要把“能做完整流程”当成产品完成；用户愿意每天用的一张表，通常比五个入口更好。
- 不要在业务应用里自造 cron；固定业务巡检用 FormSchedule，复杂跨工具任务用定时会话。
- 不要硬连具体消息渠道；业务只表达通知对象、标题、内容和必要附件引用。
- 不要把通用文件/PDF/图片/音视频/脚本处理重复写进业务 app；先判断 `/system/tools` 是否已覆盖。
- 不要用 Go 硬写 Python 生态已经成熟的重型处理；临时任务用 `/system/tools/runtime/python.form`，长期业务接口用 Go Form 编排 Python runtime。
- 不要复制当前机器的运行态代码路径作为案例；案例要写成可迁移方案。

## 方案说明模板

写场景案例时建议包含：

- 解决什么问题。
- V1 最小主表是什么，为什么够用或不够用。
- 目录里有哪些 Table、Form、Chart、定时任务、定时会话。
- 哪些字段是用户配置，哪些字段由后端或自动化写入。
- 哪些逻辑要幂等，如何避免重复执行。
- 如何从“可用工具”升级成“无人值守运营”。
- 哪些边界暂不做，避免模型过度发挥。
