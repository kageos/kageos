## 分析结论

### 一、你的想法总结

- **问题**：工具参数是「源代码」时，直接塞进 JSON 会有一堆转义/编码问题；当前用 generate_code + 从「上一条 assistant 的 markdown 代码块」里挖内容再给 write_package_code，流程重、只服务这一种场景。
- **思路**：约定一种「变量」写法——模型在**同一条回复**里先输出 `<var><key>变量名</key><value>长内容/代码</value></var>`，工具调用时只传**变量名**（如 `source_code_var: "code"`），执行时从**当前 assistant 消息**里解析所有 `<var>`，按名字取出 value，再当作真实参数传给工具。这样「长文本/代码」不经过 JSON，自然没有转义问题，且任何需要长内容的工具都能复用同一套机制。

### 二、优点

| 点 | 说明 |
|----|------|
| **通用** | 不限于「代码」：任何大段文本、配置、多行内容都可以用 `<var>` 定义，工具只引用变量名，逻辑统一。 |
| **无 JSON 转义** | 长内容在 `<value>` 里以「正文」形式输出，不参与 tool_call 的 JSON 编码，避免引号、换行、反斜杠等问题。 |
| **语义清晰** | 「先声明变量，再在工具里引用」比「先调 generate_code、再靠会话顺序和 markdown 解析找代码」更直观，也更容易在 system prompt 里说清楚。 |
| **可扩展** | 以后别的工具（如写文档、写配置）只要参数支持「引用变量」，就复用同一套解析与解析逻辑，不必再为每种场景写一套「从哪条消息挖什么」。 |

### 三、是否好做到（实现）

- **好做**。你们执行工具时已经有「当前会话消息列表」和「本条 assistant 消息的 content」：
  - 在 `executeToolCalls`（或工具真正拿参数之前）加一层：若某个参数名符合约定（如 `source_code_var`、或约定凡以 `_var` 结尾的表示「变量引用」），则取值为变量名；
  - 从**本条 assistant 消息的 content**（即含本次 tool_calls 的那条）里解析所有 `<var><key>xxx</key><value>...</value></var>`，做成 `map[key]value`；
  - 用变量名从 map 里取出 value，替换到工具的真实入参里，再调原有工具逻辑。
- **解析**：用正则或简单状态机即可（注意 value 里可能还有换行、`</key>` 等，建议用「找 `<key>key名</key>` 再找下一个 `<value>` 到 `</value>`」的边界解析，不要用贪婪匹配）。若解析不到该 key，工具层返回明确错误：「变量 'code' 未在当前消息的 <var> 中定义」。
- **与现有流程的关系**：可以**先**支持「带变量引用的新约定」；对 write_package_code 保留「若没有 source_code_var，再回退到从历史里找 generate_code 后的 markdown 代码块」的兼容，两套并存一段时间，再考虑下线旧逻辑。

### 四、大模型是否会遵循

- **有可能，但不保证 100%**。多数模型能按 system 里说的「先写 <var>…</var>，再在 tool 里只传变量名」来做，尤其是：
  - 在 system prompt 里**写清步骤**（先输出 <var>，再调用工具时用 xxx_var 传变量名）；
  - 工具描述里明确写「若传源代码，请用 source_code_var 引用你在本条消息中 <var> 里定义的内容」。
- **风险**：偶尔会只传变量名、忘了写 <var>，或 <var> 格式写错（标签不闭合、key/value 反了）。所以需要：
  - **兜底**：解析失败或变量缺失时，返回清晰错误，让模型重试或补写 <var>；
  - **提示语**：在工具描述和 system 里各写一遍约定，并给 1～2 个示例，提高遵循率。
- **智谱那种 XML 式 tool_call**：本质也是「把参数从 JSON 里拆出来，用别的结构传」，和你的「用 <var> 承载大块内容、tool 只传引用」是同一类思路，你们用 <var> 自己定义一套，不依赖厂商格式，是合理的。

### 五、风险与兜底

| 风险 | 兜底 |
|------|------|
| 模型不写 <var> 只传了变量名 | 工具层检测到「变量名未定义」时返回明确错误，并在错误信息里提示「请在本条回复中先用 <var><key>名称</key><value>内容</value></var> 定义」。 |
| <var> 格式乱（未闭合、多一层嵌套等） | 解析时尽量宽松（例如取第一个 `<value>` 到 `</value>` 的内容），或只认一行内的 key；若仍解析不到则当「未定义」处理。 |
| 同一条消息里多个工具都要引用同一段内容 | 一个变量名可被多个参数引用，map 解析一次即可。 |

### 六、和现有 generate_code + write_package_code 的对比

| 维度 | 现有方案 | <var> + 变量引用 |
|------|----------|------------------|
| 复用性 | 只服务「先 generate_code 再写代码块再 write_package_code」 | 任意「长文本/代码」参数都可复用 |
| 逻辑清晰度 | 依赖「上一条 tool 消息」「下一条 assistant 的 markdown」等隐式约定 | 显式「本条消息里定义变量，本条的 tool 引用变量名」 |
| 实现成本 | 已实现，但 findCodeContentAfterGenerateCode 等与场景强绑定 | 需加一层「变量解析 + 参数替换」，一次实现多工具复用 |
| 兼容 | - | 可与现有逻辑并存：有 _var 则解析变量，没有再走「从历史找代码块」 |

### 七、建议

- **方向**：采用「<var> 定义 + 工具参数传变量名」这套通用机制是**值得做的**，既解决转义问题，又比当前 generate_code 流程通用、好维护。
- **落地**：
  1. 在 system prompt 和工具描述里**明确约定**：需要传长内容/代码时，先在本条回复中用 `<var><key>名称</key><value>内容</value></var>` 定义，再在工具参数里用如 `source_code_var: "名称"` 引用。
  2. 在执行工具前（例如 workspace 的 executeToolCalls 或统一的一层「参数解析」）解析**当前 assistant 消息 content** 的 `<var>`，得到 key→value；对参数名以 `_var` 结尾（或白名单）的，用变量值替换后再调工具。
  3. write_package_code 可新增参数 `source_code_var`（可选）；若存在则从变量取内容，否则再回退到「从历史找 generate_code 后的代码块」，兼容旧行为。
  4. 解析失败或变量未定义时返回清晰错误文案，便于模型自我纠正。
- **是否好做到**：好做，主要是「解析 + 参数替换」一层；大模型**在写好提示的前提下**多数情况会遵循，偶发格式问题用错误提示兜底即可。
