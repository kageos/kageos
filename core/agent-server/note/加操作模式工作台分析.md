# 加「操作模式」工作台 — 可行性分析

## 一、当前架构简述

### 1. 工作台模式（Workspace Mode）是什么

- **数据层**：表 `workspace_modes`，一条记录 = 一种模式（code、name、description、system_prompt_fragment、tool_names、agent_id、sort_order、is_builtin）。
- **内置模式**：启动时 `InitWorkspaceModes` 会插入 3 条：`dev`（开发）、`modify`（修改）、`execute`（执行）。
- **提示词多态**：每种模式对应一套「模式提示词」——从 `prompt/content/mode/<code>/` 读取：
  - `config.json`（name、description、tool_names、引用的 md 文件名）
  - `system_prompt.md`
  - `first_assistant.md`（可选）
  - 可选 `operation_prompt` 文件（若 config 里配置了 `operation_prompt_file`）
- **前端**：
  - **智能工作台管理**（`WorkstationModeManagement`）：模式列表 CRUD，下拉选工具、绑智能体。
  - **工作台对话**（`WorkstationChat`）：选一个模式（如 dev/modify/execute），发请求时带 `mode` 参数；后端按 mode 选提示词和工具。

### 2. 相关代码位置（便于改）

| 层级     | 文件/目录 | 作用 |
|----------|-----------|------|
| 后端模型 | `core/agent-server/model/workspace_mode.go` | 表结构、`InitWorkspaceModes` 内置 3 条 |
| 后端提示 | `core/agent-server/prompt/mode_provider.go` | 从 `content/mode/<code>/` 加载并注册 provider（init 里只有 dev/modify/execute） |
| 后端内容 | `core/agent-server/prompt/content/mode/{dev,modify,execute}/` | 各模式的 config.json + md |
| 前端 API | `web/src/api/workspace.ts` | 模式列表、创建/更新/删除模式 |
| 前端管理 | `web/src/architecture/presentation/components/WorkstationModeManagement.vue` | 模式 CRUD 页 |
| 前端对话 | `web/src/architecture/presentation/components/WorkstationChat.vue` | 模式下拉、发请求带 `mode` |

## 二、「操作模式」的两种理解与难度

### 理解 A：新增一种工作台模式（和 dev/modify/execute 并列）

即：多一种可选模式，例如 code=`operate`，名称「操作模式」，用在现有「工作台对话」里下拉选择。

**结论：好加，工作量小。**

| 步骤 | 内容 | 难度 |
|------|------|------|
| 1 | 后端 `InitWorkspaceModes` 里增加 `operate` 的初始化（name/description/system_prompt_fragment/tool_names 等） | 低 |
| 2 | 后端 `mode_provider.go` 的 `init()` 里把 `"operate"` 加入要加载的 code 列表 | 低 |
| 3 | 新建目录 `content/mode/operate/`，并添加 `config.json`、`system_prompt.md`、`first_assistant.md`（可参考 execute） | 低 |
| 4 | 前端 | **无需改**：管理页列表和对话页模式下拉都会自动出现新记录 |

**注意**：若希望「操作模式」用到的工具集、系统提示与执行模式不同，在步骤 1 和步骤 3 里区分配置即可（例如工具只读、或增加某些操作类工具）。

---

### 理解 B：新增一块「操作模式工作台」的入口/视图

即：在工作空间里多一个入口（如 Tab、侧边栏、独立路由），点进去是「操作模式」专用界面（例如快捷操作、工单、批量执行等），而不仅仅是对话里多选一个模式。

**结论：取决于产品形态，一般中等或以上。**

| 步骤 | 内容 | 难度 |
|------|------|------|
| 1 | 产品定义：操作模式工作台具体做什么（仅跳转到现有工作台并默认选 operate？还是新布局/新交互？） | 产品 |
| 2 | 路由/入口：新路由（如 `/workspace/operate`）或现有工作台下 Tab/query（如 `?tab=operate`） | 低 |
| 3 | 视图/组件：若只是「默认选 operate 的对话页」→ 复用 `WorkstationView`/`WorkstationChat` 并传默认 mode 即可；若是新交互（表单、列表、流程）→ 需新页面 + 可能的新 API | 中～高 |
| 4 | 后端 | 若仅复用现有工作台对话 + 模式 operate，无需新接口；若有新能力再按需加 API | 视需求 |

若采用「仅多一个入口 + 默认选操作模式」的轻量方案，整体仍较好加；若是全新交互形态，需要单独排期。

## 三、推荐落地方式（在「理解 A」前提下）

若当前目标就是「支持操作模式」且先用现有对话形态：

1. **后端**
   - 在 `model/workspace_mode.go` 的 `InitWorkspaceModes` 中增加 `operate`（或你定的 code），写好 name/description/工具列表/系统提示片段。
   - 在 `prompt/mode_provider.go` 的 `init()` 中为 `operate` 注册加载（与 dev/modify/execute 一致）。
   - 新建 `content/mode/operate/`，按 README 约定放 `config.json`、`system_prompt.md`、`first_assistant.md`（可先拷贝 execute 再改文案和 tool_names）。

2. **前端**
   - 无需改代码；重新拉模式列表后，管理页和对话页下拉都会出现「操作模式」。

3. **后续若要「操作模式工作台」独立入口（理解 B 的轻量版）**
   - 增加一个入口（如 Header 或服务树旁）跳转到 `/workspace/workstation?full_code_path=xxx&mode=operate`，或封装一个「打开工作台并默认选操作模式」的按钮即可。

---

## 四、小结

- **只加「操作模式」这一种工作台模式（理解 A）**：好加；后端加一条内置模式 + 一套 mode 目录 + 注册 provider，前端零改动。
- **加「操作模式工作台」独立入口/视图（理解 B）**：轻量版好加（入口 + 默认 mode）；完整新交互需按产品设计评估，工作量中等或以上。

## 五、执行模式（execute）实现情况（已落地）

已按「四步」完成执行模式实现：

1. **pkg/apicall**：新增 `TableSearch`、`FormSubmit`、`ChartQuery`，调用 `/workspace/api/v1/table/search`、`form/submit`、`chart/query`。
2. **tool_registry**：新增工具 `run_table_search`、`run_form_submit`、`run_chart_query`，并在 `CallTool` 中实现对应调用与结果格式化。
3. **execute 模式配置**：  
   - `model/workspace_mode.go` 中 execute 的初始化增加了上述三个工具及说明；  
   - `content/mode/execute/config.json` 的 `tool_names` 已包含这三个工具；  
   - `system_prompt.md`、`first_assistant.md` 已写明可使用 run_* 查表、提交表单、查图表。
4. **已有库说明**：运行时工具列表来自 **config.json**（mode provider 从 embed 读），因此执行模式会使用新工具。若希望管理页「执行模式」的工具数一致，需在「工作台模式管理」中编辑执行模式并保存，或对已有库更新 `workspace_modes` 中 execute 的 `tool_names`。
