# 工具重复调用（如 get_current_time 连调 15 次）排查结论

## 1. 代码里有没有重试逻辑？

**结论：没有。**

- `streamloop.RunStreamLoop`：每轮一次 LLM 流式请求 → 得到 `content + allToolCalls` → 调用一次 `ExecuteToolCalls(allToolCalls)` → 然后 `runStreamLoopRound(round+1)` 进入下一轮。
- 没有对**同一条 tool_call** 的重试；下一轮是**新的** LLM 请求，模型根据历史（含上轮 tool 结果）再生成。
- 因此：若用户在同一轮里看到 15 次 `get_current_time`，说明**本轮的这一次 assistant 回复**里，模型就产出了 15 个 tool_calls（15 个不同 call id），而不是我们代码执行了 15 次“重试”。

## 2. 流式合并会不会导致重复？

**结论：不会多造出一份。**

- `processStreamChunks` 里用 `mergeToolCalls(ch.ToolCalls, allToolCalls, toolCallsIndex)` 按 **tool call ID** 合并：
  - 相同 ID：只更新同一条（Name/Arguments 累加），不追加新条。
  - 新 ID：才 `append` 一条。
- 所以：最终 `allToolCalls` 里有多少条，完全取决于**流式里出现了多少种不同的 tool call ID**。若出现 15 个不同 ID，就会得到 15 条并执行 15 次；这是**模型在一轮里就生成了 15 个 tool_calls**，不是合并逻辑重复。

## 3. 提示词里有没有诱因？

- 工作台操作提示词（`工作台操作提示词.md`）里**没有**“获取时间”“get current time”等表述，没有引导模型去调 get_current_time。
- 之前 get_current_time 在工具列表里，模型可能在某些情况下（例如“不知道调啥”或习惯性占位）反复调它；**已从工具列表和模式里下掉 get_current_time**，模型再也拿不到该工具，从根上避免该工具被连调。

## 4. 总结

| 问题 | 结论 |
|------|------|
| 代码里有没有重试导致同一 tool_call 执行多次？ | **没有**，每轮只对当前 `allToolCalls` 执行一次。 |
| 流式合并会不会把 1 条合并成 15 条？ | **不会**，按 ID 合并，只会少不会多。 |
| 15 次从哪来？ | **模型在本轮一次回复里就生成了 15 个 tool_calls**（15 个不同 ID）。 |
| 提示词有没有写“多调几次”？ | **没有**。 |
| 后续怎么避免同类问题？ | 已下掉 get_current_time；若其它工具也出现“同一轮大量重复”，需从**模型行为/提示词**找原因，而不是在代码里加“每工具最多 N 次”等粗限制。 |

**不建议**在代码里做：同一工具最多执行 N 次、或按 (name+args) 去重拒绝等“断臂”限制，容易误伤正常多次调用（如多次 read_file 不同文件）。
