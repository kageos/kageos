# 修改项目

当用户要**改已有代码**或**给项目写文档**（如 README、使用说明）时，按本文档执行。

涉及**组件类型、列表写法、包约定**时，按需 read_doc("/builtin/doc/sdk/agent-app-sdk-readme")；涉及**某类项目写法**拿不准时，按需 read_doc 最佳实践案例（路径见 read_doc("/builtin/doc/workspace/create-project") 文档末尾「参考案例（最佳实践）」表格）。

**重要**：**不要一上来就改代码**。先根据用户需求输出**修改 PRD**（详细列出修改点）；**修改 PRD 需得到用户确认后再执行**——用户表达确认（如「可以」「OK」「按这个来」「没问题」「开始吧」等，不限于某几个词）后，再执行修改；未得到用户确认前禁止改代码。**用户可能对 PRD 不满意**：若用户提出调整（如「去掉第 2 条」「把第 1 条改成 xxx」），按用户要求修改 PRD 后再输出，直到用户满意、确认后再执行。

**用户不懂技术**：确认修改 PRD 的用户只能看到**页面、表单、列表、筛选框、按钮、对话框**等 UI，看不到任何代码。因此修改 PRD 里**禁止出现**文件名（如 xxx.go）、结构体/函数名（如 MeetingRoomBookingListReq）等代码相关词汇；只用**用户能看到的**说法描述「改了什么、在哪个页面/表单、用户会看到什么效果」。

---

## 修改操作 SOP（改代码时按此执行）

**原则**：**先出修改 PRD、用户确认后再动手**；改代码时**能用 search_replace_file 就不要整文件重写**（write_go_file 整文件重写耗时长、浪费 tokens）；仅当大改或整文件重构时才用 write_go_file。

1. **理解需求并输出修改 PRD**：根据用户说的修改意图，结合当前项目（read_go_file / 可执行函数 / 可读目录下的 summary、prd）梳理出**修改点清单**，用「修改 PRD」形式输出（见下方「修改 PRD 示例」）：只写**用户能看懂的**——修改点、在哪个页面/表单/列表、用户会看到什么效果；**禁止**写文件名、结构体名、函数名等代码相关词汇。若**用户对 PRD 不满意、提出调整**（如增删改某条、改描述），按用户要求修改 PRD 后再输出，**直到用户满意**。**得到用户确认**（用户表达同意即可，如「可以」「OK」「按这个来」「没问题」「开始吧」等，不限于某几个词）后，你再在内部对应到具体文件与代码去改；未得到用户确认前**禁止**直接改代码、write_go_file、search_replace_file。
2. **按需读文档**：涉及组件/列表/包约定或某类项目写法时，read_doc SDK 或最佳实践案例（路径见 create-project 文档末尾表格）。
3. **看代码**：read_go_file 读取要改的文件，从实际内容中**复制要替换的原文**作为 search_string（必须与文件内容完全一致，含空格、换行）。
4. **改代码**：**优先 search_replace_file** 只改这一段；仅当大改或整文件重构时才用 write_go_file。改完后若需生效调用 **build_workspace**。
5. **写文档**：仅当用户明确要求写 README/使用说明时，用 write_doc；缺目录先 create_directory。

## 修改 PRD 示例（具体，供输出时参考）

下面以**会议室预约**项目为例：用户说「预约列表要能按预约状态下拉筛选」「会议室加一个容量上限，单位是人」。**给用户看的 PRD 只写用户能看到的页面和效果，不写任何代码、文件名、结构体名。**

**修改 PRD（示例，用户侧表述，无代码词汇）**

| 序号 | 修改点 | 在哪儿改 | 用户会看到什么 |
|------|--------|----------|----------------|
| 1 | 预约列表支持按「预约状态」筛选 | 预约列表页面 | 预约列表页面上方多一个「预约状态」下拉框，可选「待开始」「进行中」「已结束」；选完后列表只显示该状态的预约。 |
| 2 | 会议室增加「容量上限」 | 会议室的新增/编辑表单、会议室列表、选会议室时的弹窗 | 新增或编辑会议室时，表单里多一项「容量上限」（数字，单位人）；会议室列表里多一列「容量上限」；选会议室预约时，弹窗里也能看到每个会议室的容量上限。 |

**说明**：以上为给用户确认用的表述，**禁止**出现 .go、MeetingRoom、Handler、Req 等。你输出修改 PRD 时，只写「修改点、在哪儿改（页面/表单/列表/弹窗）、用户会看到什么」。**本修改 PRD 需得到用户确认后再执行**：若用户对 PRD 不满意、提出调整，按用户要求修改 PRD 后再输出，直到用户满意；用户表达确认（如「可以」「OK」「按这个来」「没问题」「开始吧」等，不限于某几个词）之后，你再在内部根据项目实际文件与代码去执行（read_go_file → search_replace_file / write_go_file → build_workspace）；未得到用户确认前禁止改代码。

## 一、改已有代码

**能用 search_replace_file 就不要整文件重写**；仅当大改或整文件重构时才用 write_go_file。

### search_replace_file 用法

- 传 directory、file_name、search_string、replace_string；可选 replace_all（默认 true）。
- **search_string 必须与文件内容完全一致**（含空格、制表符、换行），否则替换易失败。
- **使用前必须先 read_go_file 读取文件**，从实际内容中**复制要替换的原文**作为 search_string，不要手敲或猜空格。
- 只改匹配到的片段，不整文件覆盖，实时写盘。仅修改代码不编译；若需生效改完后需调用 **build_workspace**。
- 适合改函数体、改一行、改几行；大改或整段重写用 read_go_file 后 write_go_file。

### 编译报错与编译失败

**build_workspace 失败时会返回编译失败信息**（含报错文件、行号等）。按下面步骤循环处理，直到编译成功；**已读过的文档不必每次循环都读**，已知内容可直接操作。

**编译失败处理步骤（失败则从步骤 1 重新循环）：**

1. **查看报错信息**：看 build_workspace 返回的编译失败信息（报错文件、行号等）。
2. **按需读文件**：若已知报错位置对应的文件内容，可跳过不读；否则用 read_go_file 或 read_go_file_lines(报错行) 读取。
3. **确定原因并修复**：  
   - **能确定问题原因** → 直接修复（search_replace_file 或 write_go_file）。  
   - **不能确定** → 按需 read_doc SDK 或 read_doc create-project 文档末尾「参考案例（最佳实践）」表格，对照最佳实践写法再修复（本对话中已读过的文档可不再重复读）。
4. **再编译**：调用 build_workspace。  
   - **编译成功** → 结束。  
   - **编译失败** → 回到步骤 1，重复上述步骤。

- **编译报错带行号时**：用 **read_go_file_lines**(file_name, line_ranges) 只读指定行并带行号，便于对照。例如报错在 xxx.go 第 10、20-22 行，传 file_name: "xxx.go", line_ranges: "10,20-22"。
- **最佳实践路径**：read_doc("/builtin/doc/workspace/create-project") 文档末尾「参考案例（最佳实践）」表格中有各类型案例的 read_doc 路径，按类型选读即可。

**注意**：修改已有代码时**禁止**一上来就整文件重写；须先用 read_go_file 从实际内容复制原文作为 search_string。

## 二、写项目文档

当用户要「给这个项目写个 README」「写份使用说明」时：

- **write_doc**：传 name、code、content，可选 directory、format；缺目录先 create_directory。
- **仅当用户明确要求**写文档时再调用；不要自作主张帮用户生成文档。
- 完成后简短说明文档位置。

---

## 三、何时用什么工具（修改相关）

- **要看代码文件**：read_go_file(directory, file_name)。仅用于当前工作区下的 .go 文件；file_name 可单文件（如 a.go）或逗号分隔多文件（如 a.go,b.go）；不传则返回该目录下所有 .go 文件。
- **编译报错带行号时**：read_go_file_lines(file_name, line_ranges)。
- **要编辑已有文件（改一段）**：search_replace_file（见上文）。
- **要写文档**：write_doc（见上文）。
- **要编译工作空间**：build_workspace。无需传参。
- **要删除文件**：delete_file。传 directory、file_name。不能删 init_.go。

## 四、常见情况与应对

| 情况 | 怎么做 |
|------|--------|
| 用户要改已有代码 | **先出修改 PRD**（只写用户能看懂的：修改点、在哪个页面/表单/列表、用户会看到什么效果；**禁止**写文件名、结构体名等代码词汇），等用户确认后再改。确认后：优先 search_replace_file；先用 read_go_file 读取文件，从实际内容中复制要替换的原文作为 search_string（必须完全一致含空格），否则替换易失败。改完后若需生效需调用 build_workspace。仅当大改或整文件重构时才用 read_go_file 后 write_go_file。 |
| 用户要写文档 | 确定目录，缺则 create_directory，再 write_doc(name, code, content)；完成后一句说明位置。 |
| 编译报错带行号 | 用 read_go_file_lines(file_name, line_ranges: "10,20-22") 只看报错行并带行号对照。 |
| 编译失败 | 能根据报错改则直接改；看不出原因时 read_doc 拉取 SDK 与案例，对照示例排查。 |
| 用户要「编译/重新部署」 | 调用 build_workspace（无需传参）；不写文件，仅触发编译并部署。 |

## 五、禁止与注意

- **禁止在未得到用户确认修改 PRD 前就改代码**：须先输出修改 PRD（只写用户能看懂的：修改点、在哪个页面/表单/列表、用户会看到什么效果；**禁止**出现文件名、结构体名、函数名等代码词汇），**得到用户确认**（用户表达同意即可，如「可以」「OK」「按这个来」「没问题」「开始吧」等，不限于某几个词）后再执行 search_replace_file / write_go_file；未得到用户确认前禁止直接改代码。
- **能用 search_replace_file 就不要整文件重写**；禁止一上来就 write_go_file 重写整个文件（耗时长、浪费 tokens），仅当大改或整文件重构时才整文件重写。
- **注意**：search_replace_file 的 search_string 必须与文件内容完全一致（含空格、换行），须先用 read_go_file 从实际内容复制原文，不要手敲或猜。
- **禁止**自作主张帮用户生成文档（write_doc）；仅当用户明确要求写文档时再 write_doc。
