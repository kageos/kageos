# 创建项目

当用户要**生成应用、生成系统、创建 XX 管理**等需要写代码并落盘时，按本文档执行。

**前置**：本文档与 SDK 文档配合使用。可 `read_doc("/builtin/doc/sdk/agent-app-sdk-readme", "/builtin/doc/workspace/create-project")` 一次拉取。出 PRD 前须已读过 SDK，了解组件类型与能力边界。

**强制要求：出 PRD 前必须先参考示例**。须先 `read_doc` 与项目类型匹配的 1～2 个案例（见文末「参考案例」表格），对照案例的 PRD 表格格式、字段说明、列表模式写法后再写本项目的 PRD。禁止未读案例就出 PRD，否则 PRD 易错、格式不对、与实现脱节。

## 一、PRD 格式（必须包含两个 Markdown 表格）

- **表单字段（新增/编辑）**：五列「字段 | 类型 | 必填 | 默认值 | 说明」。类型对应 SDK 组件（文本输入、多行文本、下拉选择、用户选择、时间选择、数字输入、滑块、多选下拉、文件上传等）；默认值有则填（如「待处理」、0），无则填 —；说明写取值；select/multiselect 须配 options_colors。**仅列出用户可填写的字段**，计算字段、自动生成字段不放表单。
- **列表模式**：系统字段（ID、创建时间、更新时间、创建人）+ 业务字段（与表单顺序一致）+ **仅列表展示的计算字段**（若有）。计算字段（如剩余天数、库存状态）只在列表展示，新增/编辑不填，后端返回时计算；PRD 在列表表头列出该列，说明里注明「仅列表展示、后端计算」。须写完整表格（表头 + 分隔行 + 至少一行示例）。
- 表格用纯 Markdown，禁止放在代码块内。**是否新建目录**：明确写「不新建目录」或「会新建目录：名称 code」。

## 二、PRD 易错点（避免自相矛盾）

### 1. Table 与 Form 的存储边界

AutoCrudTable 的 model 结构体中有 gorm 列的字段，**只能是**基础类型（int、string、bool、float64 等）、files.Files（JSON 存一列）、gorm.DeletedAt。**禁止**在 Table 的新增/编辑里出现嵌套的 table 或 form 作为要落库的列。

**主从表/明细表的正确做法**：主表、明细表各为独立 Table。若需「一次填主表 + 多行明细」的界面，用 **FormTemplate**（POST），请求体里 type:table 放明细行，Handler 内先写主表再写明细表。

### 2. 自动计算/自动生成字段、仅列表展示的计算字段

- **自动计算/自动生成**（如总金额、单号）：表单里不标「必填、用户输入」，标为不展示或只读，说明「由后端计算/生成」。
- **仅列表展示的计算字段**（如剩余天数、库存状态）：**不在表单字段表里列出**，只在列表模式中列出；后端在返回列表数据时按规则计算（如剩余天数 = 截止时间 − 当前时间），model 可用 `gorm:"-"` 不落库，仅在 List 响应中填充。

### 3. 业务规则/状态联动

有状态流转且会改其它数据时（如「已入库」要加库存），PRD 里须写清：在什么状态下、对哪张表/字段、做什么运算。

### 4. Form + Table 结合

复杂表单提交不要全塞进 Table 的 template——Table 适合单行 CRUD；复杂提交用 **FormTemplate**（POST），Handler 里把数据写到 Table 对应的表。参考案例：投票系统、收银台。

### 5. 规模匹配，避免过度设计

- 默认按**用户当前场景的最小可用版本**来设计。用户说的是理发店、小门店、个人团队这类轻量场景时，不要自作主张加多门店、多仓库、复杂角色、多级审批、财务中心、分账等大系统能力。
- 只有用户明确提出，或业务规则确实离不开时，才增加更复杂的字段、流程和模块。

### 6. 流水/记录类表默认只读

- 支付记录、消费流水、操作日志、审计记录这类表，默认定位为**查询表**。
- PRD 与代码里默认**不提供新增、编辑、删除入口**；不要给这类表配置 `OnTableAddRow`、`OnTableUpdateRow`、`OnTableDeleteRows`。
- 若业务需要退款、冲正、撤销，不要让用户直接改流水本身，应做单独的业务动作或表单。

### 7. 跨表联动必须放事务

- 只要一次提交会同时改动多张表，尤其是**余额、库存、数量、状态、流水**这类强一致数据，必须在同一个事务里处理。
- 禁止“先在事务外校验，进事务后裸更新”这种写法；至少要在事务内再次做条件更新或校验，避免并发下超卖、透支、脏数据。

### 8. 数据库兼容默认按 SQLite 优先

- 工作区应用默认使用 **SQLite**，所以生成代码时，**默认要先保证 SQLite 能跑**。
- 若后续可能切换到 MySQL，遇到 SQL 方言差异时，必须先判断 `db.Dialector.Name()`，再分支处理，不要把 MySQL 语法写死在代码里。
- **优先使用 GORM 和 Go 代码做计算/聚合**；只有 GORM 表达不了，才写 Raw SQL。
- 典型差异要特别注意：
  - **时间格式化/按天分组**：MySQL 常用 `DATE_FORMAT(FROM_UNIXTIME(...), '%Y-%m-%d')`，SQLite 常用 `strftime('%Y-%m-%d', ..., 'unixepoch')`
  - **字符串拼接**：MySQL 常用 `CONCAT(a, b)`，SQLite 常用 `a || b`
  - **upsert / 冲突更新**：MySQL 常见 `ON DUPLICATE KEY UPDATE`，SQLite 常见 `ON CONFLICT DO UPDATE`
  - **JSON 函数**：两边函数名和能力不完全一致，能不用 Raw SQL JSON 就尽量不用

## 三、其他常见情况（PRD 可补充说明）

以下情况在 PRD 里按需说明即可，避免遗漏或歧义。

| 情况 | 说明 | PRD 怎么写 |
|------|------|------------|
| **仅列表展示的计算字段** | 后端返回列表时计算，表单不填（如剩余天数、库存状态） | 列表表头列出该列，说明「仅列表展示、后端计算」；表单字段表不列 |
| **自动生成字段** | 新增时后端生成，用户不填（如单号、编码） | 表单里不列，或列且说明「不展示/只读，由后端生成」 |
| **新增可填、编辑只读** | 如创建人、创建时间仅新增时写入，编辑时不改 | 说明「创建人/创建时间仅新增时填充，编辑时只读」 |
| **关联/外键** | 表单用 select 选关联，列表展示关联表名称（如订单列表显示「客户名称」而非客户 ID） | 表单列「客户」类型为用户选择或下拉（数据来自关联表）；列表列「客户名称」，说明「关联 XXX 表，展示名称」 |
| **默认值** | 字段有默认值（如状态默认「待处理」） | 在表单字段表的「默认值」列填写，无则填 — |
| **列表可筛选/可排序** | 列表支持按某列筛选、排序 | 在列表模式下方写一句「支持按 状态/创建时间 筛选，按 创建时间 排序」；实现时 model 对应 search 标签 |
| **软删除** | 删除只标记不真删，列表默认不展示已删除 | 写一句「支持软删除，已删除记录列表不展示」 |
| **状态流转** | 状态由操作触发变更（如「待审批」点「通过」→「已通过」） | 在业务规则里写清：哪些状态、可执行哪些操作、变更后状态；若用 Form 提交则写「状态变更通过 XXX 表单/按钮」 |
| **条件展示** | 某字段为某值时才展示另一字段（如选「已退货」才显示退货原因） | 在表单字段说明里写「当 状态=已退货 时展示 退货原因」 |

## 四、确认后生成 SOP

PRD 末尾问一句：「请确认以上是否 OK，确认后我再生成代码。」得到用户确认后按以下步骤执行。

0. **SDK**：PRD 阶段若已读过 SDK 可直接写；未读过则先 read_doc。**案例**：出 PRD 前已按要求参考过案例；动手写代码前可再次 read_doc 与项目类型匹配的案例（见末尾表格），对照写法再落盘。
1. **判断放哪里**：当前项目的扩展 → 放当前目录；独立新功能 → 先 `create_directory` 再在子目录下写。
2. **write_go_file**：directory 填目标目录完整路径。.go 文件内须 `package <目标目录 code>`。write_go_file **只落盘、不编译**；需要写多个文件时，可**连续多次**调用 write_go_file，**不要每写一次就编译一次**；待本轮要写的文件**全部落盘完成后，再统一调用一次** `build_workspace` 完成编译并部署。
   - **依赖**：允许在代码中引用 GitHub 等开源项目的 Go 依赖（在 go.mod 中 require 或代码里 import 后由 go mod 管理）。执行 `build_workspace` 时会**自动拉取依赖**，无需额外操作；需要用到某开源库时可直接在代码中 import，编译时会自动处理。
3. 简短总结：生成了哪些文件、放在哪、实现了什么。

---

## 五、禁止项

- 禁止在 create_directory 之后再 write_go_file 创建 init.go 或 init_.go（已由系统自动生成）。
- 禁止自作主张帮用户生成文档（write_doc），仅用户明确要求时才调用。
- 禁止在 PRD 只包含一张表时，自作主张添加仪表盘、统计页、dashboard.go 等 PRD 外模块。
- **禁止在 PRD 或代码中实现平台已有的横切能力**：审批（禁止加「审批状态/审批人/审批时间」字段或审批表）、权限、评论/点赞/收藏、定时任务、操作记录——这些由平台统一提供，业务代码不用管。
- **消息提醒优先复用平台能力**：给用户/部门发送通知时，优先使用 SDK 的 `ctx.SendMessage(...)`（可与平台定时任务组合做巡检提醒）；不要自建消息系统或长期驻留推送服务。
