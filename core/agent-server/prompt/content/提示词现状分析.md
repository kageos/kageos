# 工作台提示词现状分析

## 一、提示词来源与加载方式

| 来源 | 文件/位置 | 加载方式 | 用途 |
|------|-----------|----------|------|
| **工作台操作提示词** | `prompt/content/doc/工作台操作提示词.md` | `//go:embed content` → `prompt.WorkspacePrompt` | 教模型怎么操作工作台：定位、风格、PRD 先行、工具与 SOP |
| **工作台环境模板** | `prompt/content/doc/工作台环境模板.md` | `//go:embed content` → `prompt.WorkspaceEnvTemplate`；环境数据由 `prompt.BuildWorkspaceEnvData` + `BuildWorkspaceEnvBlock` 产出 | 当前用户、时间、当前目录、子目录、可读文件、可读文档列表等「环境信息」 |
| **SDK 使用文档** | `prompt/content/builtin/sdk/agent-app-sdk-readme.md` | `//go:embed content`，通过 `文档目录.json` 的 full_code_path 暴露 | 生成代码时由模型通过 `read_doc("/builtin/doc/sdk/agent-app-sdk-readme")` 拉取，不直接拼进 system |
| **文档目录** | `prompt/content/doc/文档目录.json` | `//go:embed content` → 解析为 `docCatalog` | 决定「可读文档」块里展示哪些目录/名称，以及 `read_doc` 时按 path 或 name 查正文 |
| **工作台模式** | `prompt/content/mode/<code>/`（dev/modify/execute） | `prompt.GetModeProvider(code)` 取 `WorkspaceModePromptProvider`，从各模式目录加载 config.json + system_prompt.md + first_assistant.md | 开发/修改/执行模式的提示与工具列表；`SystemPrompt(env)`、`FirstAssistantContent()`、`ToolNames()` 多态产出 |
| **Agent 系统提示** | DB `agent` 表 `system_prompt_template` | 选中工作台 Agent 时用其模板 | 自定义 Agent 的「你是谁」等前置说明 |

**stream 目录**（如 `stream/丢人管理系统/1.s`）是 **SSE 录制数据**，用于回放/测试，不是「提示词」本身。

---

## 二、System 消息拼接顺序（buildLLMMessages）

在 `workspace_chat_service.buildLLMMessages` 里，最终发给模型的 **system** 字符串按以下顺序拼接：

1. **Agent 基础身份**  
   - 未选 Agent：`"你是智能工作台的助手。\n\n"`  
   - 选了 Agent：`agent.SystemPromptTemplate + "\n\n"`（可为空则退化为「智能工作台的助手」）

2. **工作台环境块**  
   - 由 `prompt.BuildWorkspaceEnvData(envInput, ...)` 构建 `WorkspaceEnvData`，再经 `prompt.BuildWorkspaceEnvBlock(data, hasWorkspaceCtx, ...)` 产出 env 字符串（内部用 `FillWorkspaceEnvTemplate` 或无上下文时的降级文案）  
   - 无 `workspaceCtx` 时 `BuildWorkspaceEnvBlock` 返回简化「当前工作目录 + 可读目录」说明

3. **模式补充**  
   - 若有 `modeProvider`（`prompt.GetModeProvider(mode.Code)`）：`systemPromptFragment = modeProvider.SystemPrompt(data)`，否则用 DB 模式的 fallback

4. **工作台操作提示词**  
   - 固定追加：`"\n\n" + prompt.WorkspacePrompt`（即《工作台操作提示词》全文）

因此模型看到的 system 结构是：**身份 → 环境（当前目录/文件/可读文档）→ 模式说明 → 操作规则与 SOP**。

## 三、各块内容简要

### 1. 工作台操作提示词（WorkspacePrompt）

- **定位**：类似 Cursor，当前目录下边聊边干，少废话。
- **风格**：少废话、可执行；技术方案/PRD 用表格；确认要明确。
- **生成应用前**：必须先 PRD（表单字段表 + 列表模式表 + 是否新建目录），等用户确认后再生成；禁止未确认就写代码；禁止偏离 PRD 画蛇添足。
- **硬性规则**：消息顺序（assistant → tool 执行 → tool 结果）等。
- **生成代码 SOP**：先 read_doc 拉 SDK、想好放当前目录还是新建目录、write_go_file / write_doc、多文件时 build_workspace=false 最后 build_workspace。
- **工具使用**：何时用 read_dir / read_go_file / read_doc / write_go_file / write_doc / build_workspace / create_directory。
- **常见情况表**：生成系统、需求模糊、改代码、写文档、编译、多步任务、用户说「可以」等怎么应对。
- **禁止与注意**：再次强调 PRD 先行、按 PRD 实现、用 SDK 不用前端方案、必须 write_go_file 落盘等。

和「SDK 怎么写代码」分离：SDK 文档通过 read_doc 按需拉取；操作提示词只教「怎么用工具、按什么步骤做」。

### 2. 工作台环境模板（BuildWorkspaceEnvData + BuildWorkspaceEnvBlock 产出）

- 用户、时间、当前目录名称/代码/完整路径/类型、Go package 说明。
- 子目录与函数列表（ChildrenSection）、当前可读文件列表（FilesSection）、可读目录列表（DirectoryList）由 `prompt` 包根据 `WorkspaceEnvInput` 统一构建，不散落在 service 层。
- 一段「重要提示」：放哪里、package 名、何时不必调 read_dir、何时 read_go_file/read_doc、write_go_file 与 build_workspace 策略。

环境块是「当前上下文」；操作提示词是「通用规则与流程」。

### 3. 模式补充（WorkspaceModePromptProvider.SystemPrompt）

- 由 `content/mode/<code>/system_prompt.md` 等加载，多态实现；开发/修改/执行各一份。
- 开发模式：生成新代码、新模块；修改模式：修改已有代码或配置；执行模式：查看数据、分析结果等（只读工具）。

很短，用于在通用规则之上再收窄当前对话目标。

### 4. Agent 系统提示（SystemPromptTemplate）

- 库表配置，可自定义「你是谁、擅长什么」等，放在最前面，和环境、模式、操作提示词一起组成完整 system。

---

## 四、优点

1. **提示词文档化**：操作提示词、环境模板都在 md 里维护，用 embed 加载，不在代码里拼长字符串，便于修改和版本管理。
2. **职责清晰**：环境（模板 + 占位符）vs 操作规则（工作台操作提示词）vs 模式 vs Agent 身份，分层明确。
3. **PRD 先行**：明确要求先表格化 PRD、用户确认后再生成，且严格按 PRD 实现，减少返工和画蛇添足。
4. **SDK 与操作分离**：SDK 文档作为「按需拉取」的知识，不塞进 system，控制 token 且按需使用。
5. **文档目录可配置**：通过 `文档目录.json` 控制「可读文档」列表和 read_doc 的 path/name 解析，扩展内置文档方便。

---

## 五、可改进点（建议）

1. **环境模板与操作提示词长度**  
   - 若后续要接更多上下文（如更多目录、文件），可考虑：环境块做「摘要/折叠」或「分层」：必带简短摘要 + 详情按需 read_go_file/read_doc；或对超长 FILES_SECTION/DIRECTORY_LIST 做截断与说明。

2. **模式与工具的绑定**  
   - 当前模式会过滤工具列表（如执行模式只有只读工具），若在操作提示词里再写一句「当前模式为 XXX，仅会提供 YYY 类工具」，模型行为会更一致。

3. **read_doc 的 when_to_use**  
   - `文档目录.json` 里已有 `when_to_use`，若在「可读的目录」块或环境模板里把「何时应调用 read_doc（例如：生成系统前必读 SDK）」再写一句，和操作提示词里的 SOP 呼应，减少漏读。

4. **Agent 模板与工作台规则的衔接**  
   - Agent 模板若写得很长，和后面的环境 + 操作提示词拼在一起可能冲淡「操作规则」的权重；可考虑在操作提示词开头加一句「以下为工作台通用规则，请优先遵守」，或在产品上限制 Agent 模板长度并做提示。

5. **stream 目录命名**  
   - `stream/丢人管理系统/` 等是 SSE 录制，若团队容易误以为是「提示词配置」，可在目录或 README 里注明「仅用于回放/测试，非提示词」。

---

## 六、总结

- **提示词从哪来**：主要来自 `prompt/content/doc/*.md`、`prompt/content/mode/<code>/*`（embed content），以及 DB 的「Agent 系统提示」；模式提示由 `WorkspaceModePromptProvider` 多态提供。
- **怎么拼**：Agent 身份 → 工作台环境（`BuildWorkspaceEnvBlock` 产出）→ 模式（`provider.SystemPrompt(data)`）→ 工作台操作提示词（全文）。
- **特点**：文档化、分层清晰、环境构建与模式提示均封装在 prompt 包、PRD 先行、SDK 按需拉取；若再优化环境长度与模式/工具一致性、read_doc 时机和 Agent 与规则的权重，体验会更稳。

## 七、现状合理性 + System / 首条 Assistant 划分建议

### 7.1 现状是否合理？

**总体合理，但有明显可改进点：**

| 维度 | 现状 | 问题 |
|------|------|------|
| **System 内容** | 身份 + 环境 + 模式 + 操作提示词（整篇）全塞进 system | system 过长，且「操作提示词」里既有通用规则又有 SOP/表格示例，和「环境」里的重要提示有重复；模型容易忽略后半段。 |
| **首条 assistant** | 当前**没有**在会话开始时插入首条 assistant | 若希望「本会话当前模式 / 本轮你要先做啥」随会话或模式变化，没有入口；全部压在 system 里不灵活。 |
| **代码组织** | **已改进**：环境由 `prompt.BuildWorkspaceEnvData` + `BuildWorkspaceEnvBlock` 封装，模式由 `WorkspaceModePromptProvider` 多态提供；`buildLLMMessages` 只组「身份 + envBlock + provider.SystemPrompt(data) + WorkspacePrompt」，不再手写 ChildrenSection/FilesSection。 | 扩展新模式或改环境格式只需动 prompt 包与 content 目录。 |

结论：**提示词分层（身份 / 环境 / 模式 / 操作）思路对**；环境与模式已封装。若进一步优化：（1）system 可做「瘦身」与「稳定化」，（2）部分内容适合挪到**首条 assistant**。

---

### 7.2 System 里该放什么？

建议 **system 只放「稳定、通用、必须遵守」的内容**，尽量控制长度，避免被后面长文冲淡：

| 建议放入 System 的内容 | 说明 |
|------------------------|------|
| **身份** | 一句或短段：你是谁（智能工作台助手 / 或 Agent 模板）。 |
| **当前环境（上下文）** | 用户、时间、当前目录、Go package、子目录与函数列表、可读文件列表、可读文档列表（由环境模板 + 占位符生成）。 |
| **硬性规则（短）** | 消息顺序（assistant → tool 执行 → tool 结果）、禁止未确认就写代码、禁止偏离 PRD、必须 write_go_file 落盘、禁止前端方案等；用 bullet 或短表，不展开 SOP。 |
| **工具清单与用途（简短）** | 当前模式下发哪些工具、各工具一句话用途（read_go_file / read_doc / write_go_file / write_doc / build_workspace / create_directory）；可与模式绑定，避免冗长。 |

**不建议整篇塞进 system 的：**

- 操作提示词**全文**（PRD 格式、SOP 步骤、常见情况表、示例表格等）→ 可拆成「缩写版」进 system（只保留禁止项 + 工具一句话），**详细 SOP / 表格 / 示例** 放到首条 assistant 或单独「规则文档」按需 read_doc。
- 与环境重复的「重要提示」（例如写代码放哪里、package 名）→ 环境模板里保留一份即可，system 不必再重复一大段。

这样 system 以**身份 + 环境 + 硬规则 + 工具一句话**为主，长度可控，模型更容易遵守。

---

### 7.3 什么放在「首条 Assistant」里？

**首条 assistant** = 会话开始时由系统插入的一条 assistant 消息（在第一条 user 之前或紧跟第一条 user，视产品而定），用于**本会话、本轮的可变指引**，不污染 system。

| 建议放入首条 Assistant 的内容 | 说明 |
|------------------------------|------|
| **当前模式** | 如：「当前为【开发模式】，你可使用：read_go_file、read_doc、write_go_file、write_doc、build_workspace、create_directory。请先 PRD 再确认再生成。」 |
| **本轮简短指引（可选）** | 例如新建会话时：「用户即将说明需求。若涉及生成系统/应用，请先输出 PRD 表格，等用户确认后再执行生成代码 SOP。」 |
| **详细 SOP 摘要（可选）** | 若不想把整篇操作提示词塞 system，可把「生成代码 SOP」几步、PRD 两表结构，用一小段放在首条 assistant，仅在此会话生效。 |

这样：

- **System** = 稳定的身份 + 环境 + 硬规则 + 工具一句话。
- **首条 Assistant** = 当前模式 + 本会话/本轮要遵守的流程（PRD→确认→SOP），可随模式/会话配置变化。

后续若支持「会话级配置」或「不同入口不同指引」，只需改首条 assistant 内容，不必动 system 模板。

---

### 7.4 划分方式小结

| 位置 | 建议内容 | 来源/维护 |
|------|----------|-----------|
| **System** | 身份 + 环境（模板+占位符）+ 硬规则（短）+ 当前工具一句话 | 身份来自 Agent 或默认；环境来自 `工作台环境模板.md` + WorkspaceEnvData；硬规则可从《工作台操作提示词》抽一段「缩写版」或单独 `工作台硬规则.md`。 |
| **首条 Assistant** | 当前模式说明 + 可选「PRD→确认→SOP」简短指引 | 由后端根据当前 workspace 模式、会话类型生成；可配置模板，如「当前为 {{MODE}}，请 {{MODE_RULE}}」。 |
| **按需拉取** | 详细 PRD 格式、SOP 步骤、常见情况表、示例表格 | 保留在《工作台操作提示词》或拆成「规则文档」，需要时通过 read_doc 拉取，或仅在首条 assistant 里给摘要。 |

实现时：**先做 system 瘦身 + 首条 assistant 插入**，再视效果决定是否把详细 SOP 移到 read_doc。

---

### 7.5 建议增加的部分

1. **当前模式与工具列表的明确说明**  
   在 system 或首条 assistant 里写清：「当前模式为 XXX，你可使用的工具为：A、B、C；其中 A 用于……B 用于……」避免模型猜。

2. **错误与重试**  
   若希望模型在工具报错时行为一致，可加一句短规则：「工具返回错误时，根据错误信息调整后重试或向用户说明，不要重复相同错误调用。」

3. **输出格式约定（可选）**  
   若需要 PRD 或回复的固定格式（如必须包含表格），可在首条 assistant 或硬规则里写一句，避免冗长示例进 system。

4. **「工作台硬规则」独立成块**  
   把《工作台操作提示词》里的禁止项、消息顺序、必须落盘等抽成 `工作台硬规则.md`（短），embed 后只拼这一段进 system，其余 SOP/示例放首条 assistant 或按需拉取。

---

### 7.6 代码设计：接口 + 多态，参数封装在实现内部

之前「一个大结构体 + 组装函数」的方式不够好：**调用方还是要填很多字段**，本质还是「传参拼字符串」，只是换了个壳。

更好的做法：**用 interface 抽象「工作台模式提示词提供者」**，每种模式是一个**具体实现**（如 `WorkspaceDev`、`WorkspaceModify`、`WorkspaceExecute`），**参数和提示词内容都封装在实现内部**（从本模式的目录和配置文件加载）。运行时**根据当前模式 code 取对应实现**，调用同一套接口方法即可；**整体流程（buildLLMMessages、stream loop）不变**，只是「当前模式」从原来读 DB 的 fragment + tool_names，变成「取一个实现了接口的实例，用它的 SystemPrompt / FirstAssistantContent / ToolNames」。

示例（表达意图）：

```go
// WorkspaceModePromptProvider 工作台「模式提示词提供者」：多态接口，每种模式一个实现
type WorkspaceModePromptProvider interface {
    // Code 模式唯一标识，如 dev / modify / execute
    Code() string
    // SystemPrompt 返回该模式要拼进 system 的片段（身份/规则/工具说明等，可从本模式目录下的 md 加载）
    SystemPrompt(env *WorkspaceEnvData) string
    // FirstAssistantContent 返回本模式首条 assistant 内容（可为空）
    FirstAssistantContent() string
    // ToolNames 返回该模式启用的工具名列表
    ToolNames() []string
}

// 具体实现示例：开发模式，内部从 prompt/mode/dev/ 和 config 加载，不暴露字段给调用方
type workspaceDevProvider struct {
    systemPrompt      string // 从 dev/system_prompt.md 等加载
    firstAssistant    string // 从 dev/first_assistant.md 或 config 生成
    toolNames         []string
}
func (p *workspaceDevProvider) Code() string { return "dev" }
func (p *workspaceDevProvider) SystemPrompt(env *WorkspaceEnvData) string { return p.systemPrompt + ... }
func (p *workspaceDevProvider) FirstAssistantContent() string { return p.firstAssistant }
func (p *workspaceDevProvider) ToolNames() []string { return p.toolNames }
```

- **调用方**：`buildLLMMessages` 里根据当前 `mode.Code` 从 **Registry 或 Factory 取 `WorkspaceModePromptProvider` 实例**，然后只调 `provider.SystemPrompt(env)`、`provider.FirstAssistantContent()`、`provider.ToolNames()`；**不关心内部是 dev 还是 modify，也不拼任何模式相关字符串**。
- **新增模式**：新增一个目录 `prompt/mode/xxx/` + 配置文件，新增一个实现类（或通过配置驱动加载），注册到 Registry；**不改 buildLLMMessages 主流程**。
- **参数封装**：每个实现内部自己读本模式的 md、json 配置，组装好 `systemPrompt` / `firstAssistant` / `toolNames`；**对调用方完全隐藏**，避免「一搭没一搭」的传参。

这样既满足**多态、易扩展**，又满足**参数封装在内部、整体操作不受影响**。

---

### 7.7 提示词模块化：prompt/mode 目录 + 配置文件，尽量不硬编码

- **目录规划**：在 `core/agent-server/prompt/content/mode/` 下按**模式**分子目录，每个模式一个目录，里面放该模式所需的提示词和配置（与 doc 同属 embed 的 content 下）。
  - 例如：`prompt/content/mode/dev/`、`prompt/content/mode/modify/`、`prompt/content/mode/execute/`。
- **每个模式目录内**：
  - **提示词文件**：如 `system_prompt.md`（该模式拼进 system 的片段）、`first_assistant.md`（首条 assistant 内容）、`hard_rules.md`（硬规则，可选）。**尽量不在代码里写死大段文案**，从文件 embed 或按需读取。
  - **配置文件**：如 `config.json`（或 `config.yaml`），描述该模式的**元信息与行为**，例如：
    - `name`、`description`（展示用）
    - `tool_names`：该模式启用的工具列表
    - `system_prompt_file`、`first_assistant_file`：指向本目录下的 md 文件名
    - 其他开关或参数（如是否强制 PRD 先行、是否允许写文件等）
- **代码职责**：
  - 只做「根据 mode code 加载对应目录下的 config + 指定 md 文件」；
  - 各模式的具体提示词内容、工具列表、行为开关**全部由配置和文件决定**，避免在 Go 里 `switch code { case "dev": ... }` 硬编码文案和工具列表。
- **与多态结合**：每个 `WorkspaceModePromptProvider` 实现（如 `modeProvider`）在 **init 时**从 embed 的 `content/mode/<code>/config.json` 和该目录下的 md 加载，把内容存到内部字段；对外只暴露接口方法。这样**既有接口多态，又有模块化、可配置、少硬编码**。

---

### 7.8 小结

- **现状**：分层思路对，但 system 过长、无首条 assistant、代码拼字符串且面向过程。
- **System 该放**：身份 + 环境 + 硬规则（短）+ 工具一句话；操作提示词全文可瘦身或拆到首条 assistant / 按需拉取。
- **首条 Assistant 该放**：当前模式 + 本会话/本轮指引（如 PRD→确认→SOP）+ 可选 SOP 摘要。
- **建议增加**：模式与工具明确说明、错误/重试短规则、可选输出格式约定、硬规则独立成块。
- **代码设计**：用 **interface（WorkspaceModePromptProvider）+ 多态实现**（如 WorkspaceDev、WorkspaceModify），**参数与提示词封装在实现内部**，运行时根据模式实例化不同实现；整体 buildLLMMessages / stream 流程不变。
- **提示词规划**：**prompt/mode/<code>/** 下按模式放提示词 md + 配置文件（如 config.json），配置每个模式的工具列表、引用哪些 md 等；**尽量不在代码里硬编码**，由配置与文件驱动。
