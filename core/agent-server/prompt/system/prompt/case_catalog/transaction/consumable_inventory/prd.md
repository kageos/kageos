# 案例：耗材库存流水

## 一、项目概要

库存余额便于当前查询，库存流水负责审计。所有增减统一经过 Form，在一个事务里锁定耗材、校验余额、更新库存并新增不可变流水。

## 二、结构化 PRD JSON

完整标准样例见同目录 `prd.json`。

## 三、适用场景与选择边界

### 适用场景

- 数量、余额、额度或名额会被并发修改，不能只做普通 CRUD。
- 既要快速读取当前值，也要保留每次变化的原因和前后值。
- 需要禁止负库存、重复扣减或无痕改账。

### 不适用场景

- 只有商品资料管理，没有库存增减：普通单表 CRUD 足够。
- 只是记录互不影响的表单提交：参考投票或公开预约，不必建立余额表。
- 需要完整财务复式记账、批次成本或仓位管理：本案例只是轻量库存 MVP。

### 与相邻案例怎么选

| 方案 | 共享稀缺资源 | 审计流水 | 关键并发问题 |
| --- | --- | --- | --- |
| 耗材库存流水 | 库存数量 | 永久保留 | 防止超领和丢失更新 |
| 公开服务预约 | 场次容量 | 预约记录 | 防止超售和重复释放 |
| 收银台 | 商品库存与支付结果 | 支付记录 | 多商品结算和支付状态 |

## 四、实现参考

### 事务顺序

1. 校验耗材 ID、变动类型和正数量。
2. 开启数据库事务，并对耗材行加更新锁。
3. 在事务中重新读取库存，不信任表单展示的旧值。
4. 计算新库存；小于 0 时返回业务错误。
5. 更新余额并新增流水，两步任一失败都回滚。
6. 提交后读取当前库存，作为表单响应。

### 数据边界

- 流水表 `handlers` 为空，避免生成修改和删除入口。
- 余额字段可以展示，但编辑耗材资料时不能接受用户提交的新余额。
- 纠错通过新增反向流水，不覆盖原记录。
- 经办人从当前身份获取，不信任前端传入的姓名。

### 五分钟价值路径

先入库 10，再并发发起两次领用 8。最终只能有一次成功，库存为 2，流水与余额一致；随后做一次盘盈并确认前后库存完整可追溯。

### 不要照搬

涉及金额时还要明确精度、币种、舍入和会计规则；涉及多仓、多批次或序列号时应增加独立模型，不要继续把所有概念塞进一个库存字段。
