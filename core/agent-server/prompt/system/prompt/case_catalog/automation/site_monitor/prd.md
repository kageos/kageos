# 案例：站点可用性巡检

## 一、项目概要

这是确定性自动化案例：按固定频率读取启用目标、执行网络检测、保存结果、更新当前状态，只在故障和恢复边沿通知负责人。手工“立即检测”和定时执行复用同一业务函数。

## 二、结构化 PRD JSON

完整标准样例见同目录 `prd.json`。

## 三、适用场景与选择边界

### 适用场景

- 执行时间、输入、判断条件和动作都可以用代码明确描述。
- 需要稳定频率、低成本运行、可重试和完整日志。
- 典型任务是巡检、超期扫描、阈值提醒、日报聚合和状态同步。

### 不适用场景

- 需要阅读自然语言文档、综合上下文判断或生成非模板建议：使用 AgentTask。
- 只是用户临时点击一次：只保留普通 Form，不必配置 schedule。
- 目标地址来自任意外部输入且没有网络边界校验：不能直接开放检测。

### 与相邻案例怎么选

| 方案 | 是否需要模型 | 触发方式 | 典型输出 |
| --- | --- | --- | --- |
| 站点巡检 | 否 | Form schedule 或手工 Form | 确定状态、日志、通知 |
| 知识驱动售后工单 | 是 | AgentTask 周期执行 | 基于 docs 的处理或转人工 |
| 混合 CRM 跟进 | 部分需要 | schedule + AgentTask 分工 | 到期提醒 + 内部建议 |

## 四、实现参考

### 复用一个执行核心

把“读取目标、校验地址、请求、计时、分类结果、写日志、更新状态”放入普通函数。`app.FormTemplate` 的提交回调调用它，`app.FormSchedule` 的处理函数也调用它，避免手工和定时行为漂移。

### 状态边沿通知

执行前读取旧状态，执行后计算新状态：只有 `正常 -> 故障` 和 `故障 -> 正常` 调用通知。每轮都写检测记录，但连续故障不重复通知。发送失败应保留业务结果并记录可重试信息，不能回滚真实检测事实。

### 安全和稳定性

- 只允许 HTTP/HTTPS，并限制可访问目标范围，防止被当作内网探测器。
- 设置短超时、响应体上限和并发上限；日志只保留错误摘要。
- 同一轮任务记录运行标识，重复触发时避免重复通知。
- Chart 只从检测记录聚合，不在图表回调中再次发网络请求。

### 五分钟价值路径

创建一个正常目标和一个故障目标，手工检测验证两类记录；再运行一次 schedule，确认连续故障不重复通知；恢复故障目标后确认只收到一次恢复通知。

### 不要照搬

检测地址白名单、正常状态码范围、频率和通知对象必须按部署环境定义。业务只是“每天找逾期记录”时，保留相同的 schedule 与边沿思想，但不要引入网络检测代码。
