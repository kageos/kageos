# 案例：公开服务预约

## 一、项目概要

公开 Form 负责低门槛收集客户预约，内部 Table 负责确认和履约。场次容量与预约记录在事务内同步，取消只释放一次名额，并用业务编号支持查询和幂等返回。

## 二、结构化 PRD JSON

完整标准样例见同目录 `prd.json`。

## 三、适用场景与选择边界

### 适用场景

- 提交人不是工作空间成员，需要通过公开入口提交。
- 外部提交后还需要内部人员确认、分配、完成或取消。
- 存在场次容量、重复提交、状态流转和隐私字段隔离。

### 不适用场景

- 只给内部员工预约会议室：优先参考会议室预约，使用用户身份和内部资源选择。
- 没有容量和后续处理，只收集信息：普通公开 Form + Table 即可。
- 需要在线支付、退款或复杂排班：应在本案例基础上单独设计支付和资源日历边界。

### 与相邻案例怎么选

| 方案 | 提交者 | 资源约束 | 后台流程 |
| --- | --- | --- | --- |
| 公开服务预约 | 外部客户 | 场次容量 | 确认、完成、取消 |
| 会议室预约 | 内部用户 | 时间冲突与会议室容量 | 会前提醒 |
| 投票/问卷 | 外部或内部均可 | 通常无共享容量 | 汇总统计 |

## 四、实现参考

### 公开面与内部面分开

公开 Form 只接收场次、姓名、联系方式、人数和必要备注；负责人、内部备注、状态更新能力只存在于内部 Table。选择器只返回开放且剩余容量足够的场次。

### 创建预约

在事务内锁定场次，重新检查开放状态、开始时间和剩余容量，再生成预约编号、插入预约并增加已预约人数。同一提交标识已经成功时返回原预约，不重复占用。

### 取消与状态机

验证预约编号和联系方式，只允许未完成记录取消。状态首次变为已取消时才减少已预约人数；重复调用直接返回现有结果。内部更新也必须校验允许的状态迁移，不能任意改回早期状态。

### 五分钟价值路径

把场次容量设为 1，同时提交两次预约，确认只有一次成功；取消成功预约后再次提交应成功；重复取消不能把已预约人数减成负数。

### 不要照搬

联系方式属于敏感信息，展示、搜索、日志和通知都应最小化。公开入口必须增加频率限制和重复提交防护，不能直接复用内部 Table 的增删改接口。
