# 案例：程序与 Agent 混合的销售跟进

## 一、项目概要

程序维护客户、真实跟进记录、到期时间和提醒；AgentTask 阅读已启用销售方案，为当天待跟进客户生成内部准备建议。事实与建议分栏保存，模型不冒充已发生的客户沟通。

## 二、结构化 PRD JSON

完整标准样例见同目录 `prd.json`。

## 三、适用场景与选择边界

### 适用场景

- 同一流程同时包含确定性数据操作和需要语义理解的准备工作。
- 模型输出有价值，但不应该直接改变客户事实或自动联系外部人员。
- 销售方案由业务人员通过 docs 持续维护。

### 不适用场景

- 只是按日期提醒销售：只使用 Form schedule，不需要 AgentTask。
- 已有固定模板和明确条件即可生成消息：优先用程序模板，成本更低且更稳定。
- 要让模型自动报价、承诺条款或发送客户消息：需要额外审批，不能照搬本案例。

### 与相邻案例怎么选

| 方案 | 程序负责 | Agent 负责 | 是否对外动作 |
| --- | --- | --- | --- |
| 混合 CRM 跟进 | 事实、状态、到期扫描、提醒 | 读取方案并准备内部建议 | 默认没有 |
| 知识驱动售后工单 | 记录和安全约束 | 低风险处置或转人工 | 可有受限动作 |
| 站点巡检 | 全部检测和通知 | 不需要 | 只发确定性通知 |

## 四、实现参考

### 先划事实和建议

客户阶段、沟通纪要、跟进时间是事实，只能由明确的 Form 或 Table 操作更新。跟进建议是派生内容，必须单独字段保存，并标注生成时间和依据，不能反写成“客户已确认”。

### 两条自动化链路

1. `app.FormSchedule` 扫描已经到期且未关闭的客户，按规则通知负责人；不调用模型。
2. `app.AgentTask` 读取 runbook、客户事实和已启用方案，为近期客户准备建议；缺少依据时只记录知识缺口。

两条链路使用不同幂等标识和结果字段，避免提醒成功被误认为建议已经生成。

### Agent 边界

- 不发送邮件、短信或聊天消息给客户。
- 不修改销售阶段、沟通纪要和历史跟进记录。
- 不补写客户没有表达过的预算、时间或承诺。
- 输出包含事实摘要、适用方案、建议问题、风险和缺失信息。

### 五分钟价值路径

创建一个明天到期的客户和一份已启用方案。运行准备任务后，应产生带依据的内部建议，但沟通纪要不变；运行到期提醒后，负责人收到通知，但不会重复生成建议或虚构联系记录。

### 不要照搬

原 mini CRM demo 资源较多，本案例只保留“事实由程序维护、建议由 Agent 生成”的分工。先做客户、跟进记录和一条建议链路，确认业务使用后再增加机会、联系人或更复杂报表。
