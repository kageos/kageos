# kageos_manifest.go / runbook.docs / AgentTask 写法

这份文档用于写或审查 `kageos_manifest.go`、`runbook.docs` 和 `AgentTask.Message`。产品界面和用户语言里的“数字员工”“值守员工”默认指 `agent.session` Agent 任务；用户要求创建数字员工时，应创建或声明 AgentTask，而不是创建用户、角色或普通定时函数。命中这些对象时必须先区分目录级运行契约和具体无人值守任务，不要把两者混成一段提示词。

## 核心区别

`kageos_manifest.go` 用来给一个 kageos package 声明出厂默认资产。第一版只放两类东西：

- `runbook.docs`：目录级运行手册。
- `AgentTask`：某个具体无人值守任务的默认模板。

它们都是 seed，不是长期权威源。build/update 后，平台会把缺失的文档和默认 Agent 任务挂到 Service Tree；后续运行态以树上的 `runbook.docs` 和平台里的任务配置为准。代码里的 `kageos_manifest.go` 只负责首次创建，不应覆盖线上人工维护过的内容。

`runbook.docs` 是面向业务人员的目录使用说明和稳定处理规则。不了解 kageos、数据库或 Agent 工具的人，也应该能看懂、敢于修改，并用它表达“公司希望事情怎么处理”。Agent 进入这个目录后，同样以这些业务规则作为判断依据。

`AgentTask.Message` 是某个具体无人值守任务的执行单。它描述一次定时或自动任务如何闭环，例如每天生成公众号草稿、每小时巡检证书、定时搜索新闻并入库。它必须写清本轮任务目标、时间窗口、工具、分页、幂等、去重、写入规则、失败处理和通知规则。

一句话：`runbook.docs` 管“公司希望这类事情怎么处理”，`AgentTask.Message` 管“Agent 到点后具体怎样安全执行”。

## 业务文档与技术执行的边界

不要把业务人员变成 Agent 工程师。`runbook.docs`、`docs/readme.docs` 和 `docs/*.docs` 默认由不懂技术的业务人员长期维护；`AgentTask.Message`、代码和测试负责技术可靠性。

业务文档必须写清模型不能替公司决定的事实：

- 什么情况下使用这条规则或解决方案。
- 处理前需要哪些业务信息；缺少时向谁补充或转交。
- 公司认可的处理步骤、回复口径和完成标准。
- 系统可以做到哪一步：只答复、可以查询并答复、可以完成明确的低风险操作，还是必须人工处理。
- 哪些情况必须停止、转人工，以及谁来接手。

业务文档不要要求维护者填写模型可以从真实资源中确认的实现细节：

- 工具名称、schema、JSON 字段名、物理字段、内部 ID。
- 参数映射表、分页参数、认领锁、超时时间、重试次数。
- 幂等键、去重实现、接口返回结构和数据库写法。

这些技术规则不能丢失，应写入 `AgentTask.Message` 或代码。Agent 执行前自行搜索真实资源和 schema，确认参数、权限、影响范围、去重和验证；无法确认就转人工，不能要求业务文档维护者补一份技术说明。

判断是否越界可以用两个问题：

1. Form/Table 的字段改名后，业务文档是否也必须跟着改？如果是，文档通常写得太技术化。
2. 两位员工可能基于公司政策做出不同决定吗？如果会，这条业务规则必须写清，不能让模型猜。

## 子目录文档种子

同一个业务 package 需要把文档放到子目录时，仍然使用原来的 `packageContext`，在 `DocManifest.Code` 中填写 package 内相对路径；不要为文档目录额外声明 `PackageContext`：

```go
packageContext.AddDocs(app.DocManifest{
	Code:    "./docs/readme.docs",
	Name:    "文档/目录说明",
	Content: "# 文档目录说明\n",
	Format:  "markdown",
})
```

build/update 时，SDK 会自动把缺失的中间目录加入目录对账，并创建 `<当前 package>/docs/readme.docs`。`Name` 是文档展示名称，不是新目录的 `PackageContext.Name`。`Code` 只能使用 package 内相对路径，不允许绝对路径、反斜杠、空路径段、`.` 或 `..`。

源码中的新声明统一写 `.docs` 后缀。SDK 会把它规范化成 package 内相对文档 code 后参与 diff 和目录对账，并兼容旧的无后缀声明；新代码和示例不要省略后缀。

## 资源引用

文档和任务说明里引用当前目录资源时，使用轻量资源标记：

- 当前目录表格：`<./profiles.table>`
- 当前目录表单：`<./send_notice.form>`
- 当前目录图表：`<./risk_report.chart>`
- 当前目录文档：`<./runbook.docs>`
- 同一服务目录内的兄弟服务目录资源：`<../shared/render.form>`
- 用户明确指定的跨工作空间资源：`</alice/support/tickets.table>`（不可移植，复制后需重新绑定）
- 内置 Agent 工具：`<tool:send_notification>`

不要写 `./profiles.table`，也不要写 `<profiles.table>`；所有资源引用都放在尖括号中。选择顺序是：当前服务目录 `<./...>`，同一服务目录的兄弟服务目录 `<../...>`，最后才是跨工作空间绝对标记 `</...>`。只有用户明确要求绑定其他工作空间，而且无法用稳定相对关系表达时才使用绝对路径；必须在说明中标记“不可移植，复制或安装到其他实例后需重新绑定”。不要为了省事把本可相对引用的资源写成绝对路径。引用内置工具时不要写 `<send_notification>`，因为它不是 Service Tree 资源路径；需要回显工具 chip 时写 `<tool:send_notification>`，真实工具调用名仍是 `send_notification`。

轻量资源标记只提供导航和语义引用，不会自动查询数据。真正查询表格时，Agent 仍要调用 table 工具，并按分页读完。

## runbook.docs 写法

高质量 `runbook.docs` 应该像一份简短的“使用说明与处理规则”，不是 README、PRD、技术设计或某个定时任务 prompt。默认控制在一到两个屏幕能读完的长度；复杂场景拆到 `docs/*.docs`，不要继续堆在 Runbook。

使用用户界面上的业务名称和自然语言。可以用资源 chip 帮维护者点击查看“工单工作台”或“面试进度查询”等已有功能，但不要要求用户理解 `.table`、`.form`、schema、字段映射或工具名。技术路径存在于底层引用即可，不要成为正文的解释重点。

建议结构：

```markdown
# <服务目录>使用说明

## 这个工具能帮你做什么

用几句话说明适合解决的问题和最终结果在哪里查看。

## 怎么开始

说明用户从哪个入口提交或查看，需要提供哪些业务信息。

## 提交后会发生什么

用业务步骤说明系统会答复、查询、处理还是转人工。

## 系统可以做到哪一步

说明哪些事情可以自动完成，哪些必须先确认或交给人工。

## 什么情况会转人工

列出没有可靠方案、信息不足、结果冲突、高风险等业务条件，以及接手人。

## 人工处理后如何留下解决方案

说明在哪个文档目录维护、谁审核、何时可供下次使用。

## 通知和结束

说明谁会在什么情况下收到消息，什么状态代表事情结束。
```

Runbook 只写稳定业务规则，不写某个 cron 的细碎安排。像“黄金报价单位默认是元”“本目录不提供投资建议”属于 Runbook；“分页读完、每轮最多处理 5 条、认领超时 30 分钟”属于 AgentTask。

## 文档优先的场景知识闭环

当应用需要让 Agent 随人工处理经验持续变得更有用时，默认使用 `runbook.docs + docs/*.docs`，不要先建一张与文档重复的知识表：

- `runbook.docs` 保存稳定业务规则：怎么开始、系统能做到哪一步、何时转人工、谁接手、怎样通知和结束。
- `<./docs/readme.docs>` 用普通人的语言说明解决方案目录怎么用；其他 docs 一份文档对应一个可复用场景。
- 场景文档写清状态、什么时候使用、需要哪些业务信息、怎么处理、系统可以做到哪一步、怎么回复、失败时找谁。不要把 schema、字段名、参数映射和幂等规则做成必填模板。
- 只有人工审核且正文明确“已启用”的场景文档，才能作为正式回复或自动执行依据。“待确认”和“已停用”文档必须被忽略。
- 场景文档引用已有查询或处理功能时优先使用 `<./...>` 或 `<../...>`。用户明确要求跨工作空间编排时可以使用 `</...>` 绝对标记，但必须说明它不可移植、复制后需要重新绑定。维护者只需要说明这个功能在业务上用来做什么；Agent 执行前自行搜索真实 schema，确认参数来源、权限、风险、幂等和执行后验证。

推荐的场景文档模板：

```markdown
# <解决方案名称>

状态：待确认 / 已启用 / 已停用

## 什么时候使用

## 处理前需要什么信息

## 怎么处理

## 系统可以做到哪一步

只提供答复 / 可以查询并答复 / 可以完成明确的低风险操作 / 必须人工处理

## 可以使用的功能

通过 `/` 插入已有功能；没有则写“无”。

## 怎么回复

## 处理失败怎么办
```

推荐闭环：

```text
Agent 搜索已启用场景文档
→ 命中且条件匹配：回复、只读查询或执行低风险可验证动作
→ 没有可靠方案：记录已查证据并转人工
→ 人工填写原因、解决方案和验证结果
→ 通知处理人确认“无需沉淀 / 待沉淀”
→ 有文档维护权限的人创建或更新 docs
→ 人工审核为“已启用”
→ 后续相似问题复用
```

运行态 Agent 可以通过 `read_file`、`edit_file`、`write_file` 维护必要的 `.docs` 运行记忆，但文件工具在 `app_operator` 下只能操作 `.docs`，不能修改代码或普通文本。新建文档时 `file_name`/`code` 使用有意义的英文标识，中文项目的工作台 `name` 使用清楚的中文名称。运行记忆只保留当前仍存在、确实重要的问题；问题解决后直接删除对应内容，不维护“已解决”列表。正式 runbook、长期规则和已启用方案仍由维护流程管理，运行态 Agent 不得借运行记忆改写自身权限或执行规则。只有知识条目确实需要独立生命周期、结构化筛选、统计或批量治理时，才增加 knowledge Table；即使增加，也要明确 Table 与 docs 各自唯一职责，不能保存两份互相冲突的权威方案。

## AgentTask 无人值守价值门禁

写 `AgentTask.Message` 前先证明任务在后台运行会产生新增价值，而不是把当前交互可解决的问题延迟处理。

- 提交时已经能确定的必填、格式、附件、权限、关联存在性、状态合法性、确定性重复和计算错误，必须由 Form handler 或 Table 回调同步校验；不能交给 AgentTask 事后退回。
- 耗时校验如果决定业务记录是否有效，记录必须先处于“草稿/校验中”，通过后才进入“已受理”；不能先显示成功再补发错误。
- AgentTask 适合时间流逝、外部状态变化、持续观察、跨记录分析和多资源语义判断，例如 SLA 风险、无人接单、外部回执、相似工单聚类和跨客户事故识别。
- 每个任务都要写清结果回写位置、人工接手点、幂等、失败处理和停止条件。只生成无人处理的报告、只搬运错误、只增加一次退回或补交流程，不算闭环。

可用一个反事实判断：删除这个 AgentTask 后，是否真的需要某个人持续盯、等、查或协调？如果不需要，而且任务只是晚一点发现同一个输入错误，就不要创建。

## AgentTask.Message 写法

AgentTask 是无人值守任务，运行时用户不在线，所以不能写“到时候问我”。任务必须自己闭环，遇到不能决定的事要降级、记录、通知或留下人工待办。任务 message 应明确负责人；未指定时，运行环境按目录管理员、目录创建人、任务创建人/当前用户顺序提供人工接管候选人。通知可以征求后续决定，但当前执行不能等待回复后继续高风险动作。

高质量 AgentTask 必须先分析再执行。每轮先确定数据范围：最近 N 条、抽样、完整时间窗口或全部数据。要求完整时间窗口、总体统计或全量对象时必须分页覆盖目标范围并核对数量；有限范围按范围停止。不能只读第一页却声称完成全量分析，也不要机械要求所有任务读取全部历史。随后制定执行方案：本轮要处理多少、最多处理多少、选择哪些对象、为什么选择它们、是否需要 `web_search` 或外部数据、执行后如何验证。方案用于约束无人值守执行，不是等待用户确认。

通知治理优先保证重要事项不漏发。可能造成资损、安全/隐私/合规问题、数据损坏或丢失、大范围业务影响、关键任务持续失败/阻塞、权限异常，或明确需要人工决定时必须通知；影响未完全确认但存在合理重大风险时至少发 warning。首次基准、无变化、无待处理对象和普通成功状态默认静默；同一问题无新进展或影响扩大时不要重复通知。异常通知应包含任务/目录背景、对象/时间范围、事实证据、影响风险、已做/未做动作及原因和具体接管事项，让另一个 Agent 或人工能在新会话直接接手。

无人值守运行不是开发会话。发现应用 bug、schema/权限问题或需要代码修复时，禁止修改 Go 代码或普通文本、build、创建/删除目录或文件；只收集证据、记录真正重要且仍未解决的问题、通知负责人，并停止相关高风险动作。

AgentTask 的方案要区分“执行前缺口快照”和“执行后剩余缺口”。不要用执行后的数据解释执行前计划，也不要把本轮选择处理的对象数量当作真实总缺口。若任务有单轮上限，计划新增数通常应等于 `min(执行前真实总缺口, 单轮上限)`；如果少于这个数，必须写明素材不足、重复风险、写入失败或其他跳过原因。若执行后发现仍有缺口且不超过上限、也没有跳过原因，应继续补齐再验证。

不要让模型长期口算可由后端确定的工作量。像目标数、已有数、缺口数、完成率、待处理数、逾期数这类反复用于自动任务计划的数字，优先在主工作台 Table 行里用 `gorm:"-"` 展示字段或后端查询补齐，例如“已有草稿数 / 待补篇数 / 生产进度”。比例、完成率和进度优先使用 `widget:"type:progress;min:0;max:100;unit:%"`，不要用普通文本让模型再解释。AgentTask 应要求读取这些确定性字段，再用明细表复核标题、失败项和重复风险。

生成子记录时必须在新增时绑定上游业务对象，例如从选题生成草稿、从合同生成节点、从证书生成续期任务。不要先创建未绑定的子记录，再靠更新回调补外键或上下文；如果写入后发现上游展示名称为空，要把它视为写入不合格，不计入成功。

内容生产类 AgentTask 要明确事实和表达规则：允许在需要公开事实、新闻、产品信息、行业数据时使用 `web_search`；使用外部资料时必须记录来源。没有来源时不要编造数据、案例、引用或第一人称经历。还要写清反 AI 味要求，例如避免空泛套话、同质化结构和无场景的正确废话。

建议结构：

```markdown
## 执行身份

说明这是无人值守任务，不能向用户提问，必须按 <./runbook.docs> 执行。

## 无人值守价值

说明本任务处理的是哪种时间变化、外部状态、持续观察或跨记录判断，为什么不能在用户当前操作里同步完成，以及结果回写到哪里、谁接手、何时停止。

## 绑定范围

- 运行规则：<./runbook.docs>
- 输入资源：<./xxx.table>
- 输出资源：<./yyy.table>
- 外部工具：web_search / <tool:send_notification> / 其他连接器

## 责任人与人工接管

写清任务负责人；未指定时按目录管理员、目录创建人、任务创建人/当前用户顺序接管。需要人工决定时，本轮只发送完整交接通知并停止未获授权的动作，不等待回复后继续执行。

## 本轮目标

说明这一次定时任务要完成什么，不要泛泛写“优化业务”。

## 时间窗口和幂等

说明本轮读取哪个时间范围、如何避免重复处理、唯一键是什么、遇到已存在记录怎么办。

## 预期工具

列出预计使用的工具，例如 table 查询、table 新增、table 更新、web_search、send_notification。写入文档或任务说明时，内置通知工具可标成 `<tool:send_notification>`。

## 执行步骤

1. 先读 <./runbook.docs>。
2. 按任务规定的数据范围读取输入；完整时间窗口、总体统计或全量对象必须分页覆盖并核对数量，最近 N 条或抽样按规定范围停止。
3. 制定本轮执行方案：优先使用后端已计算的执行前缺口快照、真实总缺口、单轮上限、选择对象、预计产出、事实来源策略、验证口径。
4. 按方案过滤、去重、写入或更新目标数据；新增子记录时必须绑定上游对象。
5. 执行后重新读取目标数据验证，不要只相信写入接口返回。
6. 若执行前缺口不超过上限但执行后仍有缺口，且没有明确跳过原因，继续补齐并再次验证。
7. 汇总本轮结果，确保执行前缺口、计划新增、实际新增、执行后剩余缺口和分项明细一致。
8. 按通知规则通知或静默结束。

## 质量控制

列出本任务特有的质量规则，例如新闻入库前必须判断 URL 或标题是否重复。

## 失败处理

说明关键失败、非关键失败、部分成功、无数据时分别怎么做。

## 输出格式

规定最终日志或通知包含哪些字段。
```

任务说明里可以重复 Runbook 的关键硬边界，但不要复制整本 Runbook。AgentTask 应引用 `<./runbook.docs>`，并承担业务文档没有写出的技术执行细节，例如工具选择、schema 确认、字段匹配、分页、认领、幂等、重试、写入和验证。不要反过来要求业务人员把这些技术细节补进 docs。

## Goodcase

### runbook goodcase

```markdown
# 证书到期提醒使用说明

## 这个工具能帮你做什么

持续查看公司域名证书的到期时间，在风险出现时生成续期待办，避免负责人每天手工检查。

## 怎么开始

在 <./certificates.table> 登记域名、证书来源、到期时间和负责人。

## 提交后会发生什么

证书进入到期前 30 天时，系统在 <./renewal_tasks.table> 生成待处理事项；已经有未完成事项时不重复创建。

## 系统可以做到哪一步

可以自动整理续期待办和提醒内部负责人。续期、替换生产证书和向客户发送正式通知必须人工确认。

## 通知和结束

证书已经逾期时通知负责人；没有新增风险时不发送消息。续期完成并经人工确认后结束当前待办。
```

为什么好：业务人员不用理解工具、schema、分页或幂等，也能看懂入口、结果、自动化边界和结束条件；具体去重、分页和通知实现留在 AgentTask。

### AgentTask goodcase

```markdown
## 执行身份

你正在执行证书每日巡检任务。用户不在线，不能向用户提问。先阅读 <./runbook.docs>，并严格遵守人工确认边界。

## 绑定范围

- 运行规则：<./runbook.docs>
- 证书台账：<./certificates.table>
- 续期任务：<./renewal_tasks.table>
- 通知工具：<tool:send_notification>

## 本轮目标

扫描未来 30 天内到期的证书，为缺失续期任务的证书生成待处理任务；对已经逾期的证书通知负责人。

## 时间窗口和幂等

以任务执行时的 Asia/Shanghai 日期为准。对同一 certificate_id 和 due_date，若已存在未关闭续期任务，不再重复创建。

## 执行步骤

1. 阅读 <./runbook.docs>。
2. 分页读取 <./certificates.table> 全部启用证书。
3. 找出 30 天内到期和已逾期证书。
4. 分页读取 <./renewal_tasks.table>，按 certificate_id 去重。
5. 为缺失任务的证书创建续期任务。
6. 对已逾期证书发送通知；普通无变化结果不通知。
7. 输出本轮扫描证书数、新增任务数、逾期数、通知状态。
```

为什么好：它是一个具体任务，有时间窗口、幂等规则、分页、写入目标、通知规则和输出格式。

## Badcase

### runbook badcase

```markdown
# 运行手册

每天看看证书，有问题就处理。可以发通知。
```

问题：没有资源、没有状态、没有 SOP、没有异常处理、没有禁止事项。Agent 遇到移动端回复或临时分析请求时只能猜。

### AgentTask badcase

```markdown
每天帮我搜集新闻，写入表格，有问题问我。
```

问题：无人值守任务不能问用户；没有数据源、主题、去重、分页、入库字段、失败处理和通知规则，极容易重复写入或乱写。

### 资源引用 badcase

```markdown
读取 ./profiles.table，然后写 drafts.table。
```

问题：资源引用不可点击，也不利于工具解析。应该写 `<./profiles.table>` 和 `<./drafts.table>`。

## 检查清单

写 `runbook.docs` 前检查：

- 一个不了解 kageos、数据库和 Agent 工具的业务人员能否读懂并修改。
- 是否说明怎么开始、提交后发生什么、系统能做到哪一步、什么情况转人工、谁接手和何时结束。
- 是否只表达技术能力造成的业务后果，而没有解释 schema、字段、工具、分页、认领、重试或幂等实现。
- 复杂的具体场景是否已经拆到 `docs/*.docs`。
- 是否避免写某个具体定时任务的细碎 cron 流程。
- 涉及可成长知识时，是否区分稳定 Runbook 与具体场景 docs，并写明人工启用门禁和未知问题沉淀闭环。

写 `AgentTask.Message` 前检查：

- 是否通过无人值守价值门禁，且没有把提交时可确定的错误延迟到后台。
- 是否说明任务处理的后来状态或跨记录价值、结果回写位置、人工接手点和停止条件。
- 是否第一步要求阅读 `<./runbook.docs>`。
- 是否说明本轮目标、时间窗口和幂等规则。
- 是否明确任务负责人或人工接管顺序。
- 是否列出预期使用工具；需要回显内置工具时，是否使用 `<tool:...>` 标记。
- 是否写清数据范围，并只在完整时间窗口、总体统计或全量对象时要求分页覆盖和数量核对。
- 是否写清重要事项必发、普通无变化静默、重复通知抑制和可跨会话接管的通知正文。
- 是否区分执行前缺口快照和执行后剩余缺口。
- 如果单轮上限内没有补齐全部缺口，是否要求写明跳过原因。
- 新增子记录时是否要求绑定上游业务对象，而不是先写无归属记录再补。
- 是否能在用户不在线时自行闭环。
- 是否明确失败处理和无数据处理。
- 是否避免自动执行发布、付款、审批通过等高风险动作。
- 是否禁止运行态修改代码、普通文本、build、创建/删除目录或文件。
- 使用场景 docs 时，是否只允许“已启用”文档，且无匹配时回写证据并转人工。

写 `kageos_manifest.go` 前检查：

- 文件名必须是 `kageos_manifest.go`，不要用 `_init_data.go`。
- 默认文档使用 `packageContext.AddDocs(app.DocManifest{Code: "runbook.docs", ...})`。
- 子目录文档使用原 `packageContext.AddDocs(app.DocManifest{Code: "./docs/readme.docs", ...})`；不要额外声明 `PackageContext`。
- 如果 docs 只是场景方案载体，是否避免再创建保存同一内容的 knowledge Table。
- 默认 Agent 任务使用 `packageContext.AddAgentTask(app.AgentTask{...})`。
- 数字员工默认显式写 `Enabled: false`，安装后由用户在平台中自行开启；不要让高成本 Agent 会话随安装自动运行。
- 不要给 AgentTask 填 `Policy`，默认就是缺失才创建。
- build/update 后才会把 seed 同步到 Service Tree。
