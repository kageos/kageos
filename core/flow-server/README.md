# Flow Server

`flow-server` 计划作为平台级的**流程与审批控制面**。

它不是某个业务系统里的审批模块，也不是只服务“权限申请”的小功能，而是面向整个平台的横切能力：

- 所有高风险动作都可以先进入 `flow-server`
- 命中策略则进入审批流
- 审批通过后，才执行真实回调或真实业务动作
- 审批拒绝则终止执行

一句话说：

> **flow-server 的目标，是把“先审批，后执行”做成平台通用能力，而不是让每个业务系统自己重造审批。**

## 背景

AI-Agent-OS 的核心思路一直是：

- 权限不要在业务里重复实现
- 审批不要在业务里重复实现
- 日志不要在业务里重复实现
- 文件、评论、定时任务等横切能力，也不要在业务里重复实现

随着平台上的 `Form / Table / Docs / Board / 外部 API 能力` 越来越多，审批如果继续散落在每个系统里单独写，会很快遇到这些问题：

- 每个系统都要自己维护审批状态、审批人、审批记录
- 相同的审批规则在不同系统里重复实现
- 业务代码和审批逻辑强耦合，后续难维护
- AI 虽然能生成业务系统，但审批策略无法平台化复用
- 审计、通知、催办、超时、转交、加签等能力无法统一沉淀

因此需要独立的 `flow-server`，把审批从业务代码里抽离出来，做成平台层的通用控制面。

## 核心定位

`flow-server` 的核心定位不是“再做一个 OA 审批系统”，而是：

**给平台上的任意资源动作，统一提供流程判断、审批编排、状态管理和审批后执行能力。**

它关注的对象不是“页面长什么样”，而是：

- 对哪个资源做动作
- 动作类型是什么
- 操作人是谁
- 改了哪些字段
- 从什么值改成什么值
- 是否命中审批策略
- 命中后应该走哪条流程
- 审批通过后调用哪个真实执行器

## 能力边界

`flow-server` 优先面向“动作”建模，而不是面向“节点类型”建模。

第一阶段重点支持：

- `table.create`
- `table.update`
- `table.delete`
- `form.submit`
- 外部 API 的写操作

第二阶段逐步扩展：

- `docs.create / update / delete / publish`
- `board.post.create / update / delete`
- `service_tree` 相关变更
- 发布、推送、复制、导入等高风险平台动作

关于 `chart`：

- 纯查询类 `chart.query` 默认不一定需要审批
- 但图表导出、对外分享、触发式重算、敏感查询等动作，可以统一纳入 `flow-server`

也就是说，**是否审批由策略决定，不由资源类型强行决定。**

## 典型场景

### 1. 字段级审批

例如：

- 更新职位记录时，普通字段直接通过
- 但如果 `status` 被修改为 `下线`，则必须进入审批

这类规则的价值非常高，因为企业里真正敏感的，往往不是“能不能编辑”，而是“改成什么值才算高风险”。

### 2. 表单提交先审批后执行

例如：

- 用户提交证书申请
- 数据先进入 `flow-server`
- 审批人看到完整表单数据进行审批
- 只有审批通过后，才真正触发后端回调逻辑

业务代码无需关心审批过程，只在最终执行阶段感知一次“合法回调”。

### 3. 文档与讨论区治理

例如：

- 制度文档更新需要负责人审批后才正式发布
- 讨论区删帖需要审核后才真正删除
- 重要公告发布需要串签后再生效

### 4. 外部系统动作审批

例如：

- 调用云平台 API 删除资源前，需要审批
- 调用第三方系统修改关键状态前，需要审批

这样可以把历史系统和外部系统也纳入统一控制面。

## 业务价值

从业务角度看，`flow-server` 的价值主要有六点：

1. **统一控制**
   - 所有关键动作都能先经过平台审批，而不是散落在各个系统里各管各的

2. **降低业务实现复杂度**
   - 业务系统只关心业务回调，不需要自己维护审批状态和流程编排

3. **复用性强**
   - 同一套审批模式可以作用在多个系统、多种资源类型上

4. **合规与审计更容易**
   - 审批链、执行链、操作人、审批人、时间线都可以平台统一记录

5. **AI 更容易参与**
   - 用户可以直接描述“什么情况下要审批”，由 AI 生成结构化流程配置

6. **商业价值高**
   - 它天然适合放在企业版，作为平台级治理能力，而不是单个应用功能

## 产品价值

如果这套能力做成，平台对外卖的就不只是“会生成应用”，而会升级成：

- 能生成应用
- 能治理应用
- 能控制关键动作
- 能把审批、审计、组织、权限统一起来

这会显著提升企业版价值，特别适合：

- 审批填报系统
- 台账系统
- 内容治理系统
- 对接外部 API 的运营平台
- 内部控制要求高的业务系统

## 技术主线

### 总体思路

在平台统一入口处，先把请求封装成一个标准动作对象，再交给 `flow-server` 判断是否需要审批。

如果不需要审批：

- 直接调用原来的真实执行器

如果需要审批：

- 创建流程实例
- 保存待审批动作
- 返回“待审批”状态
- 审批通过后，再执行真实动作

### 标准动作对象

建议统一成 `ActionEnvelope` 概念，至少包含：

- `action_id`
- `resource_path`
- `resource_type`
- `action_type`
- `request_user`
- `request_user_dept`
- `row_id / row_ids`
- `request_body`
- `old_values`
- `trace_id`
- `callback_type`
- `callback_payload`
- `idempotency_key`

这样 `table.update`、`form.submit`、`docs.update`、`board.delete` 都能进入统一判断面。

### 流程策略

策略应当是**结构化配置**，而不是直接执行自然语言。

AI 的职责：

- 把用户描述转换成结构化规则

系统的职责：

- 解析规则
- 命中规则
- 创建流程实例
- 执行审批和回放

例如：

- 当 `status = 下线` 时进入审批
- 当 `salary_max > 50000` 时进入审批
- 当删除超过 10 条记录时进入审批
- 当更新文档标签包含 `生产规范` 时进入审批

### 真实执行时机

最关键的原则是：

**审批通过之前，不执行真实回调。**

也就是说：

- `table.create` 命中审批后，不直接调用 `OnTableAddRow`
- `table.update` 命中审批后，不直接调用 `OnTableUpdateRow`
- `table.delete` 命中审批后，不直接调用 `OnTableDeleteRows`
- `form.submit` 命中审批后，不直接进入真实业务处理

审批通过后，再由 `flow-server` 回放执行。

### 幂等与回放

因为审批通过后会发生“延迟执行”，所以必须重点保证：

- 动作幂等
- 回放安全
- 状态机明确
- 重试可控

否则会出现重复审批、重复执行、脏写入等问题。

## 与现有权限审批的关系

当前仓库里已有“权限申请审批”相关实现，但那只是一个垂直场景。

`flow-server` 的定位更广：

- 权限审批只是 `flow-server` 的一个具体 use case
- 后续其他业务动作都可以接入同一套流程能力

因此 `flow-server` 应该独立存在，不和某一个具体业务审批模型强耦合。

## 设计原则

### 1. 审批挂在动作上，不挂在页面上

真正需要控制的是动作，而不是页面类型。

### 2. 字段级规则优先

企业里最值钱的审批，经常是：

- 某字段改成某值要审批
- 某字段变化超过阈值要审批
- 某类字段被改动时要审批

### 3. 平台负责审批，业务负责回调

业务系统不自己维护审批状态，不自己做流程引擎。

### 4. AI 负责生成，系统负责固化

用户可以用自然语言描述流程，但最终必须落成结构化 DSL 或 JSON 配置。

### 5. 先轻后重

第一阶段先把：

- 单步审批
- 条件命中
- 审批通过后回放执行

做稳定。

后续再加：

- 串签
- 并签
- 会签
- 条件分支
- 超时
- 催办
- 转交
- 加签
- 委托

## 第一阶段目标

`flow-server` 第一阶段建议只打透四件事：

1. `table.create`
2. `table.update`
3. `table.delete`
4. `form.submit`

只要这一阶段跑通，平台就已经具备非常强的横切审批能力。

后续再逐步扩展到：

- `docs`
- `board`
- 平台管理动作
- 外部 API 写操作

## 一句话总结

`flow-server` 不是某个审批模块，而是平台级的：

**动作控制中心 + 审批引擎 + 执行前置网关。**

它要解决的不是“怎么做一个审批页面”，而是：

> **如何让平台上的任意关键动作，都能在统一策略下先审批、后执行。**
